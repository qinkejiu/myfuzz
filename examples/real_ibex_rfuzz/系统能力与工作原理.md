# MyFuzz 系统能力与工作原理

## 1. 系统目标

MyFuzz 把处理器 RTL、接口事实、ISA 契约和测试输入连接成可重放的执行流程。
本例使用真实 Ibex：自动验证接口、选择 OBI adapter、生成接线和契约转导器，
编译 Verilator 模型，再由官方 RFuzz 客户端驱动测试并收集反馈。

本例采用 `input_mode=contract_transducer`。尚未初始化、可生成指令的内存地址，
其首次指令内容来自 RFuzz 周期记录；握手选择、首次数据内容、中断和 debug request
也具有明确的输入来源。系统的编码约束、协议状态和内存状态共同决定 CPU 看到的输入。

## 2. 总体数据流

```text
固定 RTL 源码 + source-backed 接口描述 + ISA/内存域契约
  → 源码和 elaborated 物理端口验证
  → instruction/data 边界识别与 OBI adapter 选择
  → 自动组合、请求仲裁和 RTL 接线
  → 编译 contract_transducer 与 cycle layout
  → Verilator 编译真实 Ibex 和转导器

固定 TestHeader + RFuzz 周期记录
  → transport 解包
  → 指令修复 / 协议状态 / main 共享内存 / 外部字段绑定
  → 真实 RTL 执行
  → 官方 RFuzz 共享内存回复与反馈增益判断
  → 语料保存、同构建重放、独立重建重放
```

## 3. 分层架构

| 层次 | 职责 | 主要结果 |
| --- | --- | --- |
| 源码事实层 | 核对 revision、源码闭包、模块及 elaborated 端口 | source/elaboration evidence |
| 接口语义层 | 声明 clock、reset、boot、IRQ、debug 和 memory role | interface description |
| 处理器边界层 | 识别 instruction/data endpoint | processor boundary |
| 协议与组合层 | 选择 adapter，生成仲裁、后端和唯一驱动接线 | composition IR、generated top |
| 契约层 | 编译 ISA 修复、响应状态、共享域和周期位布局 | contract plan、cycle layout、transducer RTL |
| 执行层 | 编译真实处理器并核对请求、响应和首次初始化 | simulator artifact、execution proof |
| 反馈层 | 执行共享内存交换，保留有反馈增益的输入 | receipts、coverage、corpus |
| 重放层 | 核对输入、构建、契约和反馈身份 | manifest、replay evidence |

缺失或矛盾的接口、宽度、来源和哈希会导致验证失败。RFuzz 字节的合法化规则则由
已编译契约明确规定，可以检查和复现。

## 4. 源码和接口事实

接口描述记录固定源码根目录与 revision、源码文件和 include roots、顶层参数、
endpoint 功能、字段 role 及物理端口。系统用 elaboration 证据核对方向、宽度和类型。

对于 packed struct/array，物理绑定还必须具有容器宽度、member offset 和 member
width 的编译证据；不能只凭成员名称猜测切片。CPU 名称用于标识来源，协议适配和接线
选择依据 protocol、capability、role、方向和宽度。

## 5. 协议归一化与自动组合

本例的两个 OBI endpoint 经 adapter 归一为 `processor-memory-beat@1`：
请求 valid/acceptance、地址、读写、write data、byte enable，以及 response data/error。
系统生成 instruction/data 请求仲裁，并跟踪响应所属的请求。

```text
Ibex instruction OBI ──► adapter ──┐
                                 ├─► 仲裁和 backend ─► contract_transducer
Ibex data OBI ─────────► adapter ──┘                         │
                                                     main 字节内存
```

组合阶段可以保留组件 profile 和地址规划等元数据；此 constrained 执行路径禁用固定
target。输入中的 `personality` 因此不能证明 scratch、GPIO 或 timer 外设已经实际
执行，也不能作为外设通过验收的依据。旧固定启动内存路径已从本示例移除。

系统还包含 AXI4 和 TL-UL 的归一化适配路径，但本例只对所选 Ibex OBI 路径提供运行
证据。接入另一协议或处理器时，仍需相应的接口和真实执行验收。

## 6. 输入约束

本例的 ISA 为 RV32IMC、M 特权级、2 字节指令对齐，memory beat 为 32 位。
`memory_domains` 同时将 `instruction_memory_master` 和 `data_memory_master`
绑定到 `main`。

测试输入由固定头和等宽周期记录构成：

- `cycle_test.v1` 测试头包含 layout/contract hash；固定 reset_cycles=2、
  execution_cycles=200、boot_address=128、hart_id=0、illegal_instruction=false。
- 周期布局为 104 位，包括两个 8 位 `instruction_selector`、32 位
  `instruction_payload`、压缩标记、3 位 `response_choice`、32 位
  `response_data` 和 20 位外部输入。
- 外部输入覆盖软件、定时器、外部和 15 位 fast interrupt，以及
  `nonmaskable_interrupt` 和 debug request。
- transport 每周期使用 16 字节，大端高位承载 payload，末尾 24 位 padding。
  本例 live/语料入口要求完整记录且不超过测试头执行上限。

精确位区间、配置与计算公式见 [README 的输入约束说明](README.zh-CN.md#3-输入约束与精确位布局)。
时钟、复位由仿真调度；其他固定物理控制来自测试头和 `control_defaults`。

### 指令选择和修复

32 位合法模式有 56 个模板，16 位有 26 个模板，以
`floor(selector × template_count / 256)` 选择操作，再修改模板约束位。
压缩指令按需补非零寄存器或立即数。

例如 selector=0、32 位 payload=`0xffffffff` 生成 ADDI `0xffff8f93`；16 位
selector=0、payload=0 生成 C.ADDI4SPN `0x0020`。压缩模式下两个 selector 分别
处理低、高 16 位槽。首次生成使用响应完成周期的记录。

这些规则保证已实现契约的编码合法性；寄存器值、地址、CSR 和处理器状态仍可能使执行
进入 trap。CPU 已写入的内存字节会原样返回，不会再次按 ISA 修复。

### 协议修复与有界等待

`response_choice[0/1/2]` 分别表达接受、响应和错误注入请求。转导器根据已有状态
筛选这些选择：无 request 不 grant，无 pending 不 response；同一请求的接受和响应
分属不同周期，响应不接受替代请求。

`max_wait_cycles=16` 为接受和响应两个阶段分别设置强制完成界限。本例
`allow_error=false` 关闭随机 error 注入，但容量或 provenance 错误仍有效。
OBI adapter 将完成事件注册后送给 CPU，整个链路还包含外层仲裁和 backend 延迟。

### 同地址一致性与 test_begin

共享内存按 `(domain, address & ~3)` 保存小端字节。首次读取生成后，同址重复读取
复用内容；CPU 写入通过 byte enable 更新指定字节 lane，数据端能读到指令端生成的
内容，取指也能观察 CPU 写入。

先由随机 data read 初始化的 beat 随后被 fetch，会返回 `provenance_error`。
零 byte enable 不分配或修改内容；容量达到 256 entries 后返回容量错误，不驱逐
已有地址。

每个测试的 `test_begin` 清空字节和 provenance，并锁存测试头；测试内 DUT reset
清除 pending 和等待状态，保留内存。相同头和周期记录因此能够复现同一状态演进。

## 7. 真实 CPU probe

组合命令先编译真实 Ibex，再两次运行 80 周期的全零 RFuzz 格式输入。全零 selector
和 payload 会经转导器生成 ADDI `0x00000013`；首次指令仍来自输入记录。

probe 检查 instruction request/response、至少两个不同地址的首次指令初始化、
零转导器/协议错误，以及两次执行与反馈一致。全零 probe 是确定性构建探测；
官方 RFuzz live 阶段会变异周期记录，二者的证据应分别核对。

## 8. RFuzz 反馈闭环

```text
官方 RFuzz client
  → SysV shared-memory 请求
  → 真实 Ibex + 转导器执行周期记录
  → sampled RTL 信号事件计数
  → 对应 shared-memory 回复 receipt
  → 反馈增益判断
  → corpus 保存
```

反馈类型是 `sampled-dut-signal-bit-events-u8-saturating`，覆盖所选 RTL 信号位和
backend 事件的采样变化。它不能表示源码行覆盖率或分支覆盖率。

只有完整提交并收到对应回复的测试，才计入 `completed_feedback_exchanges`。
RFuzz 保留产生新反馈的输入，因此测试数、完成交换数和语料数具有不同含义。

## 9. 语料重放

`test` 命令使用本次 artifact 重放保存的语料。另一个 `replay` 命令在新目录
独立重建 simulator，核对原有 corpus manifest 和每条 coverage。

重放身份包含原始输入、周期 layout、contract/transducer、测试头、固定物理控制、
simulator input 和 simulator binary 的哈希。本例 `constraint_hash` 绑定转导器契约。
独立重建核对 composition、输入契约、测试头、固定控制、原始输入和覆盖反馈；
二进制哈希按每次构建分别记录，允许因构建路径而改变。
重放还分别比对实际计数器与原 `coverage_sha256`、保留 trace 字节与原 `trace_sha256`。
仿真程序的内部 v2 请求/响应通过单调 64 位编号关联，旧反馈不能冒充下一测试结果；
该编号不改变 DUT 输入或官方客户端的共享内存格式。旧仿真程序需要重新构建。

```bash
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src:. JOBS=1 nice -n15 \
  python3 examples/real_ibex_rfuzz/run_example.py replay \
  --input examples/real_ibex_rfuzz/input/ibex-scratch.json \
  --output runs/examples/contract-rfuzz-5s \
  --build-output runs/examples/contract-rfuzz-replay
```

`--output` 指向已有测试目录，`--build-output` 必须是新目录。

## 10. 接入更多 CPU 和外设

### CPU 直接组合条件

新 CPU 需要固定、可验证的 RTL 源码闭包和 revision，明确的顶层参数、时钟、复位、
boot/hart/interrupt/debug 控制，以及完整的 instruction/data endpoint 描述。
每个字段必须具备 role、方向、宽度和物理绑定；packed 字段还需 elaboration 证明。

协议必须落在现有 adapter 支持范围，ISA 必须符合当前指令转导器实现，memory domains
必须明确绑定。接口通过验证以后，仍需完成真实 CPU probe、官方客户端短测和重放，
不能只凭编译成功判断执行正确。

### 外设直接组合条件

一般组合路径可以接入声明了来源、参数和协议 capability 的组件。
实现 `processor-memory-beat@1` 的外设需要提供 request acceptance、地址和读写语义、
write data/byte enable、response completion、read data/error 以及 reset flush。

当前 constrained 示例的请求由转导器统一处理。要验证实际外设行为，需要另行建立并
验收会把请求路由到该外设的执行配置；仅替换 personality 名称或 profile 不足以完成。

### 系统不会自动猜测的内容

未知总线协议、缺失的字段 role/方向/宽度、无编译证明的 packed slice、超出 adapter
范围的多 outstanding 或乱序行为，都需要先补充通用契约。系统也不会猜测特殊启动
步骤、宏或生成工具依赖，以及外设的 completion/error 语义。

接入流程是固定源码、补齐接口事实、验证适配范围、检查组合和转导器产物，再进行真实
构建、probe、短测和重放。接口描述完整与执行验收通过是两个分别需要证据的条件。
