# MyFuzz 系统能力与工作原理

## 1. 系统目标

MyFuzz 是一个面向真实 RTL 处理器的自动组合与反馈驱动测试平台。它希望解决的
核心问题是：给定处理器 RTL、接口描述、ISA 契约和外设后，不再为每款处理器手工
编写测试顶层，而是自动完成接口验证、协议适配、地址分配、RTL 接线、输入约束、
仿真编译和 RFuzz 测试。

系统当前有两条相关路径：

1. Verilog/SystemVerilog 源码级插桩与传统 RFuzz 执行。
2. 协议感知的处理器自动组合与真实 CPU RFuzz 执行。

本文重点说明第二条路径。

## 2. 总体数据流

```text
处理器 RTL 源码
+ source-backed 接口描述
+ ISA 契约
+ 外设声明
+ 可随机化字段
        │
        ▼
源码与 elaborated 物理端口验证
        │
        ▼
识别通用处理器边界
        │
        ▼
按协议事实选择 OBI / AXI4 / TL-UL adapter
        │
        ▼
选择组件、分配地址、生成仲裁和唯一驱动接线
        │
        ▼
生成 Composition IR 与 SystemVerilog 顶层
        │
        ▼
生成 RFuzz 输入布局并投影 ISA/字段约束
        │
        ▼
Verilator 编译真实处理器模型
        │
        ▼
真实 CPU 启动、取指、执行和外设访问
        │
        ▼
官方 RFuzz 共享内存测试与 RTL 反馈
        │
        ▼
新语料保存、身份记录和真实 RTL 重放
```

## 3. 分层架构

| 层次 | 职责 | 主要结果 |
| --- | --- | --- |
| 源码事实层 | 验证源码版本、源码闭包、模块和端口 | source/elaboration evidence |
| 接口语义层 | 为真实端口声明 clock、reset、interrupt、memory 等角色 | interface description |
| 处理器边界层 | 将 CPU 的 instruction/data endpoint 归一化 | processor boundary |
| 协议层 | 根据事实选择 OBI、AXI4 或 TL-UL adapter | processor-memory-beat |
| 组合层 | 选择组件、分配地址、生成仲裁和接线 | composition IR、generated top |
| 约束层 | 将逻辑字段转换为受约束的 RFuzz 输入布局 | layout、constraint hash |
| 执行层 | 编译并启动真实 CPU，检查取指和进展 | simulator artifact、execution proof |
| 反馈层 | 执行 RFuzz IPC 并保存有增益的输入 | receipts、coverage、corpus |
| 重放层 | 重新执行语料并验证完整身份 | corpus manifest、replay evidence |

这些层之间使用明确的数据契约连接。接口、宽度、来源或哈希不一致时会失败关闭，
而不是猜测或静默修正。

## 4. 源码和接口事实

接口描述不只记录端口名称，还记录：

- 源码根目录和固定 revision；
- 参与 elaboration 的完整源码闭包；
- 顶层模块和参数；
- 端口方向、宽度和类型；
- packed struct/array 的容器宽度与 member offset；
- endpoint、字段 role、协议和 capability；
- clock、reset、boot、hart、interrupt 和 debug 控制语义。

对于 CVA6 这类大量使用 packed AXI 结构的设计，系统使用 Verilator elaboration
给出的物理坐标，不根据成员名称猜测切片。缺失、重叠、超出容器或来源不一致的成员
绑定都会被拒绝。

## 5. 通用处理器边界

系统把不同处理器的真实端口统一描述为：

```text
processor boundary
├── clock/reset
├── boot address
├── hart ID
├── interrupts/debug request
├── instruction-memory endpoint
└── data-memory endpoint
```

生产组合路径不通过 `if cpu == "ibex"`、`if cpu == "cva6"` 选择组件。CPU 名称只
作为配置和报告信息；真正的选择依据是 endpoint protocol、字段 role、方向、位宽、
capability 和 compiler-proven physical port。

## 6. 协议归一化

不同 CPU 的总线经过 adapter 归一成统一的通用后端：

```text
Ibex OBI  ─────► OBI adapter  ───┐
CVA6 AXI4 ─────► AXI4 adapter ───┼──► processor-memory-beat
TL-UL endpoint ► TL-UL adapter ──┘
```

`processor-memory-beat` 统一表示：

- request valid 和 acceptance；
- 地址与读写类型；
- write data 和 byte enable；
- response completion；
- read data 和 error；
- 请求与响应背压。

当前后端采用单 outstanding、按序完成和有界等待，便于明确判断 completion、错误、
超时和复位恢复。

## 7. 自动组合

组合器从接口和组件事实自动完成：

1. 识别 instruction/data memory endpoint。
2. 根据 `obi@1` 等协议事实选择 adapter。
3. 添加启动 RAM 和选定的寄存器外设。
4. 分配互不重叠并满足对齐要求的地址区间。
5. 生成 instruction/data 请求仲裁。
6. 连接 CPU、adapter、arbiter、backend 和 peripheral。
7. 检查每根网络的驱动唯一性和方向一致性。
8. 生成稳定、可哈希的 Composition IR。
9. 渲染 SystemVerilog 顶层并交给 Verilator。

真实 Ibex scratch 示例形成的结构为：

```text
                  ┌──────────────┐
RFuzz inputs ────►│  Real Ibex   │
                  └──────┬───────┘
                         │ OBI
                  ┌──────▼───────┐
                  │ OBI Adapter  │
                  └──────┬───────┘
                         │ processor-memory-beat
                  ┌──────▼───────┐
                  │   Arbiter    │
                  └───┬──────┬───┘
                      │      │
              ┌───────▼─┐  ┌─▼────────────────┐
              │ Boot RAM│  │ Scratch Registers│
              └─────────┘  └──────────────────┘
```

## 8. 输入约束

RFuzz 产生的是原始字节，但这些字节不会直接连接真实 DUT：

```text
RFuzz raw bytes
  → transport unpack
  → ISA / enum / range / mask constraint projection
  → logical field values
  → compiler-proven scalar port 或 packed slice
  → real processor RTL
```

示例输入文件是：

```text
examples/real_ibex_rfuzz/input/ibex-scratch.json
```

其中 `randomizable_fields` 只允许软件中断、定时器中断、外部中断和 fast interrupt
进入 fuzzer 布局。时钟、复位、boot address、hart ID、fetch enable 等字段由
`control_defaults` 固定，原始 fuzzer 输入不能覆盖。

系统为每个输入记录 raw hash、layout hash、constraint hash、物理控制 hash、仿真
输入 hash 和 simulator binary hash，防止配置或构建变化后仍被误认为相同测试。

## 9. 真实 CPU 启动验证

Verilator 编译完成并不等于 CPU 已正确运行。系统先装载最小 RISC-V boot image，
然后验证：

- 首次取指地址是否等于 reset vector；
- 首次取指数据是否与 boot image 一致；
- 是否读取多个不同地址并产生执行进展；
- backend 是否产生 completion；
- CPU 是否完成预期的外设 pass 写入；
- 是否出现协议错误；
- 两次相同输入的执行与反馈是否一致。

本次 80 周期真实 Ibex probe 的结果：

```text
requests:             11
completions:          11
successful_reads:     10
progress_events:      10
pass_completions:      1
errors:                0
first_fetch_matched:   1
```

## 10. RFuzz 反馈闭环

```text
RFuzz client
  → SysV shared-memory request
  → Verilator 执行真实 CPU
  → sampled RTL event counters
  → shared-memory reply receipt
  → RFuzz 判断反馈是否增加
  → 保存有增益的输入
```

当前反馈类型是 `sampled-dut-signal-bit-events-u8-saturating`，包括显式随机化的
中断输入位和内部 backend request/response 事件。它是 RTL 信号事件反馈，不是源码
行覆盖或分支覆盖。

只有经过共享内存 FIFO 完整提交并收到对应回复的测试，才计入
`completed_feedback_exchanges`，也只有这种 receipt 可以证明语料完成了真实 IPC
交换。

## 11. 新反馈与语料

RFuzz 保存语料的条件不是“执行了一次测试”，而是“产生了此前未观察到的反馈”：

```text
输入 A → 无新反馈       → 不保存
输入 B → 新反馈位置 5   → 保存
输入 C → 与 B 相同      → 不保存
输入 D → 新反馈位置 8   → 保存
```

因此 15,357 次 RTL 测试只有 19 条语料是正常的。大多数变异没有扩展反馈状态，只有
这 19 条输入产生了值得保留的反馈增益。

## 12. 语料重放

保存后，每条 corpus 输入都会再次送入真实 RTL。系统要求新反馈与保存时完全一致，
并核对：

- 原始输入 SHA-256；
- layout hash；
- constraint hash；
- simulator binary SHA-256；
- 固定物理控制 SHA-256；
- simulator input SHA-256；
- replay key。

正式 campaign 还会从保留源码重新构建 simulator，再重放全部语料，用来排除残留
进程状态、临时文件或某次构建偶然行为的影响。

## 13. 接入更多 CPU 和外设

可以继续选择其他 CPU 或外设进行组合，但“随机选择”不等于只给一个 RTL 文件和若干
端口名称就一定能够直接运行。只要新组件满足当前协议与来源契约，并提供完整接口描述，
它就可以走通用自动组合路径，而不需要在生产代码中增加 CPU 名称判断。

### 13.1 CPU 直接组合条件

新 CPU 至少需要提供：

- 固定、可验证的 RTL 源码闭包和 Git revision；
- 明确的顶层模块、参数、时钟和复位；
- boot address、hart ID、interrupt、debug 等控制接口说明；
- instruction/data memory endpoint；
- 当前支持的处理器总线协议之一：`obi@1`、`axi4@1` 或 `tl-ul@1`；
- 每个协议字段的逻辑 role、方向、位宽和物理端口；
- packed 接口的 compiler-proven container width、member offset 和 width。

OBI instruction endpoint 的部分字段可以描述为：

```json
{
  "endpoint_id": "processor.instruction_memory",
  "protocol": ["obi", "1"],
  "fields": [
    {
      "role": "request",
      "direction": "output",
      "width": 1,
      "physical": {"port": "instr_req_o"}
    },
    {
      "role": "address",
      "direction": "output",
      "width": 32,
      "physical": {"port": "instr_addr_o"}
    },
    {
      "role": "grant",
      "direction": "input",
      "width": 1,
      "physical": {"port": "instr_gnt_i"}
    }
  ]
}
```

这只是字段格式示意。正式描述必须覆盖协议契约要求的全部字段，并通过方向、位宽和
物理来源验证。

### 13.2 外设直接组合条件

最容易直接接入的是实现统一 `processor-memory-beat@1` 后端的外设。外设 profile
至少需要声明组件名称、模块、源码和参数，例如：

```json
{
  "name": "my-register-device",
  "module": "my_register_device",
  "source": "rtl/my_register_device.sv",
  "mode": 0
}
```

对应 RTL 需要实现：

- request valid/acceptance；
- address 和 read/write 类型；
- write data 和 byte enable；
- response completion；
- read data 和 error；
- reset flush。

满足该契约后，系统可以自动形成：

```text
CPU bus
→ OBI/AXI4/TL-UL adapter
→ arbiter
→ processor-memory-beat
→ new peripheral
```

使用 APB、Wishbone 或 AXI4-Lite 的外设也可以接入仓库已有协议路径，但必须提供相应
protocol manifest 和 component profile，不能把不同协议伪装成
`processor-memory-beat@1`。

### 13.3 系统可以自动完成的工作

接口描述完整后，通用路径能够自动：

1. 根据协议和 capability 事实选择 adapter；
2. 将 instruction/data endpoint 接入统一后端；
3. 选择启动 RAM 和外设；
4. 分配对齐、互不重叠的地址区间；
5. 生成请求仲裁；
6. 生成 CPU、adapter、backend 和外设接线；
7. 检查唯一驱动、方向、位宽和 packed slice；
8. 生成 Composition IR 和 SystemVerilog 顶层；
9. 生成受约束的 RFuzz 输入布局；
10. 编译 Verilator 并执行真实 CPU probe；
11. 运行 RFuzz，保存并重放有反馈增益的语料。

### 13.4 系统不会自动猜测的内容

以下信息缺失或超出当前契约时，不能直接组合：

- 未知总线协议；
- 只有端口名称，没有字段 role；
- 未声明输入输出方向或位宽；
- packed member 没有 elaboration 证明；
- coherent TileLink 等当前契约未覆盖的协议；
- 多 outstanding 或乱序行为超出当前 adapter 模型；
- 外设没有 completion/error 语义；
- CPU 需要特殊启动序列，但配置没有描述；
- RTL 依赖宏、参数或生成工具，但没有提供完整源码闭包。

遇到这些情况，系统会失败关闭。正确的扩展方式是补充名称无关的协议契约、adapter
或启动能力描述，而不是增加 `if cpu_name == ...` 的专用分支。

### 13.5 推荐接入流程

对每个新 CPU 或外设，建议按以下顺序处理：

```text
1. 固定源码 revision
2. 收集完整源码闭包、参数和生成设置
3. 生成并验证 elaborated physical ports
4. 编写 source-backed interface description
5. 构建通用 processor boundary
6. 验证现有 protocol adapter 能否匹配
7. 运行自动组合并检查生成 IR/RTL
8. 编译并执行约 80 周期的启动探测
9. 运行 5 秒官方 RFuzz 短测
10. 检查语料、反馈 receipt、重放和资源清理
11. 短测稳定后再进入正式长测
```

因此，新 CPU 使用 OBI、AXI4 或当前范围内的 TL-UL，并且接口描述完整时，通常可以
直接组合；新外设实现 `processor-memory-beat@1` 或已有协议 profile 时也可以直接加入。
未知协议或特殊启动结构则需要先扩展通用契约。

## 15. 使用示例

自动组合、编译和真实 CPU probe：

```bash
bash examples/real_ibex_rfuzz/commands.sh compose \
  runs/examples/my-ibex-compose
```

执行 5 秒官方 RFuzz 测试：

```bash
bash examples/real_ibex_rfuzz/commands.sh test \
  runs/examples/my-ibex-rfuzz-5s 5
```

检查结果：

```bash
bash examples/real_ibex_rfuzz/commands.sh inspect \
  runs/examples/my-ibex-rfuzz-5s
```

更完整的输入字段、依赖准备、输出文件和故障排查说明见同目录的
`README.zh-CN.md`。

## 16. 尚未完成的验收

当前已经证明“自动组合→协议适配→输入约束→真实 CPU→RFuzz→语料→重放”主链路
可以正确运行，但不能据此宣称全部长期验收完成：

- BOOM 真实处理器协议验收按要求暂缓；
- GPIO 和 timer personality 尚未完成本轮真实 CPU 长测；
- 三组各 300 秒的 Task 15 campaign 尚未执行；
- 5 秒结果是功能预检，不等同于三组 300 秒的稳定性门禁。
