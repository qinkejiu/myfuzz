# Independent native reset-resume gate design

This designs a directed actual warm/cold reset-resume experiment, not a result or reset-default certificate. Use separate new directories and serial single-worker resource supervision for each policy's generation and fresh CLI. Do not edit earlier alias/mask gates or their frozen identities. Current new Session/integration source closure and build identities differ from those earlier gates; all current sources, adapters, generated artifacts, frozen inputs and actual binaries must be revalidated. A copied old cache can only be a build candidate, never a restored session, reset fact or authority.

Use two original requests to GPIO A `INTEN.value`: READ before reset with an actual full-word RAM result at a safe address, then READ after reset/resume with a different actual RAM result address. Each request must run through current compiler, runtime registration, source gate, actual CPU callback, ordinary APB association and issued RAM token. Finish with schema18, full original requests and recorded schedules, authenticated production save and separate production fresh file replay. Do not hand-set waiting PC, source epoch, target epoch, counters or memory generation. A pure preview may be inspected, but submission must use actual fresh context.

The old actual mask plan was read directly: it records 53 initial warmup commands, each schedule `[cpu,gpio_a,gpio_b]`, totaling159 component steps. Its template max_steps is512. This is measured initial startup evidence, not a guaranteed reset latency. The new per-reset resume budget512 therefore leaves353 steps beyond that measured baseline. A three-component scheduler call permits at most170 such commands (510 steps); use current actual capacity checks to stop before exceeding the limit. Each loop iteration calls `Session.advance_after_reset` and records the real command, stopping only when actual `cpu.waiting_instruction_address` identifies a declared missing instruction word. Never fall back to unrecorded Runner steps when the budget or API refuses.

Cold reset normally removes materialized online code and changes actual RAM generation, so actual bootstrap can return to the first missing online slot. Warm reset retains actual RAM/program materialization and generation; after bootstrap, the old first READ fragment may execute again before the CPU reaches its next missing slot. Its result store is a real extra callback and must be drained/journaled, but it occurs outside a new selected registration and cannot manufacture another selected READ certificate. Exact actual waiting transaction/address/epoch/generation are recorded in the second request's fresh manifest. The original before certificate stays historical; current qualification after reset must belong to the new epoch only.

Expected counts are planning estimates to diagnose extra work, not assertions that replace observation. If the fixed bootstrap executes its six MMIO writes once per epoch, cold may have initial6 + selected-before1 + resumed-bootstrap6 + selected-after1 =14 associations,42 APB events and two selected RAM results. Warm may additionally reexecute the retained first READ, yielding15 associations,45 APB events and a third physical RAM result. If ISR, retries, waiting behavior or additional access changes these counts, capture and explain the complete stream rather than discard it or force the estimates. Always separately assert two selected original READs, their own actual result commits, complete request/accept/response chains and correct certificate scope. A warm reexecution without active selected submission cannot be counted as selected-case authority.

A.INTEN is a useful quiet target: actual fixed bootstrap source writes GPIO B offsets0x04,0x18(INTEN),0x1c(INTTYPE_LOW), then GPIO A offsets0x00,0x04 and0x0c(PADOUT). It does not write A.INTEN at0x18. The fixed ISR reads B.PADIN/status and writes A.PADOUT, also not A.INTEN. Plain INTEN READ has declared side_effect none and needs no side-effect permission. The pinned RTL resets `r_gpio_inten` to zero, but merely observing before/after zero and authentic RAM readback must remain ordinary read-result consistency; without a dedicated actual reset seal/conditioned rule it is not a reset-default certificate.

IRQ must still be observed. Bootstrap explicitly enables B.INTEN0x101, GPIO enable0x101 and CPU interrupts; low eight A.gpio_out bits route to B inputs. Driver resets, rerun bootstrap writes and synchronizer changes could cause a transient edge even though the intended initial input/output levels are zero. Do not infer CPU masking or disable the ISR/route in synthetic state. Capture actual CPU step commanded inputs, raw CPU physical IRQ and GPIO B physical interrupt, policy source/pulse states and actual IRQ journal events for startup, reset and resume. Distinguish a legitimate `pulse_cancelled_by_reset` from post-reset new edges; READY/END restart and `reset_barrier` are real lifecycle observations, not permission to ignore later pulses. If any ISR runs, identify its extra actual MMIO/RAM and its effect on selected attribution. The field choice reduces interference risk but does not prove none occurred.

Record resource receipts, phase boundaries, original requests, case manifests, actual case receipts, startup/reset/resume journal slices, reset barrier/physical process receipts, CPU waiting diagnostics, generation/epoch snapshots, complete ordinary/verifier state, source pins and current build cache inputs/binaries. Before enabling fresh, require complete generation within the existing wall/RSS policy and no source drift. After separately completed fresh, compare full plan/trace semantic digest/event count and exact ordinary/verifier/gate/runtime/terminal state. Run the large independent JSON audit only after both processes exit to avoid changing available-memory-derived limits.

The gate can establish actual recorded reset→scheduler resume→new current-context admission and fresh reconstruction of ordinary READ consistency. It cannot establish generic-component RTL, storage/writer versions, active prerequisites, IRQ acceptance/retirement, functional completion, reset defaults, aggregate L2, the complete permission/width/effect matrix or all E2/Stage2. Scheduler failure halts and refuses export; schema19 is not a codec for partial failed resume. The independent serializer/checker dispatch REDs must first become GREEN on the final source; this design is not a substitute for those fixes.
