# F1–F4 阻断修复与最小路径（2026-10-30）

范围：CPU ↔ 宿主 fabric（RAM/Router）↔ IP 的交互；不判定 DUT 内部正确性。DUT 断言将来单独插入；当前 Verilator 命令行没有 `--assert`，所以本文不声称任何断言通过。F5–F6 未改。

## 1. 两个阻断问题

### 1.1 OBI 取指停放被误判为协议违规

现象（batch20，`result-i2c-ibex-obi-profile/original/failure.json`）：F3 首例在 tick 33 报 `obi_response_wait_budget_exceeded` 与 `obi_request_wait_budget_exceeded`，`wait_cycles=16`（`max_wait_cycles=16`）。实际原因是宿主有意让 CPU 停在下一条尚未物化的指令槽：`PersistentMemory._check_instruction_ready` 抛 `InstructionNotReady`，会话记录 `_waiting_instr` 并停止 grant；一次用例仍推进 128 轮，host 检查器把这段宿主停顿累计成超时。

修复：`src/myfuzz/runtime/flows/memory.py::fragment_boundary_park`。用例推进到 `cursor + len(code)`（片段末尾的下一条未物化槽）后，再保留一个小的 settle 窗口就结束本用例，窗口不超过 CPU 声明的 `max_wait_cycles - 4`（最多 12），因此 host 检查器的等待计数仍低于上限。F1/F3 在 `submit_memory_case`、F2/F4 在 `CompiledMmioRuntime.submit` 使用同一助手；结果/证书记录 `instruction_boundary_park = {address, expected_address, tick, settle_advances, park_observations, stopped_after_advance, reason}`。没有扩大 `max_wait`、没有关闭检查器、没有改 `cpu_session` 的 park 语义。

settle 窗口是必要的：历史通过样例中，APB 目标对 F2/F4 的响应可比 CPU 取到片段末尾晚约 6–9 个 tick；若在第一个 park tick 立即结束，会截断目标事务，导致 hop join 缺失。

### 1.2 Wishbone UART 写策略与副作用耦合

`zipcpu_uart` 的 `SETUP` 真实 `read_mask=write_mask=0x7fffffff`、`side_effect=write_resets_uart_state`。旧校验要求 masked 写同时满足 `write_policy=full_word_reserved_zero` 和 `side_effect=none`，而 capability 解析又禁止有副作用字段声明该策略，因此 batch21 在候选阶段报 `register-candidate-masked-merge-policy-undeclared`。

修复：

- `configs/peripherals/zipcpu_uart/test_capability.json`：`SETUP/value` 增加 `write_policy: full_word_reserved_zero`；mask 与副作用保持真实值，不改成 `0xffffffff` 或 `none`。
- `src/myfuzz/composition/test_capability.py`：策略只约束“全字、`lsb=0`、`width=32`、`read_mask==write_mask`、`0<write_mask<0xffffffff`”，不再要求无副作用；副作用仍与 profile 独立比对。
- `src/myfuzz/scenario/register_source_access.py`：masked 写接受真实副作用；要求 capability 的 side_effect 与 profile 一致，值中保留位仍必须为 0，不做 host 读改写/合并。
- `scripts/generate_mmio_scenario.py`：mask 不为全 1 时无条件要求该策略。
- `src/myfuzz/runtime/descriptor_preflight.py`：preparation 完成后用与运行相同的布局解码实际 F4/F2 记录并调用 `declare_writer`/`declare_reader`，逐条写入 `rows[flow].candidates`（`ok`/`refusal`）。

## 2. 性能

- 宿主真正推进 DUT 的时间很小：AXI×APB 4 例 `execution_seconds=3.6`、`wall=34.4`；AHB×APB 4 例 4.8 / 74.6。占比最大的是装配/构建/导出与默认的同进程 replay；F1–F6 八例中 replay 可达 64%。
- `scripts/run_generic_scenario.py` 新增 `--execution-mode {develop,search,acceptance}`：`search` 跳过默认的同进程 replay；`--mode fresh` 仍做独立新进程 replay。批量验证按此运行，原始运行不再重复全前缀重放。
- 本批 6 个场景静态 preflight 用时 5.9–27.0 s（AHB 最慢，主要是一次 elaboration），F2/F4 实际候选全部 `ok`。

## 4. 支持范围与 unknown

- CPU：OBI、Wishbone、AHB-Lite、AXI4-Lite；IP 目标：APB3、Wishbone。AHB/AXI 的 IP 目标未适配。
- 单价 32 位字、单 IP 目标；addressless Wishbone 目标和更宽/更窄访问仍需单独声明。
- 退休、RAM 读取版本、跨例来源、IP 内部状态、寄存器副作用、F5/F6、覆盖率均为 unknown；不加证书、不授奖励。
- `--execution-mode search` 只减少重复 replay，不改变实际执行路径或输入；fresh replay 仍需单独运行。
