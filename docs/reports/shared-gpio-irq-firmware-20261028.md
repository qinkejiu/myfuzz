# Shared single-GPIO IRQ firmware opt-in

`configs/scenarios/compiled-f1-f5-ibex-gpio-shared/generic_scenario_irq.json` explicitly selects the authenticated `ibex_rvfi_local` CPU and fixed single-GPIO firmware; `configs/search/gpio-shared-irq.json` uses the existing unified search entry. Default pin descriptors remain unchanged. The original CPU adapter class is retained with native IRQ receipts enabled.

The layout preloads fixed executable images within the first 0x800 image bytes, separate from dynamic case slots beginning at image_start+0x1000. The vector is image_start+0x200, handler +0x400, register-save scratch +0xc00, and dedicated PADIN/status/count result words +0xc40. These result words are separate from the mixed F2/F4 result slot. A typed Ibex boot adapter checks the source-pinned PC_BOOT expression and the actual artifact's constant boot_addr_i value before choosing the preload entry; begin then checks the first native accepted fetch against that prediction. All fixed images use ScenarioGenome.initial_images and advance_initial records actual bootstrap steps in the same ScenarioSession; no CSR instructions are added to the fuzzed F1 subset and no NOP-only support restriction is relaxed. Actual bootstrap advancement must reach the reserved dynamic entry, and actual routed setup transactions must match the firmware contract.

The source-pinned PULP register map is authoritative: GPIOEN=0x04, PADIN=0x08, INTEN=0x18, INTTYPE_LOW=0x1c, INTTYPE_HIGH=0x20, INTSTATUS=0x24. Packed interrupt type 2 selects both edges for the declared physical pin. INTSTATUS is read-to-clear, with a simultaneous native trigger taking priority and OR-ing into the previous status. Configuration and ack addresses are checked against this contract, not copied from an unrelated dual-GPIO example.

Fixed bootstrap configures GPIO and mtvec/mscratch/mie.MEIE/mstatus.MIE. The ISR saves/restores x1–x4 and x31 via mscratch, reads actual PADIN and INTSTATUS, writes dedicated result words/count, and executes mret. An observational checker joins the live GPIO/native CPU acceptance/serial provider to the complete fixed handler RVFI sequence, actual GPIO APB/CPU OBI reads, actual result RAM writes/OBI/RVFI and actual mret return PC. Missing evidence remains unknown; these observations do not award policy credit or grant prerequisites.

This implementation stage requires root's original/fresh native readiness and ISR evidence validation. Software construction and mocked evidence tests cannot establish actual interrupt acceptance or ISR execution.

The software preparation gate uses the actual RVFI/PULP artifacts, original exact CPU adapter, actual GPIO IRQ export/binding/provider and actual memory layout. It preloads every fixed image through the real runner/PersistentMemory path with native process startup forbidden, verifies dynamic slots remain absent, and rejects a second preload or online overwrite of the handler. Fixed images bypass neither the fuzz ISA validator nor its range checks: they use the existing preload channel intended for fixed firmware. Pure ISR checker tests exercise successful transaction/retirement association and reject mismatched native read data; they remain software tests, not native certificates.

## First native run and corrected return-target rule

Root's `shared-full-20261028/gpio-irq-v1` run executed actual fixed bootstrap and both pin transitions. Its live provider reported 6 IRQ deliveries, 2 CPU acceptances and 2 exact retirement-serial matches. The script correctly exited nonzero because both ISR checks stopped at `native-ISR-return-outside-dynamic-image`; this run did not establish a complete IRQ/ISR chain or fresh equivalence.

The rejected assumption was treating MRET RVFI `pc_wdata` as its architectural return target. In the pinned Ibex, `ibex_core.sv` assigns that RVFI field from `pc_set ? branch_target_ex : pc_if`; the controller instead selects PC_ERET for MRET, and `ibex_if_stage.sv` restores `csr_mepc_i`. The checker now retains raw MRET `pc_wdata` and uses the existing F6 rule: first subsequent valid retirement, consecutive RVFI order, zero interrupt serial, same execution and later native receipt/tick. GPIO additionally requires a matching actual instruction response, physical OBI beat, current admitted support bytes and matching live MemoryService byte versions. An unavailable subsequent instruction leaves the result pending/unknown; future slots are never filled to manufacture completion.

The script now streams the original event journal into `trace.json.gz` before requiring a successful chain. Per-case failure evidence also retains the actual MRET and immediately following retirements. These diagnostics address the v1 artifact's lack of raw retire/response data. The corrected rule still requires a new original/fresh native run.

## Second native run: backend and physical response boundaries

Root's `gpio-irq-v2` run again exited nonzero and retained its full compressed trace. The actual successors were valid dynamic PCs 69636/69652. The failing compound clause incorrectly equated CPU-service `instr_response.producer_event_id` with physical OBI response event ID. For the first successor, backend acceptance was step 3968/tick126 (response event3969), while the physical OBI response was step3991/tick127; both carried the same instruction transaction sequence60. The second case had the same two-stage distinction. Source bytes, versions, writer IDs and frozen snapshots matched.

The corrected checker preserves both boundaries. It checks actual backend PRE valid/ready/error/data, consumed response data and transaction sequence/epoch, then the next observed CPU tick's physical OBI response reconstructed from the native trace. The one-tick transition follows the already source-pinned OBI adapter's registered rvalid/data behavior. Byte-version/source checks remain; tuple/list transport representations are compared canonically. A fixture extracted from both v2 raw cases, combined with real MemoryService instruction admissions, exercises the bridge and rejects wrong sequence or a same-value write with a different version/writer.

A diagnostic offline projection of the complete v2 traces passed all corrected ISR clauses for both cases, including the subsequent PADIN/INTSTATUS APB/OBI/RVFI and result-RAM checks. This is an offline diagnostic result, not live issuer authority or successful original/fresh native validation of the corrected source.
