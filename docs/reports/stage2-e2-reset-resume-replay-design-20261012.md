# Independent reset-resume replay boundary design

This is a read-only design review for the next register-program package, not implementation or reset-default certification. Current schema16/17 production has no replayable pre-admission scheduler prefix after reset. `ScenarioSession.advance_initial` forbids committed cases, while `RegisterProgramRuntime._context` requires the actual CPU deferred instruction request at a declared, still-unmaterialized online slot. A reset followed immediately by saved-manifest preparation cannot substitute saved waiting/epoch values for that live request.

The agreed next API is `ScenarioSession.advance_after_reset(schedule: tuple) -> OnlineCaseReceipt`. New schema18/19 reset rows are exactly `{after_cases, policy, advances}`, where advances is an ordered bounded list of schedule arrays. Schema16/17 retain exact two-key reset rows and byte layout. No extra unversioned optional key, arbitrary callback, imported provider, saved CPU waiting tuple or saved state restoration is admissible. Schema18 is complete and schema19 retains the existing registration/submission terminal codec; a failing resume advance halts and makes export impossible rather than pretending it is a successful recorded command or forcing runtime uncertainty into that codec.

The Session API must compute the current reset row and boundary itself. Require an active Session, a successful actual recorded reset, `runner.command_epoch == len(_reset_operations)`, a nonterminal clean prefix, and no active register submission or registration already admitting the next case. Schedule must be exact tuple of bounded, known actual Session component names, with strict scalar types and per-command/total capacity checked before the first step. The actual ordinary/verifier/runtime/source guards must execute before stepping. A successful call records exactly the executed order on the latest reset, returns actual journal/tick prefix and uses the ordinary Runner scheduler. Repeated resume calls may be allowed while waiting is not yet ready, but no call may attach to an earlier reset, reorder around another case, or silently step after a failed/unrecorded reset. Once the next SourceAction is registered or a new case is committed, further pre-admission resume is forbidden until a new actual reset. `prepare()` itself is pure and may be used for inspection; it stores no pending prepared operation. A later submit using that preview as expected_manifest must recompute actual context and reject it if resume made it stale.

The schedule is an execution input, not a correctness oracle. Completion means the actual scheduler command completed; readiness is the actual CPU request observed by the existing runtime, not a saved flag. Caller attempts to label a reset index/epoch/event reference must be rejected by the API signature. If the new encoding normalizes earlier reset rows to three keys with empty advances, define that normalization once and compare the fresh encoded representation consistently; do not mutate old16/17 exports. New18/19 require at least one actual resume command, or an explicitly documented startup opt-in mode, to avoid accidental schema upgrades. Different resets at one case boundary must preserve their individual ordered advances.

Pure plan validation must reject unknown fields, bool/int equivalence, non-list advances, non-list schedules, unknown components, empty/oversized schedules, excessive total commands and invalid policies. Reset `after_cases` is strict integer in a committed prefix, monotonic, and individual rows retain order even for equal boundaries. For schema19 with an appended failed terminal case, reset cannot occur after that case; with an unappended registration failure, reset/resume can occur at the last previously committed boundary only before the terminal attempt. An advance with no corresponding actual reset or nested under a nonexistent/resetless row is rejected before a runtime is constructed. Existing schema16/17 cannot gain advances; deleting all advances and relabeling18 as16 must not preserve an incompatible saved trace/configuration.

Saved validation cannot prove the reset happened. Authentic file digest/source closure is necessary, and full fresh execution must independently call `runner.reset_all`, observe its real epoch/generation changes and replay the recorded schedules before the next compile. Cold and warm reset differ in memory generation/materialization: existing live slot/RAM admission checks must decide against current actual memory. A saved old admission, witness, certificate, report or RAM cell cannot refill or heal a missing live prerequisite. Historical observational certificates may remain, current ones must follow actual reset/incomplete rules. This scheduler codec alone grants no reset-default certificate or storage/version/prerequisite/functional scope.

Meaningful software regressions should cover:

- Exact16/17 default bytes and old terminal registration/submission semantics;18/19 complete and nullable terminal positives with current actual factories and no RTL.
- Actual successful reset then multiple resumes then fresh prepared request; two resets at one case boundary with distinct ordered schedules; wrong row/order/policy/epoch rejects or fresh mismatch.
- Invalid schema/unknown keys/type/capacity/schedule before factory/begin, and capacity before any actual command or registration. Writer invalid input creates no output directory.
- Resume before begin/reset, after finish/failed reset, after case submission/registration or during active submission refuses without events/ticks/cases advancing.
- Actual reset/resume failure halts, cannot encode a fake complete18/19, does not invent runtime terminal state, and cleanup failure adds a note rather than hiding the original error.
- A pure prepare preview followed by actual resume is legal, but stale expected_manifest submission must reject; changed saved resume schedules, deleted actual reset, consistently rehashed false epoch/waiting/certificate/state, or reordered same-boundary resets cannot grant admission; current trusted objects reconstruct readiness.
- Actual current memory generation/slots and native source/method drift before/after resume fail closed. An old action cannot revive after cold reset merely because saved values match.
- File replay forwards only closed current assembly flags, compares complete manifests/plan/trace/ordinary/verifier/gate state, and retains source pin/default-off identity compatibility. Cached builds are validated against current inputs, not permission restoration.

Before native acceptance, run the actual warm/cold reset→native bootstrap→recorded resume→new original request sequence under independent resource receipts. It must demonstrate physical reset receipts, real resumed waiting requests and exact full fresh file replay. Real reset-default field evidence is a separate subsequent rule. Software stubs/interpreters, this document and earlier mask-gate evidence cannot complete that acceptance or the full Stage2 plan.
