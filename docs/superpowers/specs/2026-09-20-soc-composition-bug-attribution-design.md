# 面向组件 RTL 缺陷发现的 SoC 自动组合：项目目标与阶段计划

日期：2026-09-20
状态：讨论稿 v0.3；CPU—MMIO 总线互联方向及六类接口覆盖已确认，其余方案仍待讨论，尚未进入实现。
适用项目：myfuzz

实施范围：在当前 myfuzz 的配置、契约、组合计划、RTL 渲染和运行矩阵上增量改造。具体入口、既有能力与扩展限制见 [现有项目改造指南](2026-09-21-soc-auto-composition-guide.md)，不从零搭建另一套框架。

## 1. 我们要解决什么问题

用户提供此前未接入项目的 CPU RTL + CPU profile，以及一个或多个未知外设的 RTL + 各自 profile。工具核实描述与实际源码、按接口能力自动生成接线正确、能启动和处理中断的 SoC，随后在真实组件交互中进行 fuzz，发现组件内部 RTL 设计缺陷。CPU 和外设均不要求先进入固定型号目录；现有组件作为改造基线和回归样例。

核心难点不是生成能编译的顶层，而是回答：观察到的异常来自原始组件，还是来自自动生成的连接、适配器、测试程序或检查器？

本项目的目标表述为：

> 在明确的接口与运行假设下，生成具有结构和行为验证证据的 SoC；对每个异常保留可重放证据、排查组合环境，并仅将满足归因条件的问题报告为组件内部 RTL 缺陷。

不能承诺“自动组合后的任何失败必然是组件 bug”。即使接线正确，也可能存在配置错误、检查器错误或规范歧义。应当承诺的是：证据不足时不作组件归因，并逐步降低和测量组合环境造成的误报。

## 2. 项目目标与边界

| 目标 | 可交付结果 | 不足以证明目标的证据 |
| --- | --- | --- |
| 组件身份可信 | 固定上游版本、参数、源码清单及内容哈希 | 仅有组件名称或仓库地址 |
| 自动接线正确 | 端点契约、连接计划、实际 elaboration 结果一致 | 仅有顶层 RTL 或编译通过 |
| 协议适配正确 | 适配模块在声明支持的参数和事务范围内通过独立验证 | 两端位宽相同或 smoke 成功 |
| 中断语义正确 | 从外设事件到 CPU 处理、清除和返回的完整证据 | 只看到 irq 拉高 |
| 激励合法且有效 | 接口假设检查通过，并到达目标行为 | 只向端口写入随机比特 |
| 缺陷能够归因 | 规范违例、合法输入、边界轨迹和隔离复现组成证据包 | 全系统超时、断言失败或覆盖率增加 |
| 结果可重现 | 从干净环境恢复依赖、构建并重放相同失败 | 依赖开发者未记录的本地产物 |

第一阶段建议限定单核、单时钟域、固定复位策略、MMIO 外设和非嵌套中断。多时钟域、DMA、一致性、多核中断路由、复杂安全域和动态重配置作为后续扩展，不默认纳入首期正确性声明。

原始组件可以存在 bug，不能以“证明所有组件正确”作为接入条件。接入条件关注接口描述、运行假设和可构建性；组合层验证使用协议模型和边界检查，避免把待测组件行为当成唯一参考答案。

## 3. 现有基础及需要补齐的证据

本稿依据当前仓库源码及历史报告进行设计，不代表本轮重新完成运行验证。

已有基础：

- `src/myfuzz/composition/soc_contracts.py`：SoC 契约及中断路由字段校验。
- `src/myfuzz/composition/soc_plan.py`：组件、连接和中断路由计划。
- `src/myfuzz/composition/soc_renderer.py`：顶层、组件包装和运行环境生成。
- `src/myfuzz/protocols/rtl/soc_irq_router.sv`：边沿/电平捕获、pending、claim 和完成状态。
- `configs/soc/sources.lock.json`：组件源码锁定信息。
- `docs/reports/soc-acceptance-20260915.md`：历史运行矩阵、覆盖及 RFuzz 验收证据和未完成项。

需要重点核实和补齐：

1. 当前通用生成路径将中断路由器输出接入 CPU 中断总线，并暴露 `irq_claim_i`、`irq_complete_i` 给环境；这不能直接等价为 CPU 通过 MMIO 完成领取和结束中断。
2. 当前生成器中的部分启动代码以 `mret` 作为中断处理程序。完整验收还需要证明使能、识别来源、外设清除、控制器完成及返回后的持续执行。
3. 中断契约里的逻辑编号、控制器源 ID、CPU 物理入口及软件看到的原因码必须分别核对，不能假定是同一编号。
4. 现有路由器属于组合环境的一部分，必须独立验证。不能仅因已经存在就将其视为正确性依据，也不能未经验证称为标准 PLIC。
5. 历史报告记录过包装器响应数据未正确连接的问题，这说明组合环境缺陷是实际风险，应建立专门的归因流程。

## 4. 技术路线选择

| 路线 | 优势 | 主要问题 | 建议 |
| --- | --- | --- | --- |
| 从任意 RTL 全自动推断并组合 | 可接入范围大、人工准备少 | 端口难以表达完整时序和寄存器语义；推断错误直接污染归因 | 作为长期探索，推断结果先作为待核实建议 |
| 组件契约 + 有限连接模板 + 独立验证 | 自动化程度和可验证性平衡，便于复现与扩展 | 每种组件首次接入需要核实契约 | 首期采用 |
| 固定手工 SoC 上做 fuzz | 容易建立可信基线 | 拓扑变化小，难以覆盖组合空间 | 作为对照环境，与推荐路线配合 |

推荐通过用户提供的 profile 描述组件语义，由系统核实物理绑定与支持能力并完成组合。资料可复用，但不要求先由开发者手写组件专用接入代码。未知组件使用已支持接口时应自动接入；新协议或语义缺口另行扩展和验证。

## 5. 自动接线怎么做

### 5.0 已确认的 CPU—MMIO 访问结构

用户已确认：CPU 通过总线互联访问各个 MMIO 外设。互联负责地址译码、请求路由和响应返回；多个主设备或主接口竞争同一访问资源时，按拓扑加入仲裁。

```text
CPU 访存主接口
      │
      ▼
总线互联：地址译码、请求路由、响应返回
          存在多个主接口竞争时加入仲裁
      ├── 必要的协议/位宽适配 ── GPIO MMIO 从接口
      ├── 必要的协议/位宽适配 ── UART MMIO 从接口
      └── 必要的协议/位宽适配 ── SPI  MMIO 从接口
```

图中外设仅用于说明拓扑，首期具体组件尚未选定。地址译码决定请求送到哪个外设，仲裁决定竞争资源由哪个主接口使用；两者不能相互替代。单核 CPU 也可能暴露多个主接口，应依据实际接口和访问路径判断是否需要仲裁。

自动组合按以下步骤工作：

1. 提取并核实 CPU 主接口与外设从接口的协议、位宽和时序契约。
2. 根据外设窗口大小与对齐约束分配地址，生成统一地址表。
3. 根据可达关系生成请求译码和响应路径；存在竞争时选择已验证的仲裁模板。
4. 接口不兼容时，只选择适用范围内已验证的协议桥或位宽适配器。
5. 独立检查实际连接，并在 CPU 侧、互联边界和外设侧关联请求、握手及响应轨迹。

首个建议验收里程碑是 CPU 能经互联分别访问至少两个外设：地址命中唯一正确目标，数据、字节使能和错误响应符合契约，背压下事务不丢失、不重复，未映射地址按约定处理。对有副作用的寄存器按其语义判断结果，不能统一使用“写入值等于读回值”作为判据。

中断相关的寄存器配置、状态读取和清除也经过这条 MMIO 路径；外设发出中断通知的路径另外设计。本次确认不代表选择了中断直连或中断控制器，第 6 节仍列出候选规则。

### 5.1 组件契约

首期已确认覆盖以下六类连接；每个组件只需覆盖实际具有的接口，但所有端口必须逐一登记。

| 类别 | 连接与验收内容 |
| --- | --- |
| 时钟与复位 | 来源、频率、时钟域、极性、同步/异步方式和释放条件；首期单域 |
| 启动与存储器 | 启动地址、取指/数据接口、ROM/RAM 映射、初始化内容与访问权限 |
| MMIO 总线 | 译码、请求/响应、字节使能、背压、错误及必要的仲裁和桥接 |
| 外设外部接口 | UART/SPI 对端、GPIO 输入/输出及输出使能，外部事件时序和合法性 |
| 中断 | 通知路径、使能、来源识别、清除及处理后返回；通知拓扑另行确定 |
| 配置与故障观测 | 启动/测试/调试模式、设备标识、错误/告警、完成状态及执行轨迹 |

每个端口或独立语义位段必须记录一种处理方式：连接其他组件、连接外部模型、按契约连接常量，或明确允许不连接。记录包含端点、处理方式、信号来源/去向、契约依据及验证状态。双向端口需描述驱动方向、输出使能和争用规则；不能作为普通单向数据线处理。

必要输入不能悬空，输出是否允许不连接由契约和观测需求决定。错误/告警等用于归因的输出必须被观测。未知端口、无依据的常量连接及遗漏位段应拒绝准入，而不是自动补零。合法交互与故意违规的健壮性测试分别记录，违规输入下的响应只有违反明确的错误处理约定才可作为缺陷证据。

每个组件应描述以下信息，并记录信息来自规范、源码还是已有验证结果：

- 身份：上游版本、顶层、参数、源码闭包、编译宏和工具版本。
- 物理接口：端口、方向、位宽、结构体成员路径、时钟和复位域。
- 总线语义：协议及版本、主从角色、地址与数据宽度、字节序、字节使能、对齐、突发、ID、未完成事务和错误响应。
- 地址语义：寄存器窗口大小、对齐要求、访问权限及有副作用的读写。
- 运行前提：时钟频率约束、复位顺序、启动地址、外部输入约束。
- 中断语义：见第 6 节。

端口和位宽可由编译器提取；协议语义、清除行为和运行前提需要额外证据。无法可靠确定的字段标为未核实，相应组合不得进入组件归因实验。

### 5.2 从计划到实际 RTL 的双重校验

```text
已核实组件契约 + 拓扑约束
              ↓
确定性连接计划：端点、适配器、地址、中断、时钟与复位
              ↓
顶层 RTL + 软件配置 + 实验清单
              ↓
独立提取实际连接并检查契约 → 组合层行为验证
              ↓
通过准入的 SoC → fuzz → 异常证据 → 隔离复现与归因
```

生成器负责构造；检查器从 elaboration 后的结构重新提取实际端点与连接，核对原始契约和允许的拓扑。检查器不复用生成器的接线决策函数，也不只检查生成器输出的计划文件。

共享契约仍可能产生共同错误，因此契约还需规范审阅、已知参考设计和故意接错的负例校验。

### 5.3 必须检查的接线约束

1. 必需输入都有明确驱动，没有意外多驱动、悬空和隐式截断；允许的常量连接有依据。
2. 地址窗口满足范围、对齐和非重叠约束；地址缩窄有可验证的范围依据。
3. 请求到达正确目标，响应返回正确发起者；复位和背压下不丢失、不重复事务。
4. 位宽、字节通道、ID 和突发语义匹配；不支持的事务显式拒绝，不能静默修改。
5. 时钟和复位域兼容；首期拒绝未验证的跨域路径。
6. 每个插入的桥、仲裁器、路由器和包装器有明确版本与适用范围，超出范围重新验证。

有限状态和小规模组合逻辑优先考虑形式验证；其他部分采用独立协议模型、定向测试和随机测试。形式验证结论必须附带假设、参数与证明边界，有界检查未找到反例不等于无条件证明。

## 6. 中断怎样自动组合

### 6.1 中断契约不能只包含 irq 端口

| 对象 | 必需描述 |
| --- | --- |
| 外设中断源 | 端口/位、事件含义、极性、边沿或电平、同步时钟域、最小脉宽或保持条件 |
| 外设寄存器 | 使能、屏蔽、状态、清除方法及副作用；行为不适用时明确声明 |
| 控制器 | 源容量、ID 规则、pending、屏蔽、优先级、领取/完成及并发事件语义 |
| CPU | 外部/定时器/软件中断入口、权限、使能条件、向量与原因识别方式 |
| 运行环境 | 初始化、处理程序、可观测事件、等待条件与时限依据 |

同类字段也可能语义不同。例如，电平源保持高电平直到软件清除，与短脉冲事件不可互换；多个边沿发生时是合并为一个 pending 还是累计计数，应由契约规定。检查器不能一律要求每个边沿都产生一次 CPU 陷入。

### 6.2 首期自动生成规则

- 为每个源分配稳定标识，输出“原始端口 → CPU 入口 → 软件处理函数”的映射；若选择控制器拓扑，再加入控制器源 ID。
- 选择一种明确的拓扑模板：CPU 直接中断入口，或带软件可访问寄存器的控制器。两种模板分别验证，不能混用领取/完成语义。
- 同时生成地址表、中断表、初始化代码与处理程序，保证软件使用的映射与实际硬件连接一致。
- 默认只接受同域、可匹配的中断语义；极性转换或脉冲保持必须使用已验证且不会掩盖待测行为的适配器。
- 第一阶段不支持共享中断线；后续若加入，必须具有来源识别机制和独立验证。
- 定时器/软件/外部中断按 CPU 的真实入口契约处理，不能全部合到一个任意 irq 位上。

### 6.3 端到端验收

以“GPIO 事件触发 CPU 处理”为例，记录以下检查点：

1. 软件正确初始化向量、CPU 使能位、GPIO 和控制器。
2. 合法外部输入产生指定 GPIO 事件，GPIO 状态与原始中断输出符合规范。
3. 控制器记录正确来源，在使能和优先级条件下通知 CPU。
4. CPU 进入预期处理入口，软件取得正确来源或直接入口身份。
5. 软件按该外设规范清除事件；需要领取/完成的控制器执行相应流程。
6. 返回后程序继续执行；是否再次触发取决于事件状态和契约。

必须测试屏蔽/解除屏蔽、同时到达、处理期间新事件、持续电平、复位及重复触发。无响应首先记为异常；只有契约或环境假设支持有限响应时间时，超时才构成相应性质的违例。

## 7. 怎样把异常归因到组件内部

### 7.1 分开记录待测对象和测试环境

每次实验明确列出待测组件及组合环境。CPU、外设、上游控制器都可成为待测对象；自动生成的桥和包装器默认属于环境，不能混入“上游组件内部 bug”统计。

发现异常后，记录最早可观察到的契约违例作为定位线索，但它不自动等于根因；应继续检查违例前的输入、状态和环境假设。

### 7.2 归因流程

1. **重现异常**：固定源码、参数、工具、固件、初始状态、种子和外部事件时序。
2. **核实判据**：说明违反哪条规范或性质；核查检查器、编译/仿真工具及参考模型的适用性。
3. **检查输入合法性**：检查问题发生前的总线、复位、中断和外部输入是否满足目标组件假设。发现非法输入时先追踪其来源。
4. **检查组合环境**：对照实际连接、适配模块和软件轨迹，定位哪一段开始异常。
5. **缩减复现**：减少无关组件、软件操作和事件，保留有效前置状态与失败条件。
6. **组件隔离**：用独立验证环境驱动原始组件，重放合法边界事务，检查是否仍违反组件规范。
7. **补充交互证据**：若隔离改变了反馈或时序而无法复现，保留最小多组件场景，通过替换环境、边界断言或形式反例继续归因，不能据此直接判为组合错误。

重放含握手的总线时需保留因果关系；替换环境后不能盲目逐周期复制输入。只要重放环境违反组件接口假设，隔离结果就不能用于确认缺陷。

### 7.3 报告分级

| 分类 | 所需证据 |
| --- | --- |
| 已确认组件内部 RTL 缺陷 | 明确规范违例、合法输入、原始源码身份、可重复反例，以及隔离复现或等效的充分归因证据 |
| 候选组件缺陷 | 有具体组件线索，但隔离、假设或规范证据尚不充分 |
| 组合/适配缺陷 | 连接、映射或环境模块违反约定，能定位并复现 |
| 软件/激励/检查器缺陷 | 错误使能、清除、非法输入或判据错误等有复现证据 |
| 未定位/规范歧义 | 证据不足或规范允许多种解释，需要继续分析 |

每个报告携带最小复现、源码和构建身份、期望行为依据、实际轨迹及分类理由。注入的人工缺陷只用于校准工具，单独统计，不能作为新发现的真实组件 bug。

## 8. 项目阶段计划

以下按验收门槛推进，不先承诺工期。组件选择和首个契约核实完成后，再估算工作量。

| 阶段 | 主要工作 | 交付物与退出条件 |
| --- | --- | --- |
| P0 目标与基线 | 选定一款 CPU、至少两个 MMIO 外设，确定总线协议、主接口数量和可达关系；核实中断语义并另行确定通知拓扑 | 范围表、总线参考 SoC、待测对象/环境清单、风险清单；接口和中断语义可查证 |
| P1 组件契约 | 绑定源码并覆盖六类接口，逐端口登记处理方式；校验参数变化 | 契约格式与首批组件描述；端口无遗漏，关键字段有来源，缺失信息可明确拒绝 |
| P2 连接计划与结构检查 | 自动分配地址，生成译码和响应路由，按竞争关系选择仲裁模板，独立提取实际连接；中断映射随所选拓扑生成 | 同一输入可重现；合法组合通过；接错、漏接、多驱动、地址重叠等预设负例全部被拒绝 |
| P3 启动、总线与外部交互验证 | 验证时钟/复位、ROM/RAM、路由、桥和必要的仲裁器；CPU 启动并访问至少两个外设；核实外部模型及观测路径 | 通过第 5.0 节 MMIO 验收及第 5.1 节对应接口检查；按参数与假设记录验证结果 |
| P4 中断完整闭环 | 生成初始化与处理程序，建立边界观测点和中断参考行为 | 正常路径及并发、屏蔽、复位、清除等边界情形符合契约；CPU 实际执行处理和返回 |
| P5 缺陷发现与归因 | 集成 fuzz、合法性检查、反例缩减、组件隔离和证据报告 | 注入的组件错误可复现和定位；注入的组合错误不被误报为已确认组件缺陷 |
| P6 组合空间扩展 | 增加第二款 CPU、更多外设、位宽/协议适配及拓扑变体 | 每类新增组合重新通过准入；报告覆盖、拒绝原因、未知问题和各类缺陷数量 |

依赖顺序：P0 → P1 → P2/P3 → P4 → P5 → P6。P2 与 P3 可分开开发，但都通过后才进入有组件归因要求的系统实验。

首期候选从已有 Ibex/CVA6 与 GPIO/UART/SPI 接入中选择。建议优先挑选语义最清晰、参考环境最完整的一组，而不是直接扩大到整个历史矩阵。

## 9. 验收与评价方法

- **结构准入率**：报告在预先列出的支持组合中，通过独立结构和环境行为检查的比例；同时列出拒绝项及原因。
- **组合负例检出率**：对预设的错线、错地址、错编号、错极性、截断和握手破坏分别报告。首期要求预设必测负例全部检出，不外推为任意组合错误都能检出。
- **中断语义覆盖**：逐项记录第 6.3 节场景是否执行、判据及结果。
- **归因质量**：在具有已知来源的缺陷注入集上统计分类正确率、组件误报数量和未定位数量；首期要求已知组合错误不进入已确认组件缺陷列表。
- **复现能力**：每个已确认报告从干净环境构建并至少重复重放三次，保留结果；无法稳定复现的单独标记。
- **真实发现能力**：分别报告上游原始 RTL 新发现、已知缺陷复现和人工注入缺陷；覆盖率作为探索进展指标，不替代功能正确性判据。

通过有限测试表示在当前支持范围和验收集合内取得证据，不表示对所有状态和所有组件作出无条件保证。

## 10. 主要风险与应对

| 风险 | 应对 |
| --- | --- |
| 契约本身描述错了 | 保留规范来源，审阅关键语义，使用参考设计和不同实现交叉检查 |
| 生成器与检查器共享同一错误 | 分离连接决策与实际结构提取，设置人工负例，不仅比较两份生成清单 |
| 适配器掩盖真实组件缺陷 | 记录原始边界信号，只允许规范要求的转换，禁止无依据修正错误输出 |
| 激励约束过强而遗漏 bug | 区分必要协议假设与测试便利限制，逐步扩大合法输入空间并记录约束 |
| 软件配置错误被误认为硬件问题 | 固定并验证固件，保留寄存器与处理轨迹，使用独立事务环境辅助定位 |
| 插桩改变了行为 | 支持在未插桩原始 RTL 上重放，记录插桩版本和观察差异 |
| 多组件反馈导致隔离不复现 | 保留最小交互场景，使用替换实验或形式反例，不强行归因 |
| 删除本地产物后无法重现 | 将依赖恢复、构建、生成和重放步骤纳入正式交付，不能只保存测试通过摘要 |

## 11. 已确认决定与后续讨论

**已确认：CPU 与各个 MMIO 外设通过总线互联连接，按主接口竞争情况加入仲裁。** 先建立可验证的 MMIO 访问闭环，再完善中断通知与处理闭环。

**已确认：首期覆盖时钟/复位、启动/存储器、MMIO、外部接口、中断、配置/故障观测六类连接，并要求逐端口说明处理依据。**

后续讨论项：

0. **首期总线与组件**：选择 CPU、至少两个 MMIO 外设及其协议，核实主接口数量；据此确定是否需要桥接和仲裁。
1. **首期中断拓扑**：选择 CPU 直接入口，还是软件可访问的中断控制器？建议以希望覆盖的真实系统架构决定，首期只做一种。
2. **首次接入的人工成本**：建议允许人工核实组件契约，再自动完成后续组合；全自动语义推断作为后续辅助能力。
3. **待测对象范围**：首期建议聚焦外设 RTL，CPU 和互联仍保留故障观测；扩展时再单独设计 CPU、控制器的归因判据。
4. **首期交付重点**：建议先完成可验证的 CPU—互联—多外设访问路径，再完成可缩减、可归因的中断路径，最后扩展组合数量。

下一次讨论可先确定首期总线与组件；中断通知拓扑在接口语义核实后确定。
