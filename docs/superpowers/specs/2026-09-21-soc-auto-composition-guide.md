# 基于现有 myfuzz 的 SoC 自动组合增量改造指南

日期：2026-09-21。状态：设计与实施指导稿；不是功能完成报告。

本文件细化 [项目目标](2026-09-20-soc-composition-bug-attribution-design.md)，用于指导 [阶段计划](../plans/2026-09-20-soc-composition-assurance-plan.md) 的执行。目标文档定义为什么做，本文定义如何组合和判定是否可用，计划定义实施顺序。

**实施起点是当前仓库已有的组合链路和八格运行矩阵。** 优先复现现有配置，在原有 schema、计划、适配器、渲染器和运行入口上补充能力。后文通用规则是对现有链路的审核/扩展要求，不要求从零实现另一套系统。

**最终输入已修正为未知 CPU RTL + CPU profile，以及未知外设 RTL + 各自 profile。** 现有固定型号路径是待泛化的实现，不是用户输入限制。目标按协议/接口能力选择模板，不能为每个陌生组件增加名称分支。本文关于组件目录和事实登记的描述是现状；迁移时应转成用户 profile 的校验与绑定。

## 0. 从当前项目开始的操作路线

### 0.1 先理解实际已有的配置到 RTL 链路

`src/myfuzz/integration/soc_matrix_smoke.py::cell_documents(config_path, mode)` 已执行：

```text
matrix 中已登记的 config_path + mode
 → load_cell_config / peripheral_records
 → build_spec + build_execution + build_contracts
 → build_soc_plan(spec, processor_execution, target_contracts)
 → compile_soc_stimulus(plan, policy)
 → documents：spec / plan / stimulus / program / fuzz_ops
```

`src/myfuzz/composition/soc_renderer.py::render_soc(plan, stimulus)` 已返回生成文件内容；`src/myfuzz/integration/soc_builder.py` 已调用该渲染器进行构建。实施时复用这些入口；配置加载的事实表、源码闭包和运行程序生成也必须一起核实，不能绕过它们直接拼顶层。

### 0.2 按修改规模选择路径

| 要做的事 | 当前起点 | 需要修改/检查 | 完成条件 |
| --- | --- | --- | --- |
| 验证一个现有组合 | `configs/soc/matrix.json` 中的现有 cell | 恢复锁定依赖并运行对应测试 | 配置、计划、渲染、运行的身份一致 |
| 改现有外设地址/参数 | 对应 `configs/soc/*.json` | `build_spec`、能力契约、地址映射、程序生成和渲染参数一致 | 新参数实际进入 RTL/软件，旧矩阵不退化 |
| 用已接入组件形成新组合 | `peripheral_records`、`build_spec`、`build_contracts` 与 `cell_documents` | 配置发现、事实表、包装选择、程序/观测支持及矩阵限制 | 新组合能走同一正式链路；不能仅复制 JSON |
| 接入新外设 | `configs/soc/closures/`、源码锁、`target_adapters.py`、现有外设包装 | 新的真实源码事实、必要包装及外部模型/程序；协议已支持时复用桥 | 所有接口和语义有依据，独立验证通过 |
| 输入未知 CPU/外设，接口已支持 | 用户源码 + profile、现有接口描述与适配解析 | 核对端口、语义及构建闭包，通用生成包装/软件 | 不改生成器组件分支即可组合 |
| 输入必要接口能力未支持的组件 | profile 声明及能力解析 | 输出协议/启动/外部模型等精确缺口；能力扩展独立验证 | 未实现能力不能被静默替代 |
| 提高组合可信度 | 现有契约、plan/render 哈希和运行检查 | 补全端口台账、实际结构审计和归因报告 | 新检查与既有链路绑定，不另建独立生成器 |

### 0.3 已确认的扩展障碍

- `scripts/run_soc_campaigns.py::load_matrix` 当前限定两款 CPU、三类外设家族和恰好八格矩阵。新增 cell 之前必须区分“保留原八格验收要求”与“允许扩展组合”的入口/校验职责，并加测试；不能删除原验收约束来假装支持新组合。
- `cell_documents` 通过 `_matrix_cell_for` 查找配置归属，未登记文件不能被假设为任意可用配置。
- `soc_matrix_smoke.py` 中的 `peripheral_records`、`build_contracts`、`PERIPHERAL_PROGRAMS` 等承担组件事实和运行语义。每次新增组件都要查这些入口是否仍有硬编码限制。
- `tests/integration/test_soc_renderer_cells.py` 也维护配置构造和事实辅助逻辑。修改生产路径时对照测试，防止只更新测试副本而未影响实际运行。测试期望不能全部从被测生成器推导。
- 当前地址主要来自配置；自动地址分配是增量能力。引入时保留显式地址的兼容性，只为请求自动分配的项求解，并拒绝冲突。
- 固定 CPU/外设事实、专用包装和程序表需要迁移为统一 profile 与协议/ISA 模板。仅允许新名字进入矩阵而内部仍依赖专用分支，不算完成未知组件自动接入。

### 0.4 当前可用的验证入口

在仓库根目录、锁定依赖恢复后执行；这些是后续实施命令，本轮文档工作没有执行测试：

```bash
PYTHONPATH=src python3 scripts/verify_soc_sources.py
PYTHONPATH=src:. python3 -m unittest tests.composition.test_soc_contracts tests.composition.test_soc_plan_fabric tests.composition.test_soc_fabric_plan
PYTHONPATH=src:. python3 -m unittest tests.protocols.test_soc_fabric_rtl tests.protocols.test_soc_target_adapters_rtl
MYFUZZ_SOC_REAL=1 PYTHONPATH=src:. python3 -m unittest tests.integration.test_soc_renderer_cells tests.integration.test_soc_matrix_runtime
```

最后两类检查需要对应工具/源码；缺失依赖要列为环境问题。真实运行开关下应核实必需用例实际执行，不能把跳过视作完成。RFuzz 长时间实验继续使用既有 campaign 入口，但在结构和运行准入通过后才启动。

首个实际工作包：复现一个已有 cell → 列出六类接口的现有绑定和缺口 → 补检查并故意改错验证检出 → 再用已接入组件产生一个拓扑或参数变化。首个工作包不需要重建整个项目。

## 1. 已确定的方向与仍待选择的内容

已确定：CPU 经总线互联访问多个 MMIO 外设；互联负责地址译码、请求路由、响应返回，多个主接口竞争时加入仲裁。检查范围覆盖时钟/复位、启动/存储器、MMIO、外部接口、中断、配置/故障观测六类接口。

中断通知拓扑、首期具体组件及其协议尚未最终选择。单核单时钟、固定复位、非嵌套中断作为首期建议边界。实施者先建立支持能力表，再选择符合条件的组合；不能把建议当作已验证能力。

“自动组合”不是把名称相似的端口接起来，而是求解一组有语义约束的连接关系，生成 RTL 和软件后再独立检查其实现。输出失败也属于正常结果，必须给出具体不满足的约束。

## 2. 当前代码基础及边界

以下为 2026-09-21 的代码阅读结果，运行结果需要在对应构建环境中验证。

| 现有文件 | 可以作为实现基础的能力 | 实施者必须注意 |
| --- | --- | --- |
| `src/myfuzz/composition/soc_contracts.py` | `soc_spec.v1`、`soc_plan.v1`、`soc_stimulus.v1` 校验 | 字段校验不等于物理连接已验证 |
| `src/myfuzz/composition/soc_plan.py` | 将 spec、目标契约和处理器执行信息绑定成计划 | 不能只提供配置文件就认为目标语义已齐全 |
| `src/myfuzz/composition/soc_fabric.py` | beat 互联、主接口和目标窗口计划 | 当前检查 32/64 位数据宽度；不等于支持任意宽度和并发形态 |
| `src/myfuzz/composition/target_adapters.py` | 外设侧 APB、TL-UL、Wishbone 适配及能力校验 | 适配方向为 beat → 外设；不能反用 CPU 侧适配器 |
| `src/myfuzz/protocols/rtl/soc_arbiter.sv` | 多 beat 主接口仲裁并保持事务归属 | 全局仅一个未完成事务；轮转公平性按 grant 次数表述，不保证任意对端下的周期上界 |
| `src/myfuzz/composition/soc_renderer.py` | 顶层、包装和构建产物生成 | 现有中断环境控制和最小 ISR 不能代替完整软件处理证明 |
| `configs/soc/ibex-pulp.json` 等 | `soc_render_config.v1` 渲染配置 | 与 `soc_spec.v1` 不同，不得直接当作 `build_soc_plan` 输入 |

新增的端口台账、结构审计和归因报告在本文中是拟定产物，不声明当前解析器已接受这些字段。扩展前决定使用版本化旁路文件还是升级 schema，并添加兼容性测试；禁止偷偷改变已有字段含义。

## 3. 输入必须齐全

| 输入 | 必须包含 | 信息不足时 |
| --- | --- | --- |
| 源码锁定 | 仓库版本、递归依赖、文件清单、哈希、许可证记录 | 拒绝进入构建准入 |
| 构建上下文 | 顶层、参数、宏、语言版本、包含路径、包顺序、工具身份 | 拒绝绑定旧的接口提取结果 |
| 物理接口事实 | 端口方向/宽度/位段、结构体成员、时钟与复位端口 | 要求补充可追溯事实 |
| 语义契约 | 协议版本、角色、事务限制、复位和错误行为 | 拒绝猜测兼容性 |
| 寄存器描述 | 偏移、宽度、访问权限、读写副作用、使能/清除语义 | 不生成未知寄存器的测试 oracle |
| 组合请求 | 组件实例、主从可达关系、保留地址、支持模式、资源上限 | 报告缺失约束 |
| 外部环境 | 时钟、复位、对端模型、固件、初始状态和输入合法性 | 只能做有限结构检查，不能组件归因 |

每条语义事实记录来源：固定版本规范章节、源码位置或可重复验证结果。名称匹配和模型推断只能产生候选，不能自行提升为已确认事实。规范与源码存在差异时，记录差异并审阅，不能把当前 RTL 行为直接定义成正确答案。

## 4. 中间数据与产物约定

在现有输出目录和 manifest 上补齐以下逻辑内容。`soc_top.sv`、`soc_sources.f` 等复用现有产物；其余名称为建议，已有报告具备相同内容时扩展/引用该报告，不再创建平行事实源：

| 产物 | 内容及消费者 |
| --- | --- |
| `input_manifest.json` | 所有输入身份、工具、参数及构建种子；用于复现 |
| `port_dispositions.json` | 每个端口/位段的去向与依据；由生成器和独立审计器分别读取 |
| `soc_plan.json` | 实例、适配器、网络、地址、时钟/复位及中断映射；供 RTL/软件生成 |
| `address_map.json` | 区域、权限、地址变换和主接口可达关系；供软件与检查器 |
| `soc_top.sv`、`soc_sources.f` | 实际构建输入；供 elaboration 和仿真 |
| `software/` | 地址常量、链接脚本、启动代码、ISR、镜像及工具身份 |
| `structure_audit.json` | 实际连接与独立检查结果，含无法验证项 |
| `environment_validation.json` | 互联、适配、对端模型及软件验收证据 |
| `run_manifest.json` | 模式、初始状态、输入事件、随机种子、超时/资源预算和监视器版本 |
| `failures/` | 反例轨迹、缩减过程、隔离复现和归因结论 |

建议所有 JSON 报告带 `schema_version`、输入身份、产物哈希和结果。结果使用明确的通过、失败、未知、不适用状态；不适用必须有理由，未知不能算通过。哈希用于绑定证据，不证明内容本身正确。

端口台账最少包含：实例 ID、端口、位段、方向、物理宽度、语义角色、处理方式、连接端点或常量、时钟域、复位域、来源依据及检查状态。相同组件的两个实例必须有不同实例 ID；端口关联按实例和物理端点进行，不只按组件名称。

## 5. 组合算法与失败处理

按以下顺序执行，各步失败就输出诊断并停止该候选的准入：

1. 固定组件实例、参数、宏和源码闭包，提取实际接口。
2. 将物理端口绑定到语义端点，建立六类接口台账。
3. 根据主从角色及访问权限构造有向可达图；区分 CPU 取指、数据和 fuzz 主接口。
4. 对每条访问路径选择合法适配链，校验整个链的能力交集。
5. 分配不重叠地址区间和地址转换规则，检查 CPU 地址可表达性。
6. 对共享目标/链路的竞争选择仲裁，确定事务归属和响应路径。
7. 分配时钟、复位、存储器、配置常量及外部对端。
8. 按已选中断拓扑绑定通知路径及软件映射。
9. 生成顶层、软件和实验清单，并检查产物间映射一致。
10. 从实际 elaboration 结构独立提取连接，执行结构审计。
11. 执行环境模块和启动/MMIO/外部交互/中断行为验收。
12. 只将通过所需门槛的候选放入相应 fuzz 实验，保留失败候选及原因。

若有多个合法拓扑，先过滤正确性约束，再按显式策略排序，例如已验证模板优先、减少转换数量，再用稳定 ID 打破平局。随机探索拓扑时保存组合种子和完整计划；运行时 fuzz 种子单独记录。

诊断需包含阶段、实例、端点、违反约束、期望/实际值及证据位置。例如“GPIO 的 32 位写接口不支持所请求字节使能”，不能只返回“组合失败”。无解时不自动降低契约要求。

## 6. 总线与适配器选择规则

现有结构应明确表达为：

```text
CPU 原生主接口 → CPU 侧适配 → beat 互联/必要仲裁/地址路由
                                           ├→ 存储器后端
                                           └→ 位宽/地址适配 → 外设侧协议桥 → MMIO 外设
```

物理顺序按经验证模板确定；不能任意交换位宽变换、地址变换和协议桥的位置。

| 决策 | 允许条件 | 拒绝或另立方案的条件 |
| --- | --- | --- |
| 直接连同协议端点 | 角色、版本、时序、宽度及可选字段语义兼容 | 仅端口名/宽度相同 |
| 协议转换 | 有明确方向和支持能力的已验证桥 | 反向使用适配器、丢弃必要字段 |
| 单主多目标 | 译码和响应路由清晰 | 将仲裁当成地址译码 |
| 多主共享路径 | 事务归属保持、背压和返回路径已定义 | 响应按当前仲裁选择而非已接受请求归属返回 |
| 64 位访问 32 位 MMIO | 访问覆盖范围、字节通道和副作用允许该转换 | 无条件拆为两次有副作用访问 |
| 部分写 | 目标或已验证转换明确支持 | 自动读改写 read-to-clear/W1C/FIFO 等寄存器 |
| 突发/原子/独占操作 | 整条路径保持所需语义 | 当作普通单次读写静默降级 |
| 多 ID/多未完成事务 | 原生端适配能合法背压/串行化或完整保持并发语义 | 因 beat 层单事务就直接丢掉 ID/乱序约束 |
| 完整性/权限字段 | 按固定协议契约生成、检查和传播 | 简单绑零或忽略错误 |

当前 beat 仲裁器的“全局一个未完成事务”是实现边界。串行化是否合法需要在 CPU 原生接口侧验证，不能仅看 beat 侧通过。串行化也会减少并发状态覆盖，应在实验局限中记录。

带多个通道的协议按其握手和关联规则处理；不能假定地址与数据同周期到达。复位期间的在途事务处理也需要端到端一致。

## 7. 地址、寄存器与存储器

采用半开区间 `[base, base + size)` 表示区域。分配时按要求对齐，检查加法溢出、CPU 地址宽度、保留区域和所有可达空间重叠。显式别名必须记录别名语义；首期建议拒绝隐式别名。

对每个窗口明确：全局字节地址、局部地址变换、目标地址单位、权限和允许主接口。只有证明窗口和单位转换无损后才能缩窄地址。不能用低位截断让不同全局地址意外命中同一寄存器。

寄存器规则包括只读、只写、读清零、写一清零、FIFO 出入、保留位和合法访问宽度。oracle 根据规则预测允许结果；若硬件会异步更新状态，应使用事件模型和允许变化区间，而非机械比较写回值。

CPU 取指、数据、ROM/RAM、栈和外设区分别配置。检查 CPU 实际复位入口语义、链接脚本和加载位置一致；不能把配置里名为 reset_vector 的值未经核实直接当成首条执行指令地址。只读区域写入、禁止执行区域取指和未映射地址应按契约处理。

内存初始值、按需分配规则和未初始化读取策略必须可重现。仿真默认清零不自动代表硬件行为；实验依赖清零时显式列为假设。

## 8. 时钟、复位、配置和观测

- 建立时钟/复位分发图，明确频率、极性、同步方式与释放条件；首期单域仍需核查外设内部对外信号的采样方式。
- 测试级全复位与 CPU 局部复位分开。若 CPU 重启而外设、互联或 pending 状态保留，不能假定系统回到干净状态。
- 在途请求遇到复位：明确哪些端被清除、何时允许重新请求、旧响应是否可能返回；复位范围不一致时拒绝对应测试模式。
- 配置/调试/测试模式和标识输入的常量必须来自组件约定，不能把“未使用”统一解释为零。
- 错误、告警和完成状态应被观测。双向引脚分别表示输入、输出及输出使能，并检查争用和高阻语义。
- 若模拟器采用二值处理，不能以此证明没有 X/Z、未初始化或电气争用问题；需要相应检查或明确限制。
- 首期 RTL 仿真不等于物理时序、亚稳态、模拟电气和实现后时序验证；将这些列为范围外，不能宣称已覆盖。

## 9. 外部对端与 fuzz 输入

UART、SPI、GPIO 的外部模型必须有角色、配置和时序契约。对端模型先独立用已知序列验证，再接入 SoC，避免发送器和检查器用同一错误逻辑互相印证。

把输入分成三种入口：CPU 执行程序、MMIO 主设备发起事务、外设引脚事件。`cpu_only`、`mmio_only`、`mixed` 等现有模式的具体使能和复位行为需按代码核实；不能把只有合成主设备的结果写成 CPU 执行结果。

混合模式下，fuzz 主设备是新增总线参与者，必须服从仲裁和访问权限。CPU 与 fuzz 同时修改同一寄存器可能形成合法竞争；oracle 应依据实际接受事务的顺序判断，而不是依据两端各自的发送时间猜测结果。

建议先 fuzz 合法事件序列和事务参数，再加入有明确预期的错误输入。拒绝非法候选、约束修正及随机样本丢弃都要计数并可重放；不能靠自动修正掩盖组件输出违例。

## 10. 中断通知与 MMIO 操作分别设计

MMIO 负责配置、状态查询和清除；通知路径负责把事件传到 CPU。两条路径共同形成闭环，但不能互相替代。

| 候选拓扑 | 必须核实 | 软件职责 |
| --- | --- | --- |
| 独立入口直连 | 真实可用入口、权限、极性/触发语义、原因识别和源保持条件 | 配置 CPU/外设，按入口识别来源，清除外设并返回 |
| 中断控制器 | 原始源语义、容量、源 ID、pending/优先级/屏蔽和寄存器协议 | 再加入控制器初始化及其规定的领取/完成 |

不能把 CPU 不同权限的中断输入当作任意可互换的外设插槽。入口不足时拒绝直连候选；不默认 OR 合并。短脉冲也不能未经保持/采样条件证明就接到要求持续电平的入口。

现有 `soc_irq_router` 是环境模块，其 claim/complete 输入和行为必须独立验证。首期究竟采用哪条路径，需由固定 CPU 和外设语义决定；本文不预选。

每条路线至少核查：事件产生、原始输出、CPU 入口、陷入原因、ISR 寄存器操作、返回及后续执行。清除后仍保持有效、处理期间新事件或多个边沿合并是否正常，由契约判定。若只有“irq 曾为 1”的证据，只能说明信号活动。

## 11. 完整示例：基于现有 Ibex/PULP 配置的候选

以下示例用仓库已有配置说明工作方法，不表示它已满足本文新增的全部准入要求，也不是用户已选定的首期配置。

从 `configs/soc/ibex-pulp.json` 读取：CPU 为 32 位 Ibex，声明 OBI；GPIO 与 SPI 声明 APB3；ROM 基址 `0x00010000`、大小 `0x8000`；RAM 基址 `0x80000000`、大小 `0x10000`；GPIO 与 SPI 分别位于 `0x40000000`、`0x40001000`，各占 `0x1000`。

实施顺序：

1. 按锁文件恢复固定源码，以配置中的参数 elaboration，确认实际取指和数据主接口及所有配置输入。
2. 明确允许的可达图：例如取指访问可执行存储区，数据访问 RAM 和允许的 MMIO；以 spec 权限为准，不能仅由地址推断。
3. 为原生主接口选择正确的 CPU 侧适配；若两条路径汇入共享 beat 资源，验证仲裁归属与返回。
4. 确认两个 APB 外设实际接受的访问宽度、地址单位和部分写能力。声明 APB3 不自动提供部分写能力；不支持则限制合法激励并定义错误处理。
5. 核对全局到局部地址变换。例如 GPIO `0x40000020` 若采用字节偏移映射，应到局部 `0x20`；只有实际寄存器表确认该偏移和访问合法后，才生成对应读写测试。
6. 核对 GPIO 输入/输出使能和 SPI 主从角色及模式，对应连接环境模型。
7. 先用启动程序完成 RAM 和两个外设的合法操作，再启用外部交互。
8. 现有配置中的中断边沿、清除方式和编号先与固定源码/规范逐项核实；不能直接因配置存在就认定正确。
9. 选择通知拓扑，生成匹配的软件，完成中断生命周期测试。
10. 注入“互换外设窗口”和“响应返回错误主接口”等环境缺陷，确认独立检查器拒绝或定位，再开展组件 fuzz。

示例中所有地址来自现有配置；新增寄存器语义必须取得来源，本文不编造寄存器偏移和 ISR 序列。

## 12. 验证门槛与声明范围

| 门槛 | 验证内容 | 允许的结论 |
| --- | --- | --- |
| G0 输入完整 | 源码、参数、语义来源及工具齐全 | 可尝试构建 |
| G1 结构核查 | 逐端口台账与实际 elaboration 一致，地址和连接约束通过 | 当前结构满足已检查约束 |
| G2 环境模块 | 互联、桥、包装和对端模型在指定参数/假设下验证 | 可用于对应接口行为实验 |
| G3 系统功能 | 启动、存储器、MMIO、外部交互，选定中断路径完整通过 | 当前配置通过已执行的系统验收 |
| G4 归因校准 | 已知来源的组件/环境/软件缺陷分类正确，复现链完整 | 可按证据门槛发布组件缺陷报告 |

对 G1 的检查器必须测试“计划不变但生成 RTL 被改错”的情况。对于动态连接、译码或状态相关路由，静态图不够，加入 G2 行为性质；若前端不能提取必要结构，就报告未知。

安全性质和活性性质分开：不多驱动、不重复完成可检查安全性；最终返回需要对端响应等假设。外部 watchdog 到期只是诊断事件，不能假称为 RTL 已实现超时响应。

每个形式验证结果记录假设、参数、覆盖/可达性和证明类型，检查假设是否排除了要找的 bug。每个仿真结果记录真实执行与跳过项。测试通过不推导为任意状态下无 bug。

## 13. 反例定位、归因与去重

边界监视器记录周期/事件序号、实例端点、事务身份、地址、数据、字节使能、错误、复位阶段以及中断相关状态。事务 ID 回绕时使用运行实例和序列范围消歧，不能只用窄 ID 关联全程。

归因顺序：重现 → 核实性质 → 检查输入合法性 → 检查结构/环境/软件 → 缩减 → 隔离或最小交互复现 → 分类。缺陷报告同时保存支持与限制证据，不能把最早观测违例直接当作根因。

要确认组件内部缺陷，至少需要固定原始 RTL、明确应满足的性质、合法前置条件、可重复反例，以及排除相关环境问题的充分证据。隔离测试可能改变反馈时序，未复现不证明原组件正确；此时保留候选或未定位状态。

同一缺陷可能在多个拓扑和种子中出现，按组件版本、违反性质、最小反例及经人工核实的根因归组；不能把每个失败种子都统计成一个新 bug。CPU、外设和上游互联都可以作为研究对象，但每轮必须声明谁是待测对象、谁是环境。

## 14. 回归、缓存与再验证

变化影响表：

| 变化 | 至少重做 |
| --- | --- |
| 源码、参数、宏或前端工具 | 接口提取、结构审计、受影响行为验收 |
| 地址/可达关系/适配器/复位连接 | 计划、RTL、软件映射及相关 G1–G3 |
| 中断映射、外设清除或 ISR | 中断结构与生命周期检查 |
| 外部模型或激励约束 | 模型验证、合法性检查及相关系统实验 |
| 插桩或仿真工具 | 行为一致性核查、受影响复现与构建 |
| 检查器或参考模型 | 负例校准及既有相关失败重分类 |

缓存键绑定全部语义输入及工具；输入内容变化必须失效。生成采用临时输出目录，验证完成后发布到唯一运行目录，避免旧产物与新计划混用。失败保留诊断，不覆盖最近一次成功证据。

清理依赖/构建目录前保留可执行恢复步骤和身份清单；证据包不能仅保存已被清理路径的绝对文件名。

## 15. 代码落点与实施顺序

优先补齐已有链路，避免重写大模块：

1. 契约/端口处理：扩展 `soc_contracts.py`，新增聚焦端口台账的模块。
2. 计划：在 `soc_plan.py` 与 `soc_fabric.py` 加约束与证据绑定，复用已有目标适配解析。
3. 生成：`soc_renderer.py` 只消费已验证计划；新增审计独立于生成决策。
4. 验收：协议层测试负责互联/适配；integration 测试负责启动、外部交互和中断。
5. 实验：通过 `soc_campaign.py` 记录模式、证据和归因，不用覆盖率代替正确性判据。

本文要求对应计划任务：输入与基线（1）、端口契约（2）、拓扑/地址/转换（3）、实际结构审计（4）、启动与复位（5）、环境协议验证（6）、外部模型及配置（7）、中断（8）、归因（9）、准入校准与发布（10）。缓存和变更影响要求分别落实到各任务产物及任务 10 的重建检查。

编码前，每个子任务需冻结实际数据格式、函数输入输出、错误类别和最小正/负例。未选择的硬件语义不应写成虚构代码；先补来源，再生成实现。
