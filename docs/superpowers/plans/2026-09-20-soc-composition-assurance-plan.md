## 第一部分：最终系统是什么，怎样自动组合

### 1.1 目标、支持边界与阶段范围

用户提供首次接入的 CPU RTL/profile、外设 RTL/profiles 和组合请求。系统依据真实 RTL 接口和声明式契约，自动生成总线、存储器、中断、时钟复位及外部/特殊输入连接；后续接入运行环境与 fuzz，使确认的组件内部缺陷具有可复现和可归因的证据。

“未知”指组件实现首次出现，不表示能自动理解任意协议或 ISA。只要必要接口及执行能力已受支持，新组件与已有组件走同一流程，无需修改生成器；缺少能力时明确报告。

系统只有通用接线逻辑和按协议/能力复用的适配器，不按组件名称、型号、路径或源码哈希查表选接线。profile 是数据，不是专用脚本；不要求用户提供组件插件，不修改待测 CPU/外设内部 RTL。扩展支持范围必须增加并验证通用能力，不能增加型号特例。

#### 1.1.1 首期硬件边界

首期实现边界：一个 CPU 核，参与组合的组件使用同一个时钟域。允许 CPU 具有独立取指、数据接口，按实际竞争关系进行仲裁；单核不代表只有一个总线主接口。该边界不限制 CPU 或外设型号，符合条件的首次输入组件仍通过通用逻辑组合。

首期外设范围：外设作为 MMIO 从设备接收 CPU 访问，可以产生中断、连接外部引脚和特殊随机输入。首期不支持外设作为总线主设备主动访问 RAM 等目标，包括 DMA；多主接口仲裁范围不因此扩展到外设主接口。

必需 DMA 才能工作的外设明确报告超出首期范围。若外设具有可独立工作的非 DMA 模式，只能依据明确配置及相应契约使用该模式，并在实验报告记录 DMA 功能未测试；未使用端口的处理仍须有依据，不能简单绑死 DMA 端口。限制的是首期接口能力，不是外设型号，首期先验证 CPU 访问外设、外部事件和中断处理闭环。

首期不自动处理跨时钟域连接、多核一致性或复杂时钟切换。输入需要这些能力时，报告超出首期支持范围，不能静默合并时钟域或插入未经验证的跨域处理。复位仍按 profile 核对极性、同步方式和释放条件，不能因同域而统一绑线或假定复位契约相同。后续扩大范围时扩展并验证通用能力，不引入组件型号特例。

首期互联边界：复用当前全局仅允许一个未完成事务的 beat 互联，暂不扩展复杂并发互联。多个主接口仍通过必要仲裁访问总线。原生接口必须能够通过合法背压等方式串行处理，适配链保留已接受事务、ID 对应关系及其他必要语义，不能直接丢弃或静默降级；无法保持必要语义的组合明确报告不支持。

串行化可能减少组件经历的并发状态。生成与实验报告须注明这一限制，首期不承诺发现依赖多事务并发或乱序响应的缺陷；适配合法不等于测试行为覆盖完整。

#### 1.1.2 执行环境边界（后续运行阶段）

CPU 程序根据 ISA/ABI 后端和 profile 生成；未知 CPU 名称不妨碍使用已有 ISA 后端。首期软件执行范围为 RISC-V ISA 家族，沿用现有项目执行环境，暂不同时支持其他 ISA 的自动软件生成。这不限定 CPU 型号，也不改变通用接线目标。

用户可提交首次出现的 RISC-V CPU RTL，由 profile 声明指令集扩展、启动条件、权限模式等执行要求。系统逐项核对软件后端的实际支持能力，不能仅凭“属于 RISC-V”就判定可运行。启动代码和测试程序按执行能力生成，不按 CPU 型号选择专用代码。其他 ISA 或尚未支持的执行要求明确报告能力缺口；profile 可描述不等于已有执行支持。

外设的初始化、功能判据和清除操作必须来自 profile 与语义证据，不能从端口名自动猜测。

### 1.2 用户输入与职责分工

- CPU RTL：自包含文件，或顶层及完整源码集合；允许引用已缓存内容。
- CPU profile：顶层、构建参数、端口含义、协议、启动与执行约定、端口处理规则。
- 外设 RTL + profile：每个外设的实现、总线/寄存器/中断/外部引脚语义；每种设计可复用 profile。
- 组合请求：CPU 实例、外设实例数量、参数覆盖、可达关系、可选固定地址，以及 ROM/RAM 容量、地址约束和可选初始化镜像；可采用显式默认值。
- 测试设置：模式、种子、预算、特殊端口随机化策略和实验类别；可通过项目默认配置补齐并记录。

输入职责分工：组件 profile 描述该组件的接口、协议、能力和端口语义，不写死与某个具体对端实例的连接。组合请求指定使用哪些实例、各自参数、必要的访问关系和固定地址约束。通用生成器依据这两类输入及 RTL 物理事实，计算具体接线、地址分配、适配器与仲裁关系；用户无需逐根指定导线。

同一份 RTL 与 profile 可以被多个实例复用。例如，组合请求声明 uart0、uart1 引用同一组件描述，系统为它们分别分配地址和中断源，并按各自参数核查接口；不需要为实例复制修改 profile。组件固有的窗口大小、对齐和接口能力仍由 profile 声明，实例在当前 SoC 中的放置和连接需求由组合请求表达。

不要求用户提前提供总线顶层、连线文件、组件专用 Python 插件或完整测试平台。源码不是自包含时，profile 必须列出依赖文件、包含目录、宏与包顺序；不能只有顶层文件而假定缺失模块会自动补出。

用户 profile 是输入声明。系统校验它与实际 RTL 的名称、方向、宽度、结构成员和参数化结果是否一致；时序、寄存器及中断语义仍需规范或其他证据支撑。

物理事实与语义分工：生成前，在实际源码、宏和参数配置下解析并展开 RTL，从展开结果获取端口方向、参数化位宽、数组和结构体成员。profile 描述接口分组、各信号角色和协议，将语义显式绑定到真实端口、成员或位段。系统检查遗漏、重复绑定及物理事实与语义要求的不匹配，不依赖端口名称猜测功能，也不按组件型号套接线方案。

profile 若重复声明方向或位宽，这些声明仅作为校验条件；与实际 RTL 冲突时报告错误，不能静默覆盖 RTL 事实、反向接线或擅自截断/扩展以消除冲突。例如，profile 将 req_out 标为需要输出方向的访存请求，而实际 RTL 中它是输入，应报告绑定冲突。参数变化后重新展开并核查绑定，不能沿用旧配置的物理事实。

语义依据要求：profile 描述组件应遵守的契约，不是其自身正确性的唯一证据。接入时核查真实接口的一致性；功能语义保留规范、设计说明等来源。不能仅凭 RTL 与 profile 一致认定功能语义正确，也不能把从当前 RTL 行为提取的描述当作独立正确性依据。不要求预先证明整份 profile 完全正确，但必须区分已核实语义与缺少依据的声明。

### 1.3 profile：物理绑定、接口语义与能力

profile 应表达“端口是什么、属于哪个接口、怎样处理”，不能只有名字和注释。

职责限制：profile 只声明组件事实和有限操作，不允许嵌入任意程序。允许描述端口角色、协议、时钟复位、地址需求、寄存器属性（如只读、写一清除），以及特殊输入的合法值、采样时间和保持条件。初始化和清除通过系统定义的通用原语表达，例如写指定寄存器、带超时等待指定状态。

禁止在 profile 中嵌入组件专用 Python/C/RTL、接线回调，或通过自定义程序补齐系统不支持的协议。组件可以提供不同的描述数据，但必须由同一套通用逻辑校验和处理。有限描述无法表达必要行为时，明确报告能力缺口，不要求用户提供组件专用插件，也不能用描述数据绕过通用能力检查。

- source：顶层、源码闭包、语言、参数、宏、包含路径及内容身份。
- clocks / resets：端口映射、时钟域、频率约束、复位极性、同步方式及释放条件。
- interfaces：接口 ID、主从角色、协议/版本、信号角色到端口/成员/位段的映射。
- capabilities：地址/数据宽度、地址单位、字节使能、突发、ID、未完成事务、错误和权限语义。
- port_actions：每个端口或位段采用功能连接、常量、随机驱动或观测的处理规则。
- evidence：语义来源、适用参数和已执行检查；未知与已核实状态分开。

CPU 额外描述 ISA/位宽、统一或分离的取指/数据接口、启动入口、ABI/工具链要求、陷入/返回及中断入口语义。外设额外描述地址窗口、寄存器偏移与权限、读写副作用、初始化/清除操作、外部对端及中断产生条件。

常见协议引用系统已有契约并给出具体信号映射；不能仅写“ready 是就绪”而不说明它表示请求接受还是响应完成。多个端口共同构成一个握手接口时，必须作为接口组描述。

**协议描述按接口填写，而不是只给 CPU 填一个总协议名。** CPU 可以声明统一访存接口，也可以分别声明取指和数据接口；两者的协议和能力独立核实。ISA、CPU 数据位宽、地址位宽和总线数据位宽分别描述，不能互相推导。

现有 Ibex 描述已经使用下列格式。以下是取指端点的实际格式示例，不是完整 profile：

```json
{
  "endpoint_id": "processor.instruction",
  "function": "instruction_memory_master",
  "protocol": ["obi", "1"],
  "fields": [
    {"role": "req", "aliases": ["instr_req_o"]},
    {"role": "gnt", "aliases": ["instr_gnt_i"]},
    {"role": "addr", "aliases": ["instr_addr_o"]},
    {"role": "rvalid", "aliases": ["instr_rvalid_i"]},
    {"role": "rdata", "aliases": ["instr_rdata_i"]},
    {"role": "error", "aliases": ["instr_err_i"]}
  ]
}
```

用户的新 CPU 可用不同端口名，只需映射到正确角色；编译器核查方向和实际宽度。数据接口另行描述写使能、写数据、字节使能等字段。结构体接口复用现有 physical/member_path 选择器。protocol 中的版本值是项目协议目录的标识，不能未经核对当作上游标准版本。

同名协议还需检查子集：是否允许突发、多个未完成事务、错误返回、完整性或可选边带。不支持的必要能力不能被忽略，也不能退回随机驱动处理。

适配器匹配规则：按接口能力而非仅协议名称选择适配器。核对转换方向、协议版本与实际使用子集、地址/数据宽度、字节使能、错误返回及必要边带，并检查适配链是否满足首期单事务处理要求且保持必要语义。CPU 主接口到互联的适配与互联到外设从接口的适配不能混用，不能因协议名称相同就反向复用。

只有兼容的适配链才能进入合法连接计划。缺少转换能力时明确报告涉及的接口和能力缺口，不得丢弃必要信号以拼出可编译 RTL。适配实现按协议和能力通用复用，不按 CPU 或外设型号选择专用接线。

### 1.4 系统结构与自动生成流程

```text
用户 CPU RTL + profile             用户外设 RTL + profiles
                └──────────────┬──────────────┘
                         校验并绑定接口
                               ↓
                 自动生成 SoC 顶层及环境
  ┌────────────────────────────────────────────────────┐
  │ CPU → 必要适配 → 总线互联 → ROM/RAM                 │
  │                       ├→ 必要适配 → 外设 A         │
  │                       ├→ 必要适配 → 外设 B         │
  │                       └→ 通用中断控制器 MMIO       │
  │ 多主竞争时仲裁；地址译码和响应路由始终明确           │
  │ 时钟/复位/配置 → 各实例                             │
  │ 外设中断 → 通用中断控制器 → CPU 兼容中断入口         │
  └────────────────────────────────────────────────────┘
       ↑ 特殊输入/外部引脚           ↓ 状态/错误/轨迹
  fuzz harness + 合法对端模型         独立检查器
```

首期中断拓扑：外设中断统一接入通用中断控制器，由控制器向 CPU 兼容的中断入口发出通知。CPU 经总线访问外设及控制器的 MMIO 寄存器，完成配置、来源识别和处理；总线负责寄存器访问，控制器负责汇集与通知，不能以总线仲裁替代中断管理。

系统根据 profile 与组合约束自动分配中断源编号，生成连接和软件映射，不按组件型号打表。CPU 入口与控制器通知契约不兼容时明确报告能力缺口，不强行连接。首期不同时实现外设直连等其他通知拓扑；通用中断控制器属于测试环境，必须独立验证，不能默认无错。控制器具体寄存器和处理契约在实现前明确，现有环境模块不因名称相同就视为已满足本方案。

首期中断范围：外设与 CPU 同域，支持明确声明的电平、同域 pulse 以及 rising/falling/both edge source。level 直接采样；pulse/edge 仅在计划设置 `LATCH_MASK` 时保存 pending，edge source 先经 `soc_irq_edge_detect` 变成单周期脉冲。转换器只处理已归一化的同域输入，不是 CDC 同步器、毛刺滤波器或最小脉宽保证。跨域、无保持/清除依据或未声明 trigger 仍明确拒绝，不猜测转换。

中断验收覆盖“事件产生—中断通知—CPU 实际处理—清除—返回”完整过程，不以中断线拉高代替功能闭环，也不由测试环境代替 CPU 执行清除。行为异常按候选缺陷诊断规则处理，不能自动认定为不受支持的中断类型。

#### 1.4.1 从输入到生成产物

生成流程：先生成统一连接计划，检查通过后再生成 RTL，最后重新展开生成的 RTL 核查实际连接。扩展现有 plan 层，不另建平行组合框架，也不在读取 profile 时直接零散拼接顶层接线。

统一连接计划记录实例及参数、接口角色与真实端口绑定、各接口对端、必要适配器、总线及仲裁关系、地址窗口、中断源编号、时钟复位连接，以及常量、特殊输入导出和未连接端口的处理依据。计划由 RTL 事实、profile 和组合约束计算得到，不是按组件型号查出的固定接线表。

生成前检查计划中的遗漏、冲突和不支持能力；通用 RTL 生成器消费检查通过的计划。生成后从实际 RTL 展开结果提取连接，核对计划和接口约束，不能仅比较生成器自行输出的两份清单。该流程验证已声明的结构约束，不替代协议行为验证。

- 1：系统工作：导入源码/profile，固定文件和构建身份；失败处理：报缺依赖、顶层或构建参数。
- 2：系统工作：elaboration 提取真实接口，绑定 profile；失败处理：报端口/宽度/方向/成员冲突。
- 3：系统工作：分类所有端口，建立台账与随机端口组；失败处理：拒绝遗漏、冲突驱动与无依据处理。
- 4：系统工作：按接口能力求解访问图和合法适配链；失败处理：报不支持的协议/事务能力。
- 5：系统工作：保留指定地址，自动分配其余窗口和必要映射；失败处理：拒绝重叠、越界、不可达或资源不足。
- 6：系统工作：连接六类接口，分配特殊输入布局；失败处理：拒绝跨域不支持、布局冲突或不合法驱动。
- 7：系统工作：生成 RTL、源清单、软件配置、harness 和模型参数；失败处理：核对不同产物使用同一计划。
- 8：系统工作：独立检查实际连接，并验证环境与系统行为；失败处理：缺源码、连接遗漏、必要协议不支持等环境问题阻止常规运行；有效环境下的组件行为异常保存为候选缺陷并进入诊断；原因不明确时标记待诊断，不自动归为组件不支持。
- 9：系统工作：fuzz、保存失败、缩减、隔离重放并归因；失败处理：证据不足保持候选或未定位。

当前生成阶段执行上述 1–6、7 的 RTL/源清单/地址中断与端口清单部分，以及 8 的实际结构审计；有限 boot/ISR、MMIO 错误和 edge lifecycle 已有真实样例，但不代表完整软件或所有外设行为。生成清单记录外部端口责任、初始化规则、能力缺口和未验证性质，不能把有限运行证据外推成全组件功能正确。

### 1.5 接口连接规则

- 时钟和复位：SoC 顶层统一输入，按组件契约分发并生成必要的复位处理；核对域、极性、同步/异步方式和释放条件。
- 取指/数据访存：正确方向的 CPU 侧协议适配、存储器/总线路径。
- ROM / RAM：地址映射、镜像加载、读写后端与初始状态记录。
- MMIO：地址译码、目标路由、响应返回、必要的仲裁及外设侧协议桥。
- 中断：首期通过通用中断控制器汇集外设中断，核对 CPU 入口兼容性并自动生成源编号、连接与软件映射。
- UART / SPI / GPIO：默认作为外部接口导出顶层；组合请求明确指定内部对端时，检查兼容性后连接。后续测试环境按接口契约接入，不与 SoC 结构生成混为一体。
- 配置和故障输出：合法固定值、状态与错误观测。

“常见”仍以版本化支持能力表为准。当前 beat 互联、协议适配和环境模块尽量复用；尚未实现的组合或能力必须报具体缺口，不承诺所有常见接口已经支持。

CPU/外设内部设计不修改。生成包装器只做已声明连接和必要转换，不得修正待测组件的错误输出。

#### 1.5.1 每个端口的处理与所有权

- functional：适用情况：时钟、复位、访存、中断、UART/SPI 等已支持功能；最终连接：系统对应的环境模块、互联、适配器或对端。
- constant：适用情况：固定配置、明确禁用功能；最终连接：有位宽、有依据的常量。
- fuzz：适用情况：profile 明确允许随机控制的特殊输入；最终连接：SoC 顶层输入，由 fuzz 驱动器提供值。
- observe：适用情况：状态、错误、告警、特殊输出；最终连接：顶层输出或被动监视器。
- unconnected：适用情况：契约明确允许不连接的端口；最终连接：显式保留空连接并记录原因。

上述处理方式的 schema 在迁移步骤 2 冻结。功能输入不能因用途未知而转成 fuzz，输出不得随机驱动。双向端口的处理见 1.5.3。

完整端口处理要求：所有端口及位段必须记录去向，包括功能连接、有依据的常量、顶层导出或契约允许的显式不连接。顶层导出覆盖特殊随机输入、外部接口和观测输出，其功能、方向及驱动来源仍须明确；不能将所有导出端口都视为随机输入。显式不连接仅适用于契约允许的端口，并记录原因，不能借此放任需要驱动的输入悬空。

输入不能因为用途未知而默认绑零或随机驱动，同一输入不得有多个驱动来源。向量仅部分位被使用时，剩余位同样逐位段记录处理依据。例如，8 位中断输入只使用 3 位，其余 5 位应按各位契约连接为无效电平，不能遗漏或一律假设无效电平为零。

#### 1.5.2 时钟与复位

首期 SoC 顶层提供统一时钟与复位入口，组件包装不各自生成时钟。profile 描述组件时钟端口、复位有效极性、同步/异步方式及释放要求。通用逻辑据此生成分发和必要复位处理，不能把简单极性转换当成完整的同步处理。

组件需要特殊复位顺序时，核对现有通用模块是否能够满足；能力不足则明确报告，不猜测延迟、不按组件型号插入特例。核查实际生成的时钟、复位连接与处理模块是否符合声明。本规则只规定 SoC 内部接收和分发时钟复位，不规定测试环境激励的产生方式。

#### 1.5.3 外部接口与双向端口

profile 描述 UART、SPI、GPIO 等非 MMIO 接口的信号角色、方向和模式。组合请求没有指定内部对端时，作为外部接口导出 SoC 顶层，不因名称相似或存在同类接口就自动互接。明确指定内部对端时，检查角色、协议、位宽及必要接口约束兼容后生成连接；例如不能把两个 SPI 主接口仅按同名信号相连。

顶层外部输入不自动归入随机输入，随机驱动须显式声明。双向接口明确输入、输出及输出使能，缺少受支持的双向连接方式时报告能力缺口，不能当作普通单向导线处理。导出顶层明确了 SoC 边界，不等于外部驱动或对端环境已就绪；生成器负责落实连接意图，不猜测外部关系。

#### 1.5.4 存储器与初始化

CPU profile 描述取指/数据接口、启动地址要求和必要的存储器访问约束；组合请求给出 ROM/RAM 容量、地址约束及可选初始化镜像。系统使用通用存储器模块生成实例，接入地址译码、必要仲裁和响应路径，不按 CPU 型号编写专用存储器接线。

生成时检查启动取指地址是否落入可执行区域，以及访问宽度、读写权限、地址范围和实际访问路径是否兼容。镜像格式、加载位置及未初始化区域的处理方式必须明确并记录；未提供镜像不等于隐式加载某个程序，不能依赖隐含默认值。本规则只规定存储器结构与初始化接口，不涉及测试程序生成，也不把地址可达视为 CPU 一定能启动。

#### 1.5.5 地址、MMIO 与副作用

profile 提供外设地址窗口大小、对齐要求、寄存器偏移和访问属性。系统保留用户指定的合法地址，自动分配其余窗口，并检查重叠、越界、可达性和地址转换；不能为满足分配而静默改变用户固定地址。总线译码、软件访问地址和测试配置消费同一份分配结果，再独立核查生成 RTL 的实际连接与译码。

自动分配地址不等于自动推断寄存器语义。读清除、写一清除、FIFO 等副作用必须明确描述，不能把任意寄存器当作普通 RAM。位宽不匹配时，仅允许已验证且保持相关访问语义的转换，不能默认拆成多次访问或自动读改写。例如，一次宽访问若变成两次 FIFO 读取并改变消费次数，不能仅因位宽能够拼接就允许该转换。

#### 1.5.6 错误响应与等待

未命中任何目标的地址访问进入通用错误响应路径，不能因译码未命中而悬空或永远等待。写 ROM、违反访问权限等请求按明确策略返回错误，不静默当作成功。错误响应通过适配链返回原请求接口，并保持请求与响应的对应关系；CPU 原生接口无法表达所要求的错误语义时报告能力缺口，不能用正常零数据冒充错误响应。

未命中地址与已命中但目标迟迟不响应是两种不同情况。本规则不要求为所有外设添加响应超时，不允许把目标的等待或无响应静默改写成未映射地址错误。错误响应路径仍遵守协议握手与背压条件，不承诺在对端不接受响应时也能无条件完成事务。

### 1.6 中断：拓扑、控制器与时序契约

以下将“通用控制器、同域源、CPU 经 MMIO 处理”落实为已实现且可检查的首期方案。控制器是生成 SoC 内的真实 RTL/MMIO 从设备，同时属于需独立验证的环境基础设施；不能只实例化在 harness 内。这是项目自有、版本化的控制器契约，不声明兼容 PLIC，也不借用 PLIC 名称暗示优先级、阈值或上下文能力。

#### 1.6.1 CPU 入口与外设源

首期控制器提供一个上下文、一根同域 active-high 通知线。CPU profile 明确该线所绑定的真实输入端口/成员/位、有效极性、时钟域和入口语义；当前只接受 `machine_external`。`machine_timer`、`machine_software`、supervisor/user external、NMI、debug、machine-local 及跨域入口逐项拒绝并记录原因，不能绑到 machine external 或随机端口。通知不携带源 ID；来源只能通过控制器 MMIO 识别。需要编码 ID、确认握手、多上下文或 CPU 专用中断协议的配置仍报告能力缺口。RISC-V ISA 声明不能代替入口检查，不能统一假设 CPU 有两位 irq 总线。

外设 profile 将每个中断源绑定到实际输出位，声明同域电平、有效极性、产生/保持条件及解除原因。一个向量可声明多个独立源，也可在其确实只有一个汇总输出时声明一个源；生成器不主动 OR 合并多个输出。低有效源或 CPU 低有效入口允许通用组合反相以统一有效语义，计划明确记录该反相；这不转换事件类型，不插入脉冲捕获、同步器或 CPU 专用包装。缺少极性、域、保持或源清除依据时报告缺口，不猜测。

#### 1.6.2 源编号与容量

控制器按实际源数 N 参数化，源 ID 为 1..N，0 表示无可领取源，内部 ID 宽度为 max(1, ceil(log2(N+1)))。按稳定实例 ID、接口 ID、声明的源 ID 和逻辑位序排序编号，不使用输入列表顺序、物理端口名字或组件型号选表。向量声明需给出逻辑位到实际展开位的映射，不能依赖 Verilog 声明升降序猜测。实际控制器输入位 k 对应源 ID k+1；位图逻辑位 i 对应源 ID i，位 0 保留。准入同时检查 N 不超过该控制器实现版本已验证的 max_sources、MMIO ID 表达范围和可分配地址窗口，超出则明确拒绝，不截断或宣称任意规模已验证。本稿不虚设已验证上限：max_sources 尚需在步骤 4A 依据实现与边界验证确定，未确定前不发布支持任意 N 的承诺。ID 表、容量、编号算法版本进入计划身份，增删源后重新生成映射。空源集合不实例化控制器，其 CPU 入口按允许禁用的契约接无效电平；无法禁用则报缺口。控制器保留位与所有未用位读零写忽略。CPU 剩余输入位只有契约允许且组合请求选择禁用时才接无效值；其余分别功能连接、合法导出或报告不支持，不能套用控制器保留位规则。

#### 1.6.3 三条连接路径

第一条从原始外设输出位，经明确的极性归一化，到控制器指定 source 位；第二条从控制器通知输出，经必要极性转换，到 CPU profile 指定的实际入口位；第三条从 CPU 数据访问接口，经合法适配、仲裁和地址译码，到控制器 MMIO 目标，并沿响应路径返回原请求者。CPU 到外设清除寄存器的路径也必须可达。统一计划为控制器记录真实实例、容量参数、时钟复位、地址窗口、三条路径和源 ID 映射，不能继续把外设源直接记为 CPU 的某个 irq 编号。外设向量选错位、controller 源位互换和 CPU 接错位均应能由重新展开的实际结构发现。

#### 1.6.4 MMIO 寄存器与原子操作

首版寄存器选择 32 位、4 字节对齐的自有 ABI，这限定寄存器访问而非 CPU xlen 或总线宽度。位图组数 B=ceil((N+1)/32)，窗口大小取不小于 0x20+8B 的最小 2 次幂，并按该大小对齐；地址分配与其他目标使用同一规则，基址可由合法固定约束指定。只允许完整 32 位访问，非法大小、字节使能、方向和偏移返回错误且无副作用。更宽 CPU 总线只有具备已验证的单次 32 位访问及正确字节通道能力时可接入；不拆分 claim，不对 enable/complete 自动读改写。32 位 ID 的表达上限只是 ABI 边界，不等于该规模控制器已实现或验证。

- 0x00 CLAIM：只读、有副作用。返回获选源 ID，无候选或已有处理中源时返回 0；成功领取原子清该源 pending 并设置 in_service。
- 0x04 COMPLETE：只写 ID。仅接受与当前 in_service 匹配的非零 ID；错误 ID、0 或没有在处理的源时返回错误且不改变状态。
- 0x08 IN_SERVICE：只读，返回当前处理中源 ID，空闲为 0。
- 0x0c SOURCE_COUNT：只读，返回 N。
- 0x20+4j PENDING[j]，0≤j<B：只读位图，观察 pending，不领取、不清除；组 j 的位 k 对应 ID 32j+k。
- 0x20+4B+4j ENABLE[j]，0≤j<B：读写位图，1 允许通知和领取该源；复位为 0。未定义偏移返回错误。

控制器在一次合法请求被接受的时钟沿提交一次寄存器操作，并保存相应响应；等待响应接受期间保持响应稳定，禁止再次提交。CLAIM 返回领取时的 ID，背压不能使其变化或导致重复领取。复位优先于请求接受，复位期间不接受请求并清除旧响应；配套互联/适配器须遵循相同复位撤销契约，不能复位后重放旧 claim/complete。控制器正常操作仅来自 CPU 总线，生成 SoC 不保留环境 claim/complete 控制入口；单元验证可用总线模型驱动接口，但该证据不等于 CPU 执行证据。

#### 1.6.5 领取、完成与复位时序

固定最低 ID 优先，首期只允许一个处理中源，不实现可编程优先级、阈值或嵌套领取。每个采样沿，对于未在处理且未在该沿被领取的源，未设置 latch 的位按输入电平更新 pending；设置 `LATCH_MASK` 的位按 `pending | source` 更新，置位优先，只有成功 CLAIM 才清除。这样 pulse/edge 转换器输出不会在 CPU claim 前消失，而默认纯电平行为保持兼容。屏蔽只影响通知和领取，不清 pending；屏蔽期间仍采样源。候选从时钟沿前的 pending、enable 和 in_service 计算；该沿新出现的电平/脉冲在下一次请求时才可被领取。ENABLE 写在接受沿后生效。

CLAIM 清所选 pending 并设置 in_service，该源在处理期间 pending 保持 0。其他源继续采样 pending；已有 in_service 时通知线无效且 CLAIM 返回 0。COMPLETE 只结束匹配 ID 的控制器处理状态，不能清外设状态或主动拉低外设输出。完成沿不重新采样该源，下一采样沿若源仍有效则重新 pending；若外设已清除则保持无 pending。CPU 清除外设条件与 COMPLETE 是两个不同 MMIO 操作，源码和 profile 必须能说明源如何解除；若源清除传播尚未完成便 COMPLETE，允许再次通知，控制器不得替 DUT 屏蔽该现象。多个源同时有效按 ID 顺序领取，持续未清除的低 ID 源可能延迟高 ID 源，首期不承诺公平性。

沿前 pending 可能比当前物理电平晚一拍，CLAIM 因而可能返回刚撤销源的 ID；这是明确的采样语义，不保证领取时外设状态仍有效。服务期间同一源的多个事件由外设状态/FIFO 等契约表达，控制器每源一位不计数，也不承诺自动排队保存这些事件。功能覆盖清单须列出此限制以及单 service 无嵌套、固定优先可能饥饿的行为损失。

复位将 enable、pending、in_service 和响应状态清零，通知无效；释放后按采样规则重新观察源，复位期间出现又消失的事件不保留。所有控制器状态与生成 SoC 的复位契约一致，不能仅复位 CPU 而遗留处理中 ID。edge converter 复位期间丢弃 in-flight pulse，首次释放时按 `RESET_LEVEL` 与原始输入比较；该语义进入 converter RTL 负例。结构审计验证连接和极性；状态机、MMIO 一次提交及复位行为用独立 controller/edge RTL 验证确认，真实 Ibex lifecycle 另外验证 CPU claim/ISR/clear/complete。

### 1.7 输入方式与驱动边界

#### 1.7.1 CPU 执行、总线 BFM 与顶层驱动

RFuzz 变异的是输入语料的原始字节，已有运行链将其解码成每周期输入；RTL/仿真器构建与每个样本的执行是不同步骤。当前 campaign 先构建仿真产物再交给 RFuzz 连续运行，matrix smoke 还按生成内容、测试平台、程序、工具和源码身份缓存构建。因此需要改进的是“随机字节怎样变成有意义且可验证的刺激”，不能把现状概括为“每个样本随机编译 RTL”。程序生成、程序编译、RTL 编译、语料变异和协议驱动各自记录成本。

三种方式处于不同层级，并非只能选一个：

- **让 CPU 执行并访问组件。** CPU 接收符合其契约的指令/数据存储器内容、复位、外部事件和特殊输入，CPU 自己产生访存请求并经真实互联访问外设。最终信号当然是 0/1，但直接随机翻转取指响应、总线输入不会自然形成合法程序或一致存储器。这种方式覆盖取指、执行、寄存器数据流、访存、互联及外设的实际因果链，适合作为本项目主模式。
- **总线 BFM 主动访问目标。** 通用总线驱动器产生事务，适合隔离外设、互联或重放已捕获请求，缩小异常归因范围。CPU 通常是访存 master，不因接在同一总线上就有可写的 slave 入口；除非 profile 明确声明受支持的调试/从接口，否则 BFM 不能直接“访问 CPU 内部”。即使有该入口，也不等于覆盖 CPU 正常取指执行行为。现有 mmio_only 保持 CPU 复位，可作为隔离方式的基础。
- **驱动整个 SoC 顶层。** 这是物理边界，容纳前两种方式的环境入口和 UART/SPI/GPIO、特殊输入等事件；它不意味着任意顶层位逐周期翻转都合法，更不能越过边界强制内部 CPU/外设输出。应由各自语义驱动器把输入选择转换成合法的顶层时序。

据现有能力，建议主模式为“CPU 执行经约束的 ISA 指令/内存镜像，并由合法外部事件及特殊输入共同刺激”，BFM 作为隔离诊断和对照模式。现有 mixed 模式可保留为显式竞争实验，但不能把 BFM 完成的访问计为 CPU 覆盖。每个物理输入只有一个驱动者，每个已接受事务只有一个所有者；CPU 与 BFM 若同时存在，只能作为不同主接口经既有仲裁进入总线，不能同时覆盖同一 CPU 输出或目标输入。模式在测试开始、复位及无在途事务的明确边界选择，不能中途偷换所有权。控制器 claim/complete 在主模式仍由 CPU 实际 MMIO 操作，不能用 BFM 补出假的 ISR 闭环。

这不是将旧 mixed 改名：旧 mixed 明确同时启用 CPU 与独立 fuzz_mmio 主接口；新 `cpu_only` 主模式已经能装载有限 instruction/data image，但多候选、完整跨记录依赖和 BFM raw layout 仍拒绝。通过版本化 drive_profile/ownership 策略明确“CPU 执行 + 外部事件”“BFM 隔离”“CPU/BFM 竞争”，保留旧 mode 含义、布局及回归，不暗改语料解释。

#### 1.7.2 特殊输入的导出与时序策略

这是目标系统的正式能力，CPU 和外设都适用。特殊端口原则：profile 显式标记允许随机驱动的特殊输入，系统自动导出到 SoC 顶层；未知用途的必要功能输入不能自动归入随机端口。随机驱动不意味着任意逐周期翻转都合法。

例如 CPU 有四位自定义输入 event_i，profile 声明其为同域独立事件、允许每周期变化，则系统：

1. 从参数化 RTL 验证 event_i 是四位输入。
2. 生成稳定的顶层端口标识，例如 cpu0__event_i。
3. 在该实例的随机布局中分配四个位，记录 offset、width、位序及布局版本。
4. 生成顶层端口到 CPU 实例 event_i 的单一连接。
5. fuzz harness 每个有效采样周期从输入流取出四个位，驱动顶层端口。
6. 保存实际施加值、采样时刻和输入身份，使失败能够精确重放。

以简化包装示意说明连接关系，实际端口名和时钟名来自 profile：

```systemverilog
// 仅展示特殊端口绑定，不是完整可编译的 SoC。
input logic [3:0] cpu0__event_i;
// CPU 实例端口连接：.event_i(cpu0__event_i)
```

随机数由测试 harness/fuzz 输入流驱动；用户 CPU 内部不插入随机数发生器。协议相关端口组由一个驱动器共同控制，不能把 ready/valid/data 各自随机翻转当成合法事务。

需要支持的驱动策略：

- cycle_value：行为：每个允许采样周期取一个值；需记录的约束：时钟域、合法值、何时允许更新。
- reset_sampled：行为：复位配置窗口选择一次，之后保持；需记录的约束：配置窗口及再次选择条件。
- pulse：行为：输入决定是否触发，驱动器产生约定脉冲；需记录的约束：极性、宽度、间隔、可否重入。
- hold / handshake：行为：值保持到指定条件满足；需记录的约束：保持条件、确认信号及组内因果关系。

直接按位随机仅适用于明确不需要额外约束的输入。带约束时保存原始 fuzz 字节、转换版本和实际驱动轨迹；拒绝、修正或丢弃样本要计数。约束不得静默变化。

具有保持、脉宽或握手要求的输入，由通用驱动器按 profile 声明的约束产生；缺少所需驱动能力时明确报告，不能退回无约束按位随机。例如，仅允许复位期间变化的配置位应在规定窗口随机选择，随后保持，不得每周期翻转。所有策略记录实际施加的值与时序，以支持重放。特殊输入的脉冲驱动不代表首期自动组合已支持脉冲中断，仍须遵守各功能接口的支持边界。

合法交互实验和故意违反接口约定的故障注入/健壮性实验分别标记，并保留实际违反的约束。故意非法输入引起的异常不能直接认定为组件 bug；只有违反明确规定的错误处理行为时才可作为相应缺陷证据。合法交互实验中出现驱动违例时，应保留异常并诊断驱动或环境问题，不能继续把该输入标记为合法。

### 1.8 输入约束：来源、分类与执行

输入约束定义“在本次实验契约下，环境可以向 SoC 提供什么、何时提供”；依赖修复是满足这些约束的一种实现手段，两者不能混为一谈。约束满足只证明已声明的环境前提成立，不证明 profile 正确、连接正确或 DUT 正确。以下为目标设计，不能据此认为现有正式运行链已经全部支持。

#### 1.8.1 约束来源与责任

RTL elaboration 提供方向、位宽、参数和实际端口，不能仅凭端口名称推断功能；组件 profile 描述协议角色、ISA 能力、复位/配置窗口和有依据的端口语义；通用协议/ISA 契约提供可复用规则；组合计划提供实例绑定、真实地址窗口、中断路由和输入所有权；实验配置只选择场景、预算与搜索偏好。每条规则记录来源及版本，用户只补无法自动获得的事实，不重复手写生成后的地址和接线。来源冲突、缺失语义或不支持的规则须定位到实例、字段和规则并报告，不能按“最后一个配置覆盖前者”默默通过。profile 中的行为事实仍须独立核验，不能由同一份声明同时产生激励与唯一正确性判据。

#### 1.8.2 规则分类



- 环境硬约束：输入位宽、允许值、复位配置保持、协议驱动时序等；适用条件成立时必须满足，不能被随机混合分支绕过。
- 场景前置条件：为了到达某个行为所选择的初始化、操作顺序和状态要求。它们限制的是该场景，不是组件全部合法行为。例如“事件在使能后到达”可用于中断处理场景，但不能禁止另一个场景测试使能前事件。
- 搜索偏好：地址偏置、事件频率、指令权重、延迟分布等；用于提高到达概率，不作为合法性证明。它们与硬约束分开计数、版本化及对照。
- DUT 保证/检查断言：例如 DUT 请求在背压期间保持稳定、响应对应已接受请求。它们不是供修复器修改 DUT 的输入约束；违例必须保留为异常，不得转成过滤该样本的条件。

#### 1.8.3 约束范围



- 位与字段：有符号解释、掩码、枚举、范围、对齐、保留位、互斥关系及条件有效性。保留位不默认清零，必须有契约依据；无效周期的载荷区分“不关心”“必须保持”“规定常量”，不能统一置零。二态 fuzz 不等于已验证 X/Z 行为，四态初始化与传播检查另列验证边界。
- 指令与镜像：ISA 扩展、指令长度、编码组合、初始程序入口、取指区域、分支目标及有限程序的数据流。正常执行场景与定义内异常场景分别配置，不能一律禁止异常指令或异常地址。
- 访存与 MMIO：实际有效地址、访问宽度、字节使能、窗口边界、访问权限、寄存器副作用及操作前置。CPU 输出的非法请求是待检查行为，不能在互联前改成合法地址；环境拥有的 BFM 候选才可以在提交前修复。
- 协议与跨周期：请求/响应接受点、等待期间保持、事务归属、顺序、允许在途数及复位取消规则。只约束本端拥有的信号；对端是否及时响应属于契约检查或运行超时分类，不能靠输入规则保证它成功。
- 时钟与复位：合法采样相位、复位极性与宽度、同步释放要求、配置采样窗口和状态恢复策略。首期单时钟由 harness 按契约提供，不把时钟当普通随机位翻转；复位插入作为显式场景，不能在发现等待或错误时偷偷重置 DUT。
- 中断与外部事件：UART/SPI/GPIO 等已支持协议的事件格式、间隔、持续时间、前置事务，以及特殊输入的 pulse/hold/reset_sampled 策略。真实外设 IRQ 是 DUT 输出，环境只能驱动其合法外部原因；CPU 中断入口由已生成的路由拥有，不能再由随机输入覆盖。只有契约明确归环境所有的独立中断源才由环境驱动，并单独标记覆盖范围。

#### 1.8.4 声明形式与现有能力

拟在现有 ABI/静态策略/布局约束上编译统一规则记录，而不是再要求用户编写一份组件程序。记录至少包含稳定规则 ID、依据、适用实验/模式、目标字段与所有者、条件/读取集合、谓词及参数、允许修改集合、执行阶段、必要的有界状态、失败分类和检查器引用。字段映射绑定 elaboration/layout 身份，读 DUT 信号只用于被允许的事件观察，写集合只能指向环境候选或环境驱动器状态。仅提供已实现的通用值约束、关系约束和有限时序原语，不开放 Python 回调、任意脚本或无界状态机。未知原语与尚未实现的约束交集直接报告不支持，不能假装支持任意 CPU/协议。

现有 RuntimeProjector 已有 range、enum、mask、alignment、gated_by 等字段处理，并显式拒绝部分指令约束交集；static_policy 已有 mask_align、legal_set、dependency_gate、mutual_exclusion、rarity_fold、entropy_mix 等动作。新增统一记录必须保留这些既有语义和身份：特别是当前无效 gate 的清零行为不能泛化为所有协议的保持规则。新增时序或条件语义应使用新版本/明确动作并交给在线协议驱动器，不改变旧语料的解释。

#### 1.8.5 执行与失败分类

编译时检查来源、类型、方向、所有权、能力、约束交集和依赖闭包；样本准备时生成或修复未提交的候选，并重新检查全部适用硬约束；运行时由驱动器遵守时序，并由接口监视器检查实际施加的轨迹。静态通过不能代替运行检查。结果分别标记为约束冲突、能力不支持、样本不可满足、求解预算耗尽、驱动违例、DUT 违例或观察不足；拒绝原因保留，DUT 超时不能自动归为输入不可满足。缩减与重放保留同一约束身份、实验类别和失败性质。

#### 1.8.6 防止过度约束

每个受支持的接口/模式均列出未约束、已约束和暂不支持项；每条新增硬约束给出依据与允许边界样例。比较约束前后有效输入去重率、行为到达及 DUT 覆盖，保留边界值、合法异常、背压、寄存器相关和事件竞争场景。正式合法交互只放宽偏好或场景选择，不随意关闭接口硬约束；需要故意违反后者时另建鲁棒性实验并使用对应错误处理判据。通过约束不等于完整行为覆盖，更不等于异常已经归因到组件内部。

### 1.9 依赖修复：指令、地址与跨周期关系

拟复用现有 raw ABI、静态依赖图与投影框架，由源码结构、CPU ISA/profile、组合计划、寄存器契约和明确时序规则编译一个版本化修复计划。结构依赖只说明谁连接谁、什么路径可达，不能自动推导任意寄存器语义或跨周期行为。规则必须是受限声明式通用原语，并记录依据、读集、可修改字段集合、前置条件和检查器；不允许组件型号脚本。修复对象仅为尚未提交的环境输入选择、指令/初始镜像或合法事件计划，不包括 CPU 寄存器强写、DUT 请求地址/写数据改写、外设响应替换和强制 IRQ。

#### 1.9.1 需要处理的依赖

应分别表达以下依赖，而不是只修若干相邻位：

- ISA 编码依赖：扩展、指令长度、opcode/funct、寄存器字段及立即数的合法组合。修复编码后还需独立解码核查；合法编码本身不保证控制流、数据访问或程序目的有效。
- 寄存器与控制流依赖：用于后续访存/分支的基址、立即数和目标需要前序初始化或已知状态。可修改候选指令的操作数、显式生成必要初始化，并重新检查后续受影响的指令；不能靠强写 CPU 架构寄存器完成依赖。基址来自 MMIO 返回等未知动态值时，记录未知或使用受支持的运行检查，不能从当前 DUT 的错误执行结果反推“正确输入”掩盖错误。
- 地址与权限依赖：用组合计划确定 CPU 可达 ROM/RAM/MMIO、字节地址、访问宽度和权限，检查有效地址及跨窗口情况。把原始地址取模到窗口内仅是取样偏置，不能证明 CPU 的基址加立即数最终访问了该窗口。FIFO、读清除、写一清除等副作用约束不可用任意拆分或读改写满足。
- 操作前置依赖：初始化、使能、状态检查、外部事件、数据收发与源解除的顺序来自寄存器契约。通用有限操作图可以表达“先使能、再送事件、再读状态”，但不默认所有组件采用同一寄存器序列，也不为每次操作添加多余复位而消除有趣状态。
- 跨周期依赖：请求接受、等待期间保持、响应归属、外设中断保持、控制器领取/完成及复位阶段。依赖事务事件而非固定假想周期，允许合法背压和多样延迟；对端迟迟不响应时保留真实等待和超时诊断，不伪造成功使输入看似有效。

#### 1.9.2 编译、样本准备与在线驱动

编译期只解决静态事实、约束顺序、能力和所有权；样本预处理解决有限指令/镜像及事件计划；在线驱动器根据真实握手观察更新自身状态。观察 DUT ready/valid/IRQ 可用于判断已发生的接口事件，不能把这些输出作为功能正确性的唯一参考模型。环境拥有的存储器 responder 可以按声明选择其 ready/响应延迟并保证自身服务规则；它无权修改真实 MMIO 外设的 ready/data/error，也不能接管本不归它的地址。现有 declared_windows 存储器契约应作为这一隔离的基础。

推荐主场景按“测试开始/建立初态 → 保持 CPU 复位并完成镜像和环境初始化 → 冻结非自修改镜像 → 释放 CPU → 按真实事务调度事件”执行。运行期不根据错误 PC 临时改写指令以帮助 CPU 返回预期路径；自修改代码须另有明确存储一致性与检查契约。既有 on_demand 存储器模式可以作为显式独立策略保留，但确定初始化规则不能用于把异常取指地址自动修成有效程序。

“冻结”约束环境初始化器不再改写，不得拦截 CPU 正常 store 或擅自将 RAM 改成只读。需要稳定代码的主场景通过合法区域/程序约束达成；支持自修改时按相应契约验证。host 可在获得完整多周期样本后先解码镜像和事件，再通过初始化入口装载，后续周期交给驱动器，不需要为每条 0/1 输入重新编译 RTL。新增模板、插入初始化或保留基址寄存器都会限制分布，须计入覆盖清单；保留真实 RAW/WAR/WAW 寄存器依赖和 hazard 场景，不能将依赖修复理解为消除 CPU 内所有数据依赖。

现有首次接受访问时懒初始化本身并非错误；复用该模式时保存接受点所用熵及初始化后的地址—字节映射，同址后续访问保持一致，不能根据观察到的异常结果重写既有字节。它和执行前冻结整幅镜像的主场景分别报告，不混称相同的程序前置条件。

#### 1.9.3 示例：外设事件到 CPU 中断处理

例如一个契约已支持中断的 MMIO 外设：raw 候选选择指令/操作数与事件参数，先修复 ISA 编码，通过正常指令建立合法基址并构造寄存器访问；候选程序先访问使能寄存器，事件计划在契约要求的前置事务真实发生后才送入外部事件；外设真实 IRQ 进入控制器，CPU 实际领取、访问外设解除条件并完成处理。此处仅描述受支持操作模板的因果依赖，具体 ISR 生成仍属于后续软件工作。事件不按假定第 k 周期强行发生，控制器不代 CPU 操作；CPU/外设未按预期响应时保存轨迹和前置状态，不能逼 ready/IRQ 或修改已执行指令使该链看似成功。

#### 1.9.4 冲突处理与防止掩盖错误

修复流程先检查结构与字段所有权，再在明确实验类别下依次处理编码/初始状态、数据流/地址、操作前置，最后交给在线协议驱动器。每次修复计算受影响约束的传递闭包，只重新检查相关下游字段；不得假定按 action ID 执行一遍就满足所有约束。同一字段多规则写入需在编译期证明可组合或确定显式优先关系，随后检查全部硬约束；无法兼容则拒绝该规则组合。循环依赖只允许已实现的有界求解/有限展开，超过步数、状态或事件预算及不可满足分别计数并停止该样本，不无限重试，不偷偷退回未经检查的原始输入。合法区域内仍可按原始熵确定选择，尽量保留未受约束位；不承诺全局最小位修改。

输入有效以具体实验契约为准，不等于“避免一切异常”或“DUT 必须响应”。合法交互测试保证环境遵守接口前提；针对 ISA/执行环境已定义的非法指令陷入、未映射访问、未对齐行为、中断/返回或错误响应可设独立场景和判据，不一律修成普通成功访问。故意违反接口前提的鲁棒性/故障注入另行标记，不能和正常合法输入混算。地址可达偏置、稀有事件频率和 direct/entropy 混合是搜索策略，不是硬合法性证明；直接分支也不得绕过该场景的硬约束。没有响应时保存反例和环境假设，不能立即判成输入无效或自动改输入绕过可能的组件 bug。

### 1.10 验证证据、覆盖与 bug 归因

#### 1.10.1 生成产物与身份

复用现有 plan、stimulus、render 和运行 manifest，补充以下内容：

- 源码、profile、工具、参数和组合约束的身份。
- 逐端口处理台账、实例/接口绑定和适配选择依据。
- 实际 RTL、源码清单、地址表、中断表和软件镜像。
- 顶层特殊输入与 fuzz 位段映射、驱动时序规则、初始状态。
- 独立结构审计、协议检查及真实运行记录。
- 首期单事务互联的适用条件、串行化依据及并发测试局限。
- 原始输入、实际驱动、反例缩减及隔离复现包。

随机布局按稳定实例 ID、端口/位段 ID 排序，声明位序与采样规则。布局或驱动规则改变必须改变身份；旧语料不能按新布局静默解释。复位时驱动器内部状态和 DUT 状态如何恢复必须记录。

同一输入与策略生成确定性计划。若随机选择拓扑，则单独保存组合种子；不与运行输入种子混用。

#### 1.10.2 输入重放与效果评价

保存原始 RFuzz 字节、语料谱系、transport/layout/修复计划与实现版本、可用的策略种子、初始内存/复位状态、每项修复前后值及原因、样本拒绝/延迟/丢弃计数，以及实际驱动和已观察事务轨迹。官方 RFuzz 当前接入未提供全局变异种子时，明确记录不可用并保存语料，不伪称仅靠 seed 能重现其搜索过程。运行重放以已保存输入、环境初态、规则和事件调度为依据；协议重放等待真实握手，时序不同须报告分歧，不盲按原周期强制旧响应。静态修复相同输入应产生相同产物；有状态驱动还要求相同状态和观察历史，不能宣称单个 raw word 脱离上下文即可确定全部时序。

生命周期也进入身份：测试开始、DUT 复位、驱动器复位与内存重新初始化是不同操作，声明哪些状态清除或保留；记录事件触发条件、实际周期、采样相位、请求/响应接受点及复位插入位置。不能把仅复位 DUT 的重放等同于重建整个测试初态。

CPU/总线复位不意味着 RAM/ROM 初始化区自动恢复；逐项记录字节镜像、投影器状态、事件队列、中断控制器和覆盖计数的恢复/保留策略。静态约束不可满足、有限求解预算耗尽、运行中真实 DUT 等待超时分开统计：前两项报告策略/样本状态，最后一项保留候选行为及环境证据，不能统一当修复失败丢弃。

同一 SoC/工具/覆盖身份下比较直接输入、现有约束基线与新依赖修复：分别记录冷构建、复用构建、每样本投影/调度成本、每秒执行周期和样本；记录输入满足各项前置条件的比例、拒绝率、实际 CPU 执行和各目标事务；记录原始语料数与去重后有效镜像/事件序列数，检测大量 raw 映射到同一有效输入的多样性损失。覆盖仅统计 CPU/目标组件及明确互联观察点，不将修复器自身计数增长算成 DUT 覆盖。报告边界/异常场景、功能/模式覆盖与发现的可重放候选、最终确认内部 bug；有效率上升而唯一有效语料、DUT 覆盖或缺陷发现下降，不算单独成功。

比较使用相同初始语料、预算与配置，并报告多次运行的差异；官方工具无法固定变异随机性时披露限制，不声称逐样本公平配对。输入修复改变状态分布，应保留可比的较弱修复/异常场景对照。任何 DUT 异常发生后不得回头修改已经施加的刺激来制造合法轨迹；按 1.10 排查本反例相关连接、规则、适配和环境问题，再判断组件内部缺陷。

#### 1.10.3 正确性与内部缺陷的确认门槛

生成成功、编译成功、能启动和已确认组件 bug 是不同结论。

准入原则：检查环境是否具备测试条件，不要求待测组件先证明自己没有 bug。无法建立有效环境时（如缺源码、连接遗漏、必要协议不支持），阻止相应常规运行并报告接入问题。有效环境下出现启动卡住、中断异常或握手违例时，保存轨迹并进入候选缺陷诊断，不能仅因异常就标记组件不受支持。暂时无法区分环境问题与组件问题时标记待诊断，保留证据；不据此宣称环境有效、组件有错或测试通过。

系统分别报告以下三种能力，不用“支持该组件”替代具体结论：

- 能组合：端口、协议、地址和连接满足已检查的约束；不据此声称实际运行或功能正确。
- 能运行：具备所需启动与交互环境，且有 CPU 执行指定测试程序的运行证据；结论限定于实际测试配置和场景。
- 能判错：针对具体行为，有明确规范、断言或参考模型作为判据；逐项说明可检查的性质、适用假设和无法检查的行为，不承诺组件全部内部功能均可判定。

例如，新外设能够连接总线并被 CPU 访问，但若缺少其计算功能的预期行为描述，只能检查已有判据覆盖的性质（如总线协议），不能声称已验证其全部内部功能。报告须分别列出三种能力的证据与缺口；缺少功能判据不能伪装成验证通过，运行成功也不能当成功能正确。自动组合与 fuzz 的最终目标不变，但每次实验必须明确能检查什么。

用户希望尽可能全面地连接和测试 CPU 及每个组件，并使最终确认的 bug 来自组件内部。生成阶段据此输出逐实例的功能覆盖清单：每项端口/功能路径、工作模式与必要交互、连接或导出的对象、使能/常量禁用/不支持状态、约束依据，以及由此失去的行为覆盖。端口全部有去向只证明处理完整，不能证明组件行为全部得到测试；禁止通过绑死关键端口换取“完整连接”的表面结论。

例如，CPU 的 external、software、timer、fast、NMI 中断入口，以及 debug request、fetch_enable 等分别列项。外设中断控制器只提供其声明的外部中断入口，不能代表其他中断类别或调试能力已经覆盖。其他入口需具备对应的通用功能连接或合法顶层导出契约；明确允许禁用时记录无效值及覆盖损失，必要功能不支持时报告缺口。未知端口不能用任意 fuzz 代替功能语义。外设列表同样分别标出 MMIO、外部引脚、各中断源、独立工作模式及主动访存需求。

首期全局单事务会限制并发与乱序行为，非 DMA 模式不覆盖 DMA，单上下文中断控制器不覆盖嵌套领取，多核/跨域能力仍未覆盖。这些是此前范围约束及本稿控制器提案带来的明确局限，不能将首期称为“完整行为测试”。最终扩大覆盖需逐项补足通用接口、互联、模式和环境能力并独立验证；本轮不撤销首期边界，也不扩展测试软件。

确认某个反例为组件内部 bug 前，须有针对该反例的证据排除相关接线、极性、地址译码、协议适配、控制器及刺激/检查环境错误，并在原始组件上保留或重放相同违例。结构审计和环境回归降低连接错误风险，但不是“环境永不出错”的保证；证据不足保留候选或未定位，不强行归为组件 bug，也不承诺穷尽所有行为。

1. profile 校验保证声明与物理接口一致，但不自动证明所有语义正确。
2. 结构审计独立提取实际连接；不能只比较生成器自己写出的两份清单。
3. 互联/适配/随机驱动/外部模型独立验证，故意改错时应能检出。
4. 系统验证 CPU 启动、存储器、MMIO、外部交互和选择的中断路径。
5. 发现失败后检查输入合法性、软件和检查器，再缩减与隔离复现。

已确认组件内部缺陷必须有：原始 RTL 身份、明确规范违例、合法前置状态和输入、可重复反例及充分归因证据。环境缺陷、profile 错误、软件/模型问题和未定位异常分别统计。

确认组件 bug 前，重新核对与失败相关的 profile 语义及其依据。软件、激励和检查器均由同一 profile 生成时，它们的一致结果不能独立证明该 profile 正确。例如，将写一清除误描述为读清除，会使生成的软件和检查器共享错误；必须核对相应规范或设计说明。缺少可靠语义依据时保留候选异常或未定位结论，不直接归因于组件内部。

有限仿真或有界证明不等于所有状态无错误，时限结论必须附带对端响应等假设。

### 1.11 最终验收场景

冻结生成器实现后，仅提交新的 RTL/profile/约束，完成：

- 首次输入 CPU + 已有外设。
- 已有 CPU + 首次输入外设。
- 首次输入 CPU + 首次输入外设。
- CPU 和外设均含特殊随机输入，顶层绑定和可重复驱动正确。
- 错误 profile、不支持协议和非法端口处理被准确拒绝。

名称变更和端口重排作为辅助测试，不能代替真实陌生设计。新设计使用已支持协议和执行后端时，不允许为了通过测试新增型号专用分支或手改顶层。

## 第二部分：怎样把现有 myfuzz 逐步转变成目标系统

### 2.1 现有系统、差距与复用原则

当前链路以已登记配置为起点：

```text
soc_matrix_smoke.cell_documents(config_path, mode)
 → load_cell_config / peripheral_records
 → build_spec + build_execution + build_contracts
 → build_soc_plan + compile_soc_stimulus
 → render_soc → 现有 builder/campaign
```

继续使用现有 interface_description、source_crawler、processor_execution、soc_plan、soc_fabric、target_adapters、soc_renderer、soc_stimulus 和 integration 模块。

当前障碍：固定矩阵限制、组件事实表、CPU/外设专用包装与程序选择、缺少统一特殊输入处理。迁移应把选择依据从“型号名称”转为“profile 声明的接口能力”，而不是仅允许任意字符串作为 CPU 名称。

#### 2.1.1 组合链路：已有基础与缺口

**错误响应验证：** 未映射访问、写 ROM 和违反已声明权限的请求按策略返回错误，不作为成功访问；背压下响应和归属保持正确，必要错误语义无法跨适配链表达时拒绝组合。已命中但暂不响应的目标不能被误判为地址未命中，不能通过伪造正常零数据或错误响应掩盖等待。
**存储器生成验证：** ROM/RAM 容量、地址、权限及实际连接符合请求；启动取指地址不在可执行区域、必要访问宽度不兼容、镜像格式不支持或加载越界时明确报错。无镜像与未初始化区域按显式规则处理，初始化记录与实际内容核对；这些检查不能代替 CPU 启动行为验证。
**首期范围验证：** 单核、同域且具有独立取指/数据接口的组合正确规划连接和必要仲裁；需要多核或跨域连接、复杂时钟切换的输入明确报告超出范围；复位契约不匹配时不能靠统一绑线通过检查。
**时钟复位验证：** 重新展开生成 RTL，核对统一顶层入口到组件的时钟/复位路径、实际极性与所需处理模块；必要处理缺失、连接错误或包装私自生成时钟应检出。特殊复位顺序不受支持时明确报告，不能靠任意延迟或仅反相通过契约检查；涉及释放时序的性质另验证处理模块行为，不能仅凭结构一致声称满足。
**外设范围验证：** MMIO 从设备可完成访问及所声明的外部交互和中断；必需 DMA 的配置明确拒绝；具有独立非 DMA 模式的组件按明确配置接入并报告测试范围，不能用无依据的 DMA 端口绑死代替能力检查。
**串行化验证：** 多主竞争、背压和响应等待场景中，检查单事务限制、已接受事务不丢失或重复、响应归属及必要 ID 映射正确；适配能力无法保持必要语义时明确拒绝。报告应说明该配置未覆盖多事务并发和乱序响应相关行为，不能仅凭串行测试通过声称并发覆盖完整。
**补充关键回归：** 非 AXI4 的统一访存端点不能被误拆成两个 OBI 接口；CPU xlen 与总线宽度不同必须按实际接口处理或精确拒绝；声明支持但缺少运行必需信号时拒绝；合法端口映射变化应改变执行身份，而不是沿用固定哈希。
**通过条件：** 无手改顶层即可生成；协议能力缺口精确拒绝。
**产物：** 通用包装、互联/地址计划及旧新对照证据。
