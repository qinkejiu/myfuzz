# myfuzz 系统总览、自动组合与 RFuzz 约束示例

> 文档版本：2026-09-09
>
> 本文对应分支 `feature/ibex-protocol-longrun` 的当前实现。文中把“协议已声明支持”“生成器可渲染”和“真实 RTL 矩阵已经跑过”分开说明，避免把三者混为一谈。

## 0. 先给结论

系统的核心思想是：CPU 和外设不按名称硬编码连接，而是各自提供一份“说明文件”。
CPU 的说明文件列出源码位置、顶层模块和真实端口；外设的说明文件列出模块、地址范围
和原生总线。组合器从源码中核对这些信息，再把 CPU 的 OBI/AXI 等接口转换成一个
内部统一的内存访问格式。RFuzz 的随机 bit 串仍然是唯一输入来源，约束转导器只修复
“必须满足 ISA/协议的位”，并维护有限状态、共享内存和超时。

系统需要以下几类说明，含义都是具体的：

| 说明 | 里面写什么 | 当前示例 |
| --- | --- | --- |
| CPU 接口说明 | CPU 源码位置、顶层模块、时钟/复位、取指端口、数据端口、中断端口的真实名字和方向。 | `configs/cpus/ibex/official_core_interface_description.json` |
| 外设连接说明 | 外设模块位置、地址范围、数据宽度、原生总线、需要编译的源码文件。 | `src/myfuzz/components/profiles/real_uart.json` 等 |
| 协议规则说明 | 一次读写需要哪些信号、信号的先后关系、哪些字段必须一致、最长等待多久。 | `src/myfuzz/protocols/plugins/*.json` |
| 测试配置 | ISA、启动地址、共享内存、可随机的中断/debug 输入和测试时长。 | `examples/real_ibex_rfuzz/input/ibex-scratch.json` |
| 生成结果 | 最终接线、输入 bit 的含义、源文件清单和约束逻辑。 | `generic_composition_top.sv`、`input_layout.json`、`sources.f` |

如果只是运行现成示例，通常只需要看两个输入：CPU 接口说明文件和示例配置文件；其余
规则由系统从源码和仓库中的协议/外设说明中生成。

### 0.1 最短操作流程

把整个系统当成“按插头形状自动接线”的工具即可：

1. 找到 CPU 的 HDL 源码，并在 CPU 接口说明文件中写出顶层模块、时钟/复位、取指和
   数据端口的实际名字。
2. 在测试配置中写明 ISA（例如 `RV32IMC`）、启动地址、哪些中断允许随机，以及取指
   和数据是否共享同一块测试内存。
3. 运行组合命令。系统会检查端口是否真的存在，并自动生成适配器、仲裁器、内存响应
   逻辑和顶层 SystemVerilog。
4. RFuzz 每周期给出一段随机 bit。系统只修改必须修改的 opcode/握手/依赖位，其余位
   继续保持随机，然后把生成的顶层交给 Verilator 运行。
5. 查看生成目录中的 `generic_composition_top.sv`（最终接线）和
   `input_layout.json`（一条 RFuzz 输入各 bit 的含义）。

外设也是同样的方式：外设说明文件告诉系统“模块在哪里、地址是多少、原生总线是哪种”，
系统再自动插入对应桥接模块。用户不需要为每个 CPU 手写一套新的顶层接线。

```text
CPU/外设源码 + 接口描述 + ISA/协议声明
                  │
                  ▼
        源码核对：核对真实端口、宽度、方向、时钟/复位
                  │
                  ▼
      生成接线施工图：接口组匹配、适配器、地址图、执行边界、输入布局
                  │
       ┌──────────┴──────────┐
       ▼                     ▼
  生成 generic_top       生成 RFuzz 契约转导器
  OBI/AXI/TL/APB 适配器    ISA 修复 + 协议 FSM + 共享内存
       │                     │
       └──────────┬──────────┘
                  ▼
        Verilator 真实 CPU/外设 RTL + live RFuzz
```

当前有两条相关但不同的执行路径：

1. **契约 RFuzz 路径**：真实 Ibex（或其他符合接口说明的 CPU）接到约束转导器，用
   随机周期驱动指令、内存响应和选定外部控制。当前示例中的固定寄存器测试目标在
   约束模式下被禁用，所以这条路径不是 UART/SPI/Timer 的功能验证。
2. **真实 CPU × 真实外设矩阵**：Ibex、CV32E40P、CV32E20、CVA6 分别接到真实 RAM、
   UART、SPI、Timer、GPIO RTL。CPU 侧先归一化为 beat 契约，外设侧再通过 TL-UL、
   AXI4-Lite 或 APB4 桥接。该矩阵是组合、完整源码集合、Verilator 语法/连接检查（lint）和短时钟连通测试（smoke）
   的证据，不等于每个外设寄存器都已被 RFuzz 功能访问。

## 1. 系统总体与协议支持

### 1.1 三层协议边界

| 层 | 当前内容 | 说明 |
| --- | --- | --- |
| 协议规则层 | `apb@3`、`apb@4`、`axi4@1`、`axi4-lite@1`、`obi@1`、`processor-memory-beat@1`、`ready-valid-memory@1`、`ready-valid-mmio@1`、`tl-ul@1`、`wishbone@classic` | 在 `src/myfuzz/protocols/plugins/*.json` 中描述字段、方向、能力上限、布尔投影动作和时序规则。这里列出的规则不等于每一种协议都有真实 RTL 外设桥。 |
| 通用生成器层 | APB3、APB4、Wishbone Classic、AXI4-Lite，以及测试 fixture 使用的有界单通道格式 | 可从 CPU/外设说明生成接线计划、顶层和 `sources.f`。新通用 renderer 当前不做共享多目标总线、CDC、Wishbone pipelining、完整 AXI4 burst/ID 路由或 OBI 原生路由；AXI4/OBI 有独立桥接测试。 |
| 真实 CPU/外设矩阵层 | CPU 侧 OBI/AXI → `processor-memory-beat@1`；外设侧 TL-UL（RAM）、AXI4-Lite（UART/SPI）、APB4（Timer/GPIO） | 这是当前真正接入并跑过真实 RTL 的路径。Ibex/CV32 使用 OBI 处理器边界，CVA6 使用 64 位边界；适配器由端点字段和协议选择，而不是 CPU 名称选择。 |

RTL 桥的共同本地边界是：

```text
valid, write, addr, wdata, be, rdata, ready, error
```

每个桥最多保持一个未完成事务，源端等待和目标端等待默认最多 16 个周期；超时会
产生确定性 error，不使用动态队列或无界计数器。

### 1.2 已实现的真实外设连接说明

`src/myfuzz/components/profiles/real_*.json` 中的外设说明都对外声明
`processor-memory-beat@1`，并给出真实 RTL 源文件列表。它们不是外设本身，而是告诉
组合器如何找到和连接外设的“小档案”：

| 外设连接说明 | 外设原生协议 | 实际桥接模块 |
| --- | --- | --- |
| `real_ram` / `real_ram64` | TL-UL | `real_tl_ram_target*.sv` + `tl_ul_mmio_bridge/target.sv` |
| `real_uart` / `real_uart64` | AXI4-Lite | `real_axi_uart_target*.sv` + `axi4_lite_mmio_bridge/target.sv` |
| `real_spi` / `real_spi64` | AXI4-Lite | `real_axi_spi_target*.sv` + `axi4_lite_mmio_bridge/target.sv` |
| `real_timer` / `real_timer64` | APB4 | `real_apb_timer_target*.sv` + `apb4_mmio_bridge/target.sv` |
| `real_gpio` / `real_gpio64` | APB4 | `real_apb_gpio_target*.sv` + `apb4_mmio_bridge/target.sv` |

64 位 CVA6 的 RAM 保留两个 32 位 lane；32 位 MMIO 目标只接受一个对齐的完整
lane，非法 lane 或 partial write 返回确定性错误。64 位 TL-UL bridge 特别保留了
`+4` 高 lane 的合法 32 位读写情况。

### 1.3 当前真实矩阵结果和边界

```text
seed=20260909：9/9 cases passed
CPU 出现次数：Ibex 2，CV32E40P 2，CV32E20 2，CVA6 3
每个 32 位真实外设说明至少复用 2 次
```

每个 case 都通过了自动组合、输出生成、Verilator 语法/连接检查和 2048 个时钟周期的
短测。矩阵中外部 IRQ 绑为零；CV32E40P 没有架构性的 OBI error pin，因此
当前只证明 no-error 路径，错误响应会 `$fatal`，生产接入仍需 core-specific
exception bridge。CVA6 的结果包含其 reset-time I-cache clear 所需的等待。

## 2. 自动组合是怎么做的

### 2.1 输入不是“CPU 名称”，而是五类事实

一个真实组合至少需要以下五类输入。它们分别回答“源码在哪里”“端口怎么接”“总线怎么
握手”“外设在哪里”和“本次测试允许什么”：

1. **CPU 接口说明文件**：例如
   `configs/cpus/ibex/official_core_interface_description.json`。它给出源码根、固定
   revision、顶层模块、源码文件/`include_roots`，以及每个端口属于取指、数据、时钟、
   复位还是中断，端口在源码中的实际名字是什么。
2. **被固定版本的 HDL 源码**：源码核对器会重新读取声明的硬件描述语言源码，核对端口是真实存在的，
   并记录方向、宽度、时钟/复位、连续/时序赋值和源码位置。说明文件中的 width、direction
   不是无条件信任的替代品。
3. **协议规则文件**：提供信号字段集合、能力上限、布尔修复动作和时序规则。文件位于
   `src/myfuzz/protocols/plugins/`。
4. **外设说明文件**：给出外设模块名、地址对齐/大小、真实源码路径、协议特性和
   参数范围。文件位于 `src/myfuzz/components/profiles/`。内置组件目录默认不自动加载
   `real_*.json`，真实矩阵显式选择这些真实外设，防止它们意外进入普通短测。
5. **ISA/测试约束**：例如 RV32IMC、共享内存区域、可随机化的
   外部字段、测试头和转导器上限。

### 2.2 组合步骤

```text
① 读取 CPU 接口说明 JSON
② 源码核对器分析完整源码集合并锁定版本
③ 根据接口组用途、协议和字段角色匹配 CPU 适配器
④ 将取指/数据端口归一化为统一内存访问格式 `processor-memory-beat@1`
⑤ 选择外设说明、检查协议能力、生成非重叠地址区间
⑥ 生成接线施工图、RFuzz 输入位布局、CPU 执行边界和内存访问后端
⑦ 生成顶层 generic_composition_top.sv 和 sources.f
⑧ 受约束模式额外编译约束转导器和 RFuzz 字节打包器
⑨ 运行 Verilator 语法/连接检查和有界短测；成功后才原子发布输出目录
```

关键点是第③步不看 `ibex`、`cva6` 这样的名字，而看字段。例如 Ibex 的
`instr_req_o/instr_gnt_i/instr_addr_o/instr_rvalid_i/instr_rdata_i` 会匹配 OBI
instruction master；data master 还必须找到 `we/wdata/be`。换一个实现同一组字段的
RISC-V CPU，可以复用同一适配器和 ISA/协议约束。

### 2.3 生成的文件及用途

典型输出目录包括：

```text
composition/
  composition_ir.json              # 组合计划：端口、适配器、地址、来源证据和 hash
  input_layout.json                # RFuzz 每周期各字段占哪些 bit
  processor_execution.v1.json      # CPU 执行边界和取指/数据发起端
  processor_backend.v1.json        # 统一内存访问格式的后端和超时规则
  contract_transducer.json         # ISA/协议/内存约束（仅受约束模式）
  contract_transducer.sv            # 上述约束的可综合 RTL
  rfuzz_input_transport.json        # raw bits ↔ 16-byte record 的打包规则
  rfuzz_input_transport.sv          # 字节到 bit 的边界模块
  generic_composition_top.sv        # 真正实例化 CPU、适配器、仲裁器和后端
  sources.f                          # 固定源码闭包和生成 RTL 的编译清单
```

组合发布程序会再次核对源码、检查地址重叠，并用临时目录原子发布；
因此端口事实不符、地址冲突或约束不完整时，不会留下“看似成功”的半成品顶层。

## 3. RFuzz 输入约束：随机来源不变，约束只修复必要关系

这里的“约束”不是把输入替换成固定程序，而是把一个 cycle 的随机 bit 分成几段：

```text
原始 RFuzz bits
  ├─ instruction selector/payload ──┐
  ├─ response choice/data           ├─ contract_transducer
  └─ 外部 IRQ/debug bits ───────────┘
       选择合法操作 → 布尔/模板修复 → 协议 FSM → 共享内存/响应
```

### 3.1 ISA：先选择操作，再保留随机性地修复编码

指令约束模块当前对 I/M/C 做合法编码验证：

1. 用 8 位 `selector` 在当前 ISA 支持的模板集合中均衡选择一个操作；
2. 用 `payload` 填充寄存器、立即数等自由字段；
3. 只把 opcode、funct、格式位和必要的非零约束写回模板固定值；
4. 对压缩指令再修复非零 `rd/rs2/imm` 等最小依赖；
5. `illegal_instruction=false` 时不选择非法模板，`true` 时才加入非法选项。

因此输入仍然能产生大量不同寄存器和立即数，而不是每次都得到同一条指令。当前
公开实现只验证 I/M/C；Zicsr、F/D/A/B 等未实现扩展不会被假装成合法指令。合法
**编码**也不保证一定有用：分支目标、权限或地址可能让 CPU trap。

例子：

| 原始字段 | 修复结果 |
| --- | --- |
| 32 位 `selector=0`、`payload=0xffffffff` | `ADDI`，结果 `0xffff8f93`（`addi x31,x31,-1`） |
| 16 位 `selector=0`、`payload=0` | `C.ADDI4SPN`，补齐非零立即数字段，结果 `0x0020` |

### 3.1.1 当前实际支持的 RISC-V 指令范围

这里的范围指“RFuzz 输入约束器能够主动选择并修复为合法编码”的范围，不是说 CPU
本身只能执行这些指令。

| ISA 配置 | 32 位指令模板 | 16 位压缩指令模板 | 说明 |
| --- | ---: | ---: | --- |
| RV32I | 42 | 0 | 基础整数运算、访存、分支、跳转、`FENCE`、基本系统指令 |
| RV32IM | 50 | 0 | RV32I 加乘法/除法/余数指令 |
| RV32IMC | 50 | 26 | 当前 Ibex 示例使用的范围 |
| RV64I | 54 | 0 | 增加 64 位访存和 word 运算 |
| RV64IM | 67 | 0 | 再增加 RV64 的乘除法 word 版本 |
| RV64IMC | 67 | 32 | 增加 RV64 压缩指令 |

32 位基础指令包括：

- 整数立即数：`ADDI`、`SLTI`、`SLTIU`、`XORI`、`ORI`、`ANDI`、`SLLI`、`SRLI`、`SRAI`；
- 寄存器整数运算：`ADD`、`SUB`、`SLL`、`SLT`、`SLTU`、`XOR`、`SRL`、`SRA`、`OR`、`AND`；
- RV32 访存：`LB`、`LH`、`LW`、`LBU`、`LHU`、`SB`、`SH`、`SW`；RV64 另有
  `LD`、`LWU`、`SD`；
- 分支：`BEQ`、`BNE`、`BLT`、`BGE`、`BLTU`、`BGEU`；
- 跳转和地址生成：`AUIPC`、`LUI`、`JAL`、`JALR`；
- 其他：`FENCE`、`ECALL`、`EBREAK`、`WFI`，以及按特权模式允许的 `MRET`/`SRET`；
- `M` 扩展：`MUL`、`MULH`、`MULHSU`、`MULHU`、`DIV`、`DIVU`、`REM`、`REMU`；
- RV64 word 运算：`ADDIW`、`SLLIW`、`SRLIW`、`SRAIW`、`ADDW`、`SLLW`、`SRLW`、
  `SUBW`、`SRAW`，以及 `MULW`、`DIVW`、`DIVUW`、`REMW`、`REMUW`。

RV32C 的 26 种压缩模板覆盖压缩加法、访存、分支、跳转、移位、逻辑运算、寄存器
搬运和栈访问；RV64C 再增加 `C.LD`、`C.SD`、`C.ADDIW`、`C.SUBW`、`C.ADDW`、
`C.LDSP`、`C.SDSP` 等变体。

当前没有主动生成或验证 `A` 原子、`F/D/Q` 浮点、`B` 位操作、`V` 向量、CSR 指令
（`CSRRW/CSRRS/CSRRC` 等）、`FENCE.I`、`SFENCE.VMA` 和自定义扩展。通用输入布局
可以把未知扩展当作完全原始的指令 bit，但受约束 RFuzz 执行只接受上表中的 I/M/C
集合；未知扩展不能被标记为“已经完成合法指令约束”。

最后，合法指令编码不等于一定能顺利执行：随机分支目标、访存地址、权限状态仍可能
使真实 CPU 产生 trap。当前约束器保证的是编码字段和跨周期内存/协议关系，不模拟完整
的寄存器语义、CSR 状态机或操作系统。

### 3.2 协议：状态机约束握手和进度

约束转导器目前执行统一内存访问格式 `processor-memory-beat@1`：

- 没有待处理请求时，`response_choice[0]` 或达到 `max_wait_cycles` 才接受请求；
- 有待处理请求时，`response_choice[1]` 或达到超时才返回响应；同一周期不接受替换
  请求；
- `rsp_ready` 在归一化投影中固定为 1；
- `response_choice[2]` 只有 `allow_error=true` 才会注入错误。本例显式使用
  `allow_error=false`；
- 默认 `max_wait_cycles=16`，所以随机输入不会制造无限挂起。

各原生协议的规则文件以相同方式表达依赖：AXI4-Lite 固定单 beat、`AW/W` 可独立到达但
必须在 `B` 响应前都握手；APB4 必须先 setup 再 access，`PSTRB` 对应 byte mask；
TL-UL 只允许 Get/PutFullData/PutPartialData 单 beat，A/D 通道受 bounded wait 约束。

### 3.3 共享内存：把同一条 bit 流用于连续周期

instruction/data domain 在配置中都绑定到 `main`，所以两类请求访问同一份按 beat
对齐的字节内存：

- 第一次 instruction read：用修复后的 ISA 指令初始化该 beat；
- 第一次 data read：用 raw `response_data` 初始化；
- CPU write：按 `be` 更新字节，并把 provenance 标为 `cpu_written`；
- data 生成的 beat 随后被 instruction fetch：返回 `provenance_error`，避免把任意
  数据误当指令；CPU 自己写入后再取指则允许精确返回；
- `be=0` 的空写不分配、不改变 provenance；容量到达 256 entries 时返回
  `capacity_error`，不驱逐旧数据；`test_begin` 清空本测试的内存和协议状态。

这就是“可以把随机 bit 切成连续周期使用”的实现：每个周期仍有新的随机 record，
但状态化内存保证跨周期的读写关系一致。

### 3.4 外部输入和固定控制

`randomizable_fields` 只允许绑定到接口描述中已经找到的物理端口；本例随机化 6 类
字段：software/timer/external interrupt、15 位 fast interrupt、NMI、debug request。
`boot_address`、`hart_id`、clock/reset、fetch enable、scan reset、完整性输入等由
`test_header` 或 `control_defaults` 固定。这样 RFuzz 不会通过一个“未连接的逻辑字段”
伪造覆盖点。

## 4. 具体示例：Ibex RV32IMC 从输入到顶层再到 RFuzz

### 4.1 输入文件

示例使用以下文件：

| 文件 | 作用 |
| --- | --- |
| `configs/cpus/ibex/official_core_interface_description.json` | CPU 接口说明文件：Ibex 源码 revision、`ibex_top`、源码闭包和 OBI/控制端口语义。 |
| `examples/real_ibex_rfuzz/input/ibex-scratch.json` | 选择 CPU 接口、ISA、总线协议、共享内存区域、测试头和可随机化外部字段。 |
| `src/myfuzz/protocols/plugins/obi.json` | OBI 协议规则文件：请求、授权、响应字段和握手关系。 |
| `src/myfuzz/protocols/plugins/processor_memory_beat.json` | 统一内存访问格式的请求/响应、字节使能和最大等待规则。 |
| `src/myfuzz/composition/contract_transducer.py` | 编译 ISA/协议约束并提供 Python 参考执行。 |
| `src/myfuzz/composition/transducer_rtl.py` | 生成和参考执行一致的 `contract_transducer.sv`。 |
| `examples/real_ibex_rfuzz/commands.sh` | compose、test、inspect、replay 的入口。 |

CPU 接口说明文件的核心片段如下（实际文件还包含完整 Ibex 源码列表）。其中
`endpoints` 不是网络接口，而是“按用途分组的一组端口”：`instruction` 是取指，
`data` 是读写数据；`fields` 列出这组端口里的请求、地址、数据和响应信号。

```json
{
  "schema_version": "interface_description.v1",
  "source": {
    "root": "third_party/rfuzz/upstream/ibex",
    "revision": "git:34b0705760ef3dfa00e99637432473d2be8f22f3",
    "top_module": "ibex_top",
    "files": ["rtl/ibex_pkg.sv", "rtl/ibex_top.sv", "..."]
  },
  "endpoints": [
    {
      "endpoint_id": "processor.instruction",
      "function": "instruction_memory_master",
      "protocol": ["obi", "1"],
      "fields": [
        {"role": "req", "aliases": ["instr_req_o"]},
        {"role": "gnt", "aliases": ["instr_gnt_i"]},
        {"role": "addr", "aliases": ["instr_addr_o"]},
        {"role": "rvalid", "aliases": ["instr_rvalid_i"]},
        {"role": "rdata", "aliases": ["instr_rdata_i"]},
        {"role": "error", "aliases": ["instr_err_i"]}
      ]
    },
    {
      "endpoint_id": "processor.data",
      "function": "data_memory_master",
      "protocol": ["obi", "1"],
      "fields": [
        {"role": "req", "aliases": ["data_req_o"]},
        {"role": "gnt", "aliases": ["data_gnt_i"]},
        {"role": "addr", "aliases": ["data_addr_o"]},
        {"role": "we", "aliases": ["data_we_o"]},
        {"role": "wdata", "aliases": ["data_wdata_o"]},
        {"role": "be", "aliases": ["data_be_o"]},
        {"role": "rvalid", "aliases": ["data_rvalid_i"]},
        {"role": "rdata", "aliases": ["data_rdata_i"]}
      ]
    }
  ]
}
```

这里的 `source` 是“去哪里找 CPU”，`top_module` 是“从哪个模块开始编译”，
`processor.instruction`/`processor.data` 是“哪一组端口负责取指和数据访问”，
`aliases` 是源码中实际出现的端口名。`schema_version` 只是这份说明文件的格式版本。

示例配置文件的关键部分如下：

```json
{
  "interface": "configs/cpus/ibex/official_core_interface_description.json",
  "isa": "rv32imc",
  "isa_contract": {
    "xlen": 32,
    "extensions": ["I", "M", "C"],
    "privilege_modes": ["M"],
    "instruction_alignment": 2
  },
  "protocol": ["obi", "1"],
  "input_mode": "contract_transducer",
  "memory_domains": {
    "instruction_memory_master": "main",
    "data_memory_master": "main"
  },
  "test_header": {
    "reset_cycles": 2,
    "execution_cycles": 200,
    "boot_address": 128,
    "hart_id": 0,
    "illegal_instruction": false
  },
  "randomizable_fields": [
    "processor.interrupts:software_interrupt",
    "processor.interrupts:timer_interrupt",
    "processor.interrupts:external_interrupt",
    "processor.interrupts:fast_interrupt",
    "processor.execution_controls:nonmaskable_interrupt",
    "processor.debug:request"
  ]
}
```

这里的 `isa_contract` 说明允许哪些 RISC-V 指令，`memory_domains` 把取指和数据访问
放到同一个名为 `main` 的共享内存，`randomizable_fields` 列出允许 RFuzz 改变的
中断/debug 输入；`control_defaults`（完整文件中还有）则固定不应随机的控制脚。

`personality` 字段仍可记录来源模块，但在本 constrained 示例中只是元数据；实际
固定 target 被禁用，内存响应来自契约转导器。

### 4.4 本例的精确 RFuzz cycle layout

`contract_transducer.json` 和 `input_layout.json` 是权威文件。本例的 raw cycle 共
104 位，16 字节传输；大端 payload 位于 16 字节的高 104 位，末尾 24 位 padding
输入忽略、编码置零。

| 字段 | raw bit 区间 | 宽度 | 来源/作用 |
| --- | ---: | ---: | --- |
| `instruction_selector` | `[7:0]` | 8 | 低半字指令模板选择 |
| `instruction_selector_1` | `[15:8]` | 8 | 高半字指令模板选择 |
| `instruction_payload` | `[47:16]` | 32 | 指令自由位/立即数来源 |
| `instruction_compressed` | `[48]` | 1 | 是否按 16 位槽修复 |
| `response_choice` | `[51:49]` | 3 | 接受、响应、错误选择 |
| `response_data` | `[83:52]` | 32 | 数据读的随机初值 |
| `external.processor.debug:request` | `[84]` | 1 | `debug_req_i` |
| `external.processor.execution_controls:nonmaskable_interrupt` | `[85]` | 1 | `irq_nm_i` |
| `external.processor.interrupts:external_interrupt` | `[86]` | 1 | `irq_external_i` |
| `external.processor.interrupts:fast_interrupt` | `[101:87]` | 15 | `irq_fast_i` |
| `external.processor.interrupts:software_interrupt` | `[102]` | 1 | `irq_software_i` |
| `external.processor.interrupts:timer_interrupt` | `[103]` | 1 | `irq_timer_i` |

布局身份是：

```text
raw_width   = 104
byte_count  = 16
padding     = 24 bits
layout_hash = sha256:d23dd16f9cd98973407167d90bd3431d82c7736bf2519eef8c47934fad111d8a
contract_hash = sha256:99bc895ab8c8f94ac66e8af4043b96e275dae5ec90a683d1df4cdf0640d5e6b1
```

### 4.5 一个具体的输入约束实例

假设 RFuzz 在 CPU 发出一次 instruction request 的周期给出：

```text
instruction_selector   = 0x00
instruction_selector_1 = 0x00
instruction_payload    = 0xffffffff
instruction_compressed = 0
response_choice        = 0b001   # bit0=1：接受当前请求
response_data          = 0x00000000
所有 external 字段    = 0
```

按 `raw = Σ(field_value << raw_lo)` 打包，raw 数值为
`0x2ffffffff0000`，16 字节大端记录为：

```text
00000000000000000002ffffffff0000
```

这一个周期只完成请求接受。下一周期把 `response_choice=0b010`（bit1=1）后，
转导器才返回该请求的数据。若这是 boot address 的首次 instruction read，ISA
转导器选择第一个 32 位模板 `ADDI`，固定 opcode/funct 等结构位，并保留 payload
中允许随机的寄存器/立即数字段，结果是：

```text
payload       = 0xffffffff
合法操作      = ADDI
修复后的指令  = 0xffff8f93       # addi x31, x31, -1
```

若下一周期仍访问同一 beat，内存返回已经保存的指令，而不会重新随机生成。若 CPU
先对该 beat 做 byte-enable 写入，之后取指会返回 CPU 写入的字节；若这个 beat 原先
由 data read 随机初始化，则 instruction fetch 会得到 `provenance_error`，这正是
跨周期依赖约束，而不是丢弃所有随机数据。

## 5. 扩展一个新 CPU 或外设时要提供什么

### 新 CPU

1. 固定源码版本和完整 source/include 文件集合；
2. 添加一份 CPU 接口说明 JSON，声明
   clock/reset、取指/数据端口、协议和源码中的真实端口名；
3. 若使用 OBI/AXI 等已知协议，复用相应适配器；若是新协议，先添加协议规则文件，
   再实现桥；
4. 提供 ISA 规则。只有实现了合法编码验证的 ISA 才能进入受约束指令生成；未知扩展
   可以先走原始 bit 模式，但不能声称已完成合法指令验证；
5. 运行组合规划器、生成顶层、Verilator 语法/连接检查和短测，再加入真实矩阵。

### 新外设

1. 提供一份外设说明 JSON，写清模块名、真实源码路径、地址范围和原生协议；
2. 对外暴露 `processor-memory-beat@1`，或实现从该契约到外设原生协议的桥；
3. 明确地址对齐、大小、byte-enable、错误和 reset/flush 行为；
4. 用同一份外设说明参与多个 CPU 组合，检查地址图、lint 和请求/响应活动；
5. 若需要 RFuzz 功能覆盖，再把真实外设路径接入 live transducer；当前矩阵的
   约束模式短测与真实外设短测是有意分开的两种证据。
