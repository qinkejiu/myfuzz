# myfuzz 系统总览、自动组合与 RFuzz 约束示例

> 文档版本：2026-09-09
>
> 本文对应分支 `feature/ibex-protocol-longrun` 的当前实现。文中把“协议已声明支持”“生成器可渲染”和“真实 RTL 矩阵已经跑过”分开说明，避免把三者混为一谈。

## 0. 先给结论

系统的核心思想是：CPU 和外设不按名称硬编码连接，而是各自提供一份“说明文件”。
CPU 的说明文件列出源码位置、顶层模块和真实端口；外设的说明文件列出模块、地址范围
和原生总线。组合器从源码中核对这些信息，再把 CPU 的 OBI/AXI 等接口转换成一个
内部统一的内存访问格式。RFuzz 的随机 bit 串仍然是唯一输入来源，约束转导器只修复
“必须满足 ISA/协议的位”，并维护有限状态、共享内存和超时。

系统需要以下几类说明，含义都是具体的：

| 说明         | 里面写什么                                                   | 当前示例                                                     |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| CPU 接口说明 | CPU 源码位置、顶层模块、时钟/复位、取指端口、数据端口、中断端口的真实名字和方向。 | `configs/cpus/ibex/official_core_interface_description.json` |
| 外设连接说明 | 外设模块位置、地址范围、数据宽度、原生总线、需要编译的源码文件。 | `src/myfuzz/components/profiles/real_uart.json` 等           |
| 协议规则说明 | 一次读写需要哪些信号、信号的先后关系、哪些字段必须一致、最长等待多久。 | `src/myfuzz/protocols/plugins/*.json`                        |
| 测试配置     | ISA、启动地址、共享内存、可随机的中断/debug 输入和测试时长。 | `examples/real_ibex_rfuzz/input/ibex-scratch.json`           |
| 生成结果     | 最终接线、输入 bit 的含义、源文件清单和约束逻辑。            | `generic_composition_top.sv`、`input_layout.json`、`sources.f` |

如果只是运行现成示例，通常只需要看两个输入：CPU 接口说明文件和示例配置文件；其余
规则由系统从源码和仓库中的协议/外设说明中生成。

### 0.1 最短操作流程

把整个系统当成“按插头形状自动接线”的工具即可：

1. 找到 CPU 的 HDL 源码，并在 CPU 接口说明文件中写出顶层模块、时钟/复位、取指和
   数据端口的实际名字。
2. 在测试配置中写明 ISA（例如 `RV32IMC`）、启动地址、哪些中断允许随机，以及取指
   和数据是否共享同一块测试内存。
3. 运行组合命令。系统会检查端口是否真的存在，并自动生成适配器、仲裁器、内存响应
   逻辑和顶层 SystemVerilog。
4. RFuzz 每周期给出一段随机 bit。系统只修改必须修改的 opcode/握手/依赖位，其余位
   继续保持随机，然后把生成的顶层交给 Verilator 运行。
5. 查看生成目录中的 `generic_composition_top.sv`（最终接线）和
   `input_layout.json`（一条 RFuzz 输入各 bit 的含义）。

外设也是同样的方式：外设说明文件告诉系统“模块在哪里、地址是多少、原生总线是哪种”，
系统再自动插入对应桥接模块。用户不需要为每个 CPU 手写一套新的顶层接线。

```text
CPU/外设源码 + 接口描述 + ISA/协议声明
                  │
                  ▼
        源码核对：核对真实端口、宽度、方向、时钟/复位
                  │
                  ▼
      生成接线施工图：接口组匹配、适配器、地址图、执行边界、输入布局
                  │
       ┌──────────┴──────────┐
       ▼                     ▼
  生成 generic_top       生成 RFuzz 契约转导器
  OBI/AXI/TL/APB 适配器    ISA 修复 + 协议 FSM + 共享内存
       │                     │
       └──────────┬──────────┘
                  ▼
        Verilator 真实 CPU/外设 RTL + live RFuzz
```

## 2. 自动组合是怎么做的

### 2.1 输入不是“CPU 名称”，而是五类事实

一个真实组合至少需要以下五类输入。它们分别回答“源码在哪里”“端口怎么接”“总线怎么
握手”“外设在哪里”和“本次测试允许什么”：

1. **CPU 接口说明文件**：例如
   `configs/cpus/ibex/official_core_interface_description.json`。它给出源码根、固定
   revision、顶层模块、源码文件/`include_roots`，以及每个端口属于取指、数据、时钟、
   复位还是中断，端口在源码中的实际名字是什么。
2. **被固定版本的 HDL 源码**：源码核对器会重新读取声明的硬件描述语言源码，核对端口是真实存在的，
   并记录方向、宽度、时钟/复位、连续/时序赋值和源码位置。说明文件中的 width、direction
   不是无条件信任的替代品。
3. **协议规则文件**：提供信号字段集合、能力上限、布尔修复动作和时序规则。文件位于
   `src/myfuzz/protocols/plugins/`。
4. **外设说明文件**：给出外设模块名、地址对齐/大小、真实源码路径、协议特性和
   参数范围。文件位于 `src/myfuzz/components/profiles/`。内置组件目录默认不自动加载
   `real_*.json`，真实矩阵显式选择这些真实外设，防止它们意外进入普通短测。
5. **ISA/测试约束**：例如 RV32IMC、共享内存区域、可随机化的
   外部字段、测试头和转导器上限。

### 2.2 组合步骤

```text
① 读取 CPU 接口说明 JSON
② 源码核对器分析完整源码集合并锁定版本
③ 根据接口组用途、协议和字段角色匹配 CPU 适配器
④ 将取指/数据端口归一化为统一内存访问格式 `processor-memory-beat@1`
⑤ 选择外设说明、检查协议能力、生成非重叠地址区间
⑥ 生成接线施工图、RFuzz 输入位布局、CPU 执行边界和内存访问后端
⑦ 生成顶层 generic_composition_top.sv 和 sources.f
⑧ 受约束模式额外编译约束转导器和 RFuzz 字节打包器
⑨ 运行 Verilator 语法/连接检查和有界短测；成功后才原子发布输出目录
```

### 2.3 生成目录：每个文件是什么、什么时候看

组合命令成功后，系统会生成一个目录。这个目录不是让用户继续手工填写的配置，而是
“自动接线的结果”和“这次测试实际使用的输入规则”。以真实 Ibex 受约束运行结果为例：

```text
runs/examples/contract-rfuzz-final-replay/sim/
├── composition/                 # 自动接线和编译所需的全部文件
├── test_header.json              # 本次测试固定的启动/复位参数
├── runtime_layout.json           # 运行时真正采用的 RFuzz 位布局
└── runtime_transport.json        # 运行时真正采用的字节打包方式
```

可以把 `composition/` 理解成一张“施工包”：其中既有给人检查的清单，也有给
Verilator 编译的 SystemVerilog。下面的文件名保持不变，但含义用直白的话说明：
文件名中的 `ir`、`v1`、`raw` 只是内部格式或版本标记，阅读时不需要先理解这些缩写。

| 文件 | 它实际回答的问题 | 什么时候看 |
| --- | --- | --- |
| `composition_ir.json` | “这次到底接了谁？”列出 CPU、外设、适配器、地址区间、中断连接、源码来源和校验值。 | 想确认选中了哪个 CPU/外设，或检查地址是否冲突时。 |
| `input_layout.json` | “RFuzz 每一位输入送到哪里？”列出每周期的字段、位区间、宽度和总位数。 | 想知道随机 bit 如何变成指令选择、内存响应或中断时。 |
| `processor_execution.v1.json` | “CPU 的取指口和数据口分别怎么接？”记录每一路端口使用的协议适配器、宽度和方向。 | 换 CPU 或怀疑端口接错时。 |
| `processor_backend.v1.json` | “CPU 发出一次读写后由谁响应？”记录取指/数据两路如何仲裁、地址如何分发、未映射地址和超时如何处理。 | 想理解内存响应、等待周期或错误响应时。 |
| `contract_transducer.json` | “约束器准备修复什么？”记录 ISA 合法指令范围、协议握手、共享内存容量和最大等待周期。 | 受约束模式下，想检查哪些随机字段会被修复时。 |
| `contract_transducer.sv` | “约束器在硬件中怎样执行？”是上一文件对应的可编译 RTL，不是 Python 模拟结果。 | 想看实际约束逻辑，或 Verilator 报错时。 |
| `rfuzz_input_transport.json` | “一条 RFuzz 记录怎样装进输入总线？”记录 raw bit 的总宽度、字节顺序、padding 和 16 字节记录格式。 | 自己写 RFuzz 客户端或复现输入时。 |
| `rfuzz_input_transport.sv` | “字节怎样变成顶层的 bit 总线？”是测试平台与顶层之间的打包边界，不负责决定哪条指令合法。 | 排查输入位序、大小端或 padding 问题时。 |
| `generic_composition_top.sv` | “最终的硬件接线是什么？”真正实例化 CPU、协议适配器、仲裁器、内存后端、约束器或真实外设。 | 想看最终连线，或需要 Verilator 编译顶层时。 |
| `sources.f` | “编译时到底用了哪些源码？”列出固定版本的 CPU/外设 RTL、适配器、桥、约束器和顶层文件。 | 想复现编译，或核对是否误用了另一份源码时。 |

外层三个运行文件也有明确分工：`test_header.json` 保存启动地址、复位周期、执行周期、
hart id 和相关校验值；`runtime_layout.json` 与 `runtime_transport.json` 是测试程序
真正读到的布局和打包规则。它们用于复现，不能替代 `generic_composition_top.sv`。

执行 `test` 以后，目录中还可能出现以下运行产物：

| 文件/目录 | 直白含义 |
| --- | --- |
| `live_tb.sv` | 本次短测使用的测试平台：产生时钟/复位，读取 RFuzz 输入并收集反馈。 |
| `compiler.log` | Verilator 编译的完整日志；端口、语法或缺少源码时先看这里。 |
| `build/report.json` | 编译和短测的机器可读结果。 |
| `build/checkpoint.json` | 测试在何时、用什么输入和 hash 完成的检查点。 |
| `artifact_provenance.json` | 输出由哪个命令、哪一版源码和哪些校验值生成。 |
| `observations.json` | 测试期间 CPU/内存/协议活动的反馈记录。 |
| `obj_dir/` | Verilator 的编译缓存和可执行文件；它是构建产物，不是需要阅读或修改的输入。 |

按目的查文件，可以直接这样做：

```text
看最终接线       → generic_composition_top.sv
看 CPU/外设选择  → composition_ir.json
看取指/数据适配  → processor_execution.v1.json
看仲裁/地址/超时  → processor_backend.v1.json
看 RFuzz 位含义  → input_layout.json + rfuzz_input_transport.json
看 ISA/协议修复  → contract_transducer.json（受约束模式才有）
复现一次测试      → test_header.json + runtime_*.json + sources.f
```

一条输入在这些文件中的流向是：RFuzz 字节先按 `rfuzz_input_transport.json` 还原为
周期 bit；`generic_composition_top.sv` 把它送入 CPU 和约束器；CPU 发出的取指/数据
请求经适配器变成统一的 `processor-memory-beat@1`；后端按地址和内存状态返回响应。
因此 `input_layout.json` 解释“输入是什么”，`processor_execution.v1.json` 解释“CPU
怎么接”，`generic_composition_top.sv` 才是“线已经怎样连起来”。

有两个容易混淆的边界：没有使用 `--constrained` 时，不会生成
`contract_transducer.json/.sv`，因为此时没有 ISA 合法化转导器；受约束的 CPU-only
示例由转导器提供内存响应，所以顶层不会同时实例化 UART/SPI/Timer/GPIO。真实 CPU ×
真实外设矩阵则会把外设桥和外设源码列入 `generic_composition_top.sv` 与 `sources.f`。

最后，发布程序会把这些文件先写入临时目录，重新核对端口、源码校验值和地址重叠，检查
通过后才一次性改名为目标目录。任一步失败都会删除临时目录，因此不会留下“文件看似齐全
但实际上没有检查过”的半成品组合。

## 3. RFuzz 输入约束：随机来源不变，约束只修复必要关系

这里的“约束”不是把输入替换成固定程序，而是把一个 cycle 的随机 bit 分成几段：

```text
原始 RFuzz bits
  ├─ instruction selector/payload ──┐
  ├─ response choice/data           ├─ contract_transducer
  └─ 外部 IRQ/debug bits ───────────┘
       选择合法操作 → 布尔/模板修复 → 协议 FSM → 共享内存/响应
```

### 3.1 ISA：先选择操作，再保留随机性地修复编码

指令约束模块当前对 I/M/C 做合法编码验证：

1. 用 8 位 `selector` 在当前 ISA 支持的模板集合中均衡选择一个操作；
2. 用 `payload` 填充寄存器、立即数等自由字段；
3. 只把 opcode、funct、格式位和必要的非零约束写回模板固定值；
4. 对压缩指令再修复非零 `rd/rs2/imm` 等最小依赖；
5. `illegal_instruction=false` 时不选择非法模板，`true` 时才加入非法选项。

因此输入仍然能产生大量不同寄存器和立即数，而不是每次都得到同一条指令。当前
公开实现只验证 I/M/C；Zicsr、F/D/A/B 等未实现扩展不会被假装成合法指令。合法
**编码**也不保证一定有用：分支目标、权限或地址可能让 CPU trap。

### 3.1.1 当前实际支持的 RISC-V 指令范围

这里的范围指“RFuzz 输入约束器能够主动选择并修复为合法编码”的范围，不是说 CPU
本身只能执行这些指令。

| ISA 配置 | 32 位指令模板 | 16 位压缩指令模板 | 说明                                                  |
| -------- | ------------: | ----------------: | ----------------------------------------------------- |
| RV32I    |            42 |                 0 | 基础整数运算、访存、分支、跳转、`FENCE`、基本系统指令 |
| RV32IM   |            50 |                 0 | RV32I 加乘法/除法/余数指令                            |
| RV32IMC  |            50 |                26 | 当前 Ibex 示例使用的范围                              |
| RV64I    |            54 |                 0 | 增加 64 位访存和 word 运算                            |
| RV64IM   |            67 |                 0 | 再增加 RV64 的乘除法 word 版本                        |
| RV64IMC  |            67 |                32 | 增加 RV64 压缩指令                                    |

32 位基础指令包括：

- 整数立即数：`ADDI`、`SLTI`、`SLTIU`、`XORI`、`ORI`、`ANDI`、`SLLI`、`SRLI`、`SRAI`；
- 寄存器整数运算：`ADD`、`SUB`、`SLL`、`SLT`、`SLTU`、`XOR`、`SRL`、`SRA`、`OR`、`AND`；
- RV32 访存：`LB`、`LH`、`LW`、`LBU`、`LHU`、`SB`、`SH`、`SW`；RV64 另有
  `LD`、`LWU`、`SD`；
- 分支：`BEQ`、`BNE`、`BLT`、`BGE`、`BLTU`、`BGEU`；
- 跳转和地址生成：`AUIPC`、`LUI`、`JAL`、`JALR`；
- 其他：`FENCE`、`ECALL`、`EBREAK`、`WFI`，以及按特权模式允许的 `MRET`/`SRET`；
- `M` 扩展：`MUL`、`MULH`、`MULHSU`、`MULHU`、`DIV`、`DIVU`、`REM`、`REMU`；
- RV64 word 运算：`ADDIW`、`SLLIW`、`SRLIW`、`SRAIW`、`ADDW`、`SLLW`、`SRLW`、
  `SUBW`、`SRAW`，以及 `MULW`、`DIVW`、`DIVUW`、`REMW`、`REMUW`。

RV32C 的 26 种压缩模板覆盖压缩加法、访存、分支、跳转、移位、逻辑运算、寄存器
搬运和栈访问；RV64C 再增加 `C.LD`、`C.SD`、`C.ADDIW`、`C.SUBW`、`C.ADDW`、
`C.LDSP`、`C.SDSP` 等变体。

当前没有主动生成或验证 `A` 原子、`F/D/Q` 浮点、`B` 位操作、`V` 向量、CSR 指令
（`CSRRW/CSRRS/CSRRC` 等）、`FENCE.I`、`SFENCE.VMA` 和自定义扩展。通用输入布局
可以把未知扩展当作完全原始的指令 bit，但受约束 RFuzz 执行只接受上表中的 I/M/C
集合；未知扩展不能被标记为“已经完成合法指令约束”。

最后，合法指令编码不等于一定能顺利执行：随机分支目标、访存地址、权限状态仍可能
使真实 CPU 产生 trap。当前约束器保证的是编码字段和跨周期内存/协议关系，不模拟完整
的寄存器语义、CSR 状态机或操作系统。

### 3.2 协议：状态机约束握手和进度

约束转导器目前执行统一内存访问格式 `processor-memory-beat@1`：

- 没有待处理请求时，`response_choice[0]` 或达到 `max_wait_cycles` 才接受请求；
- 有待处理请求时，`response_choice[1]` 或达到超时才返回响应；同一周期不接受替换
  请求；
- `rsp_ready` 在归一化投影中固定为 1；
- `response_choice[2]` 只有 `allow_error=true` 才会注入错误。本例显式使用
  `allow_error=false`；
- 默认 `max_wait_cycles=16`，所以随机输入不会制造无限挂起。

各原生协议的规则文件以相同方式表达依赖：AXI4-Lite 固定单 beat、`AW/W` 可独立到达但
必须在 `B` 响应前都握手；APB4 必须先 setup 再 access，`PSTRB` 对应 byte mask；
TL-UL 只允许 Get/PutFullData/PutPartialData 单 beat，A/D 通道受 bounded wait 约束。

### 3.3 共享内存：把同一条 bit 流用于连续周期

instruction/data domain 在配置中都绑定到 `main`，所以两类请求访问同一份按 beat
对齐的字节内存：

- 第一次 instruction read：用修复后的 ISA 指令初始化该 beat；
- 第一次 data read：用 raw `response_data` 初始化；
- CPU write：按 `be` 更新字节，并把 provenance 标为 `cpu_written`；
- data 生成的 beat 随后被 instruction fetch：返回 `provenance_error`，避免把任意
  数据误当指令；CPU 自己写入后再取指则允许精确返回；
- `be=0` 的空写不分配、不改变 provenance；容量到达 256 entries 时返回
  `capacity_error`，不驱逐旧数据；`test_begin` 清空本测试的内存和协议状态。

这就是“可以把随机 bit 切成连续周期使用”的实现：每个周期仍有新的随机 record，
但状态化内存保证跨周期的读写关系一致。

### 3.4 外部输入和固定控制

`randomizable_fields` 只允许绑定到接口描述中已经找到的物理端口；本例随机化 6 类
字段：software/timer/external interrupt、15 位 fast interrupt、NMI、debug request。
`boot_address`、`hart_id`、clock/reset、fetch enable、scan reset、完整性输入等由
`test_header` 或 `control_defaults` 固定。这样 RFuzz 不会通过一个“未连接的逻辑字段”
伪造覆盖点。

### 4.4 本例的精确 RFuzz cycle layout

`contract_transducer.json` 和 `input_layout.json` 是权威文件。本例的 raw cycle 共
104 位，16 字节传输；大端 payload 位于 16 字节的高 104 位，末尾 24 位 padding
输入忽略、编码置零。

| 字段                                                         | raw bit 区间 | 宽度 | 来源/作用             |
| ------------------------------------------------------------ | -----------: | ---: | --------------------- |
| `instruction_selector`                                       |      `[7:0]` |    8 | 低半字指令模板选择    |
| `instruction_selector_1`                                     |     `[15:8]` |    8 | 高半字指令模板选择    |
| `instruction_payload`                                        |    `[47:16]` |   32 | 指令自由位/立即数来源 |
| `instruction_compressed`                                     |       `[48]` |    1 | 是否按 16 位槽修复    |
| `response_choice`                                            |    `[51:49]` |    3 | 接受、响应、错误选择  |
| `response_data`                                              |    `[83:52]` |   32 | 数据读的随机初值      |
| `external.processor.debug:request`                           |       `[84]` |    1 | `debug_req_i`         |
| `external.processor.execution_controls:nonmaskable_interrupt` |       `[85]` |    1 | `irq_nm_i`            |
| `external.processor.interrupts:external_interrupt`           |       `[86]` |    1 | `irq_external_i`      |
| `external.processor.interrupts:fast_interrupt`               |   `[101:87]` |   15 | `irq_fast_i`          |
| `external.processor.interrupts:software_interrupt`           |      `[102]` |    1 | `irq_software_i`      |
| `external.processor.interrupts:timer_interrupt`              |      `[103]` |    1 | `irq_timer_i`         |

布局身份是：

```text
raw_width   = 104
byte_count  = 16
padding     = 24 bits
layout_hash = sha256:d23dd16f9cd98973407167d90bd3431d82c7736bf2519eef8c47934fad111d8a
contract_hash = sha256:99bc895ab8c8f94ac66e8af4043b96e275dae5ec90a683d1df4cdf0640d5e6b1
```

### 4.5 一个具体的输入约束实例

假设 RFuzz 在 CPU 发出一次 instruction request 的周期给出：

```text
instruction_selector   = 0x00
instruction_selector_1 = 0x00
instruction_payload    = 0xffffffff
instruction_compressed = 0
response_choice        = 0b001   # bit0=1：接受当前请求
response_data          = 0x00000000
所有 external 字段    = 0
```

按 `raw = Σ(field_value << raw_lo)` 打包，raw 数值为
`0x2ffffffff0000`，16 字节大端记录为：

```text
00000000000000000002ffffffff0000
```

这一个周期只完成请求接受。下一周期把 `response_choice=0b010`（bit1=1）后，
转导器才返回该请求的数据。若这是 boot address 的首次 instruction read，ISA
转导器选择第一个 32 位模板 `ADDI`，固定 opcode/funct 等结构位，并保留 payload
中允许随机的寄存器/立即数字段，结果是：

```text
payload       = 0xffffffff
合法操作      = ADDI
修复后的指令  = 0xffff8f93       # addi x31, x31, -1
```

若下一周期仍访问同一 beat，内存返回已经保存的指令，而不会重新随机生成。若 CPU
先对该 beat 做 byte-enable 写入，之后取指会返回 CPU 写入的字节；若这个 beat 原先
由 data read 随机初始化，则 instruction fetch 会得到 `provenance_error`，这正是
跨周期依赖约束，而不是丢弃所有随机数据。

## 5. 增加新 CPU 或外设：能否直接接入、需要准备什么

这一节回答一个实际问题：拿来一个新的 RISC-V CPU 或一个新的 UART/Timer 类外设后，
是不是只填一个名字就能自动组合？答案是：不能只填名字，但也不需要为每个组合手写
顶层。系统需要先确认“真实源码、真实端口和协议行为”三件事，然后才能复用已有适配器
和测试流程。

### 5.1 先判断“直接接入”还是“需要加桥”

| 要检查的事实 | 可以直接复用什么 | 不满足时会怎样 |
| --- | --- | --- |
| CPU 有时钟、复位、取指访问和数据访问端口 | CPU 适配器、取指/数据仲裁器和统一内存后端 | 缺少取指或数据端口，不能作为处理器组合。 |
| 端口字段和已有协议一致，例如 OBI 的请求/授权/响应字段 | 已有 OBI/AXI 等适配器 | 字段不全、方向或宽度不一致，组合器拒绝发布。 |
| 外设使用当前已有的 AXI4-Lite、APB4、TL-UL 等总线 | 对应总线桥，再转为 `processor-memory-beat@1` | 新总线没有桥，先实现桥和桥的时序测试。 |
| CPU 的 ISA 在当前合法指令范围内 | 受约束模式可以选择并修复合法指令 | 新扩展只能先使用原始 bit 输入，不能宣称已完成该扩展的约束。 |
| 源码文件、include 目录和固定版本齐全 | 完整源码编译和版本校验 | 源码不完整时，系统不会生成“看起来能用”的顶层。 |

这里的“协议相同”不是看 CPU 的品牌或模块名，而是看端口字段的意义。例如，另一个
CPU 即使不叫 Ibex，只要它也提供请求、地址、授权、响应数据等同样的 OBI 字段，就可以
复用同一类适配器。反过来，名字相近但字段语义不同的端口不能强行连接。

### 5.2 增加一个新 CPU 至少要准备四类资料

#### ① 完整且固定版本的 CPU 源码

需要给出顶层模块依赖的全部 Verilog/SystemVerilog 文件、include 目录、宏定义和固定
版本号。系统会重新打开这些文件，核对顶层模块确实存在，不能只相信说明文件里写的一行
路径。

#### ② 一份 CPU 接口说明文件

这份文件要用真实源码中的名字说明：

- 时钟和复位端口，以及复位有效电平；
- 取指端口：请求、地址、授权/完成、返回指令、错误；
- 数据端口：请求、读写方向、地址、写数据、字节使能、返回数据、完成和错误；
- 中断、debug、启动地址等外部控制端口；
- 每个端口的方向和位宽，以及它属于取指还是数据访问。

这份说明不是让组合器猜 CPU，而是告诉它“源码中的哪一组脚完成什么工作”。端口缺失、
同一用途有多个候选、宽度不一致或复位含义不清时，会在生成顶层之前报错。

#### ③ ISA 和测试配置

要写清 XLEN、启用的扩展（例如 RV32IMC）、指令对齐方式、启动地址、共享内存区域和
允许 RFuzz 改变的中断/debug 输入。只有已经实现合法编码检查的扩展才进入受约束指令
生成；没有实现的扩展仍然可以让 CPU 接收原始 bit，但结果只能算原始输入测试。

#### ④ 一次可重复的短测入口

组合器会自动生成顶层和 `sources.f`，但新 CPU 还需要一条能运行 Verilator 语法/连接检查
和有限时钟短测的命令。短测至少要证明 CPU 能退出复位，并在取指或数据端口产生请求；它
不是完整软件功能测试。

### 5.3 新 CPU 的实际接入步骤

```text
放入固定版本的完整 CPU 源码
        ↓
填写 CPU 接口说明文件和 ISA/测试参数
        ↓
源码核对器确认顶层、端口、宽度、方向和复位
        ↓
按字段语义选择 OBI/AXI 等适配器
        ↓
把取指/数据访问转换为 processor-memory-beat@1
        ↓
生成 generic_composition_top.sv 和 sources.f
        ↓
Verilator lint + 有界短测
        ↓
同一个 CPU 再换一个外设组合，确认不是“一次性特化接线”
```

通用生成命令的形状如下；32 位 CPU 使用 `--isa-xlen 32`，64 位 CPU 改为 64，并按实际
支持情况填写扩展：

```bash
PYTHONPATH=src python3 scripts/generate_composition.py \
  --interface-description configs/cpus/<cpu>/interface_description.json \
  --base-dir . \
  --out-dir runs/examples/<cpu>-composition \
  --isa-xlen 32 \
  --isa-extension I --isa-extension M --isa-extension C \
  --constrained
```

生成后先看 `composition/generic_composition_top.sv` 和 `composition/sources.f`：前者
确认实际连线，后者确认完整源码闭包。再看
`composition/processor_execution.v1.json`，确认取指和数据端口使用了正确适配器；最后
运行该 CPU 的短测入口。只通过 Python 规划而没有通过 Verilator，不算 CPU 接入完成。

### 5.4 增加一个新外设至少要准备什么

外设需要提供一份“怎么找到并连接它”的说明，内容至少包括：

1. 外设顶层模块名、完整 RTL 源码和 include/宏定义；
2. 原生总线类型，以及读写请求、地址、写数据、byte-enable、返回数据、ready/error
   等端口的真实名字和位宽；
3. 地址区间大小、对齐要求、支持的访问宽度和 partial write 行为；
4. 复位后的默认值、等待周期上限、错误响应方式和可选中断输出；
5. 如果使用参数（例如 FIFO 深度、计时器宽度），参数的合法范围和默认值。

如果外设本身已经使用统一的 `processor-memory-beat@1` 字段，组合器可以直接把它放入
地址图；如果外设使用 AXI4-Lite、APB4 或 TL-UL，系统会在 CPU 和外设之间加入相应桥，
桥的工作是把统一的读写字段翻译成外设原生总线的握手顺序。使用一个当前没有桥的总线，
不能只补一份说明文件，必须先实现桥并验证读、写、等待、错误和复位行为。

### 5.5 新外设的实际接入步骤

```text
准备外设 RTL 和连接说明
        ↓
检查协议桥、数据宽度、对齐和 byte-enable
        ↓
自动分配不重叠地址区间
        ↓
生成 CPU → 统一内存访问 → 外设桥 → 外设的接线
        ↓
把外设 RTL、桥和顶层一起写入 sources.f
        ↓
Verilator lint + 有界请求/响应短测
        ↓
让同一个外设出现在至少两个 CPU 组合中
```

外设短测证明的是“地址能到达、协议能握手、响应能返回、复位能恢复”。它不自动证明
每一个寄存器字段的功能，也不等同于 RFuzz 已经对该外设完成深度功能覆盖；要做后者，
还需要把外设访问路径接到 live RFuzz 输入和反馈统计中。

### 5.6 接入完成的最低证据

新 CPU 或外设只有同时满足下面几项，才算真正加入系统：

| 证据 | 说明 |
| --- | --- |
| 源码核对通过 | 声明的顶层、端口、宽度、方向和依赖文件都在固定源码中找到。 |
| 顶层生成成功 | `generic_composition_top.sv` 中能看到真实实例和实际连接。 |
| 编译清单完整 | `sources.f` 包含 CPU/外设 RTL、桥、适配器和生成顶层。 |
| Verilator 检查通过 | 没有未定义模块、端口悬空、宽度错误或语法错误。 |
| 有界短测通过 | 在限定周期内观察到预期的请求/响应和 reset-time progress。 |
| 至少一次复用 | 同一 CPU 或外设换到另一个组合仍能通过，证明接入依赖协议和字段，而不是某个固定顶层。 |

当前仓库中的复用例子是：Ibex、CV32E40P、CV32E20 使用 32 位处理器边界，CVA6 使用
64 位处理器边界；真实 RAM、UART、SPI、Timer、GPIO 分别通过 TL-UL、AXI4-Lite 或
APB4 桥接。新组件按照同样的“说明真实端口 → 自动接线 → lint → 短测 → 换组合复用”
流程接入即可。
