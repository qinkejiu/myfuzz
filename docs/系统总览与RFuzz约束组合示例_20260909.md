# myfuzz 系统总览、自动组合与 RFuzz 约束示例

> 文档版本：2026-09-09
>
> 本文对应分支 `feature/ibex-protocol-longrun` 的当前实现。文中把“协议已声明支持”“生成器可渲染”和“真实 RTL 矩阵已经跑过”分开说明，避免把三者混为一谈。

## 0. 先给结论

系统的核心思想是：CPU 和外设不按名称硬编码连接，而是各自提供一份“说明文件”。
CPU 的说明文件列出源码位置、顶层模块和真实端口；外设的说明文件列出模块和原生总线。组合器从源码中核对这些信息，再把 CPU 接口转换成一个
内部统一的内存访问格式。RFuzz 的随机 bit 串仍然是唯一输入来源，约束转导器只修复
“必须满足 ISA/协议的位”，并维护有限状态、共享内存和超时。

系统需要以下几类说明，含义都是具体的：

| 说明         | 里面写什么                                                   | 当前示例                                                     |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| CPU 接口说明 | CPU 源码位置、顶层模块、时钟/复位、取指端口、数据端口、中断端口的真实名字和方向。 | `configs/cpus/ibex/official_core_interface_description.json` |
| 外设连接说明 | 外设模块位置、地址范围、数据宽度、原生总线、需要编译的源码文件。 | `src/myfuzz/components/profiles/real_uart.json` 等           |
| 协议规则说明 | 一次读写需要哪些信号、信号的先后关系、哪些字段必须一致、最长等待多久。 | `src/myfuzz/protocols/plugins/*.json`                        |
| 测试配置     | ISA、启动地址、共享内存、可随机的中断/debug 输入和测试时长。 | `examples/real_ibex_rfuzz/input/ibex-scratch.json`           |
| 生成结果     | 最终接线、输入 bit 的含义、源文件清单和约束逻辑。            | `generic_composition_top.sv`、`input_layout.json`、`sources.f` |

如果只是运行现成示例，通常只需要看两个输入：CPU 接口说明文件和示例配置文件；其余
规则由系统从源码和仓库中的协议/外设说明中生成。

### 0.1 最短操作流程

把整个系统当成“按插头形状自动接线”的工具即可：

1. 找到 CPU 的 HDL 源码，并在 CPU 接口说明文件中写出顶层模块、时钟/复位、取指和
   数据端口的实际名字。
2. 在测试配置中写明 ISA（例如 `RV32IMC`）、启动地址、哪些中断允许随机，以及取指
   和数据是否共享同一块测试内存。
3. 运行组合命令。系统会检查端口是否真的存在，并自动生成适配器、仲裁器、内存响应
   逻辑和顶层 SystemVerilog。
4. RFuzz 每周期给出一段随机 bit。系统只修改必须修改的 opcode/握手/依赖位，其余位
   继续保持随机，然后把生成的顶层交给 Verilator 运行。
5. 查看生成目录中的 `generic_composition_top.sv`（最终接线）和
   `input_layout.json`（一条 RFuzz 输入各 bit 的含义）。

外设也是同样的方式：外设说明文件告诉系统“模块在哪里、地址是多少、原生总线是哪种”，
系统再自动插入对应桥接模块。用户不需要为每个 CPU 手写一套新的顶层接线。

```text
CPU/外设源码 + 接口描述 + ISA/协议声明
                  │
                  ▼
        源码核对：核对真实端口、宽度、方向、时钟/复位
                  │
                  ▼
      生成接线施工图：接口组匹配、适配器、地址图、执行边界、输入布局
                  │
       ┌──────────┴──────────┐
       ▼                     ▼
  生成 generic_top       生成 RFuzz 契约转导器
  OBI/AXI/TL/APB 适配器    ISA 修复 + 协议 FSM + 共享内存
       │                     │
       └──────────┬──────────┘
                  ▼
        Verilator 真实 CPU/外设 RTL + live RFuzz
```

## 2. 自动组合是怎么做的

### 2.1 输入

一个真实组合至少需要以下五类输入。它们分别回答“源码在哪里”“端口怎么接”“总线怎么
握手”“外设在哪里”和“本次测试允许什么”：

1. **CPU 接口说明文件**：例如
   `configs/cpus/ibex/official_core_interface_description.json`。它给出源码根、固定
   revision、顶层模块、源码文件/`include_roots`，以及每个端口属于取指、数据、时钟、
   复位还是中断，端口在源码中的实际名字是什么。
2. **被固定版本的 HDL 源码**：源码核对器会重新读取声明的硬件描述语言源码，核对端口是真实存在的，
   并记录方向、宽度、时钟/复位、连续/时序赋值和源码位置。说明文件中的 width、direction
   不是无条件信任的替代品。
3. **协议规则文件**：提供信号字段集合、能力上限、布尔修复动作和时序规则。文件位于
   `src/myfuzz/protocols/plugins/`。
4. **外设说明文件**：给出外设模块名、地址对齐/大小、真实源码路径、协议特性和
   参数范围。文件位于 `src/myfuzz/components/profiles/`。内置组件目录默认不自动加载
   `real_*.json`，真实矩阵显式选择这些真实外设，防止它们意外进入普通短测。
5. **ISA/测试约束**：例如 RV32IMC、共享内存区域、可随机化的
   外部字段、测试头和转导器上限。

### 2.2 组合步骤

```text
① 读取 CPU 接口说明 JSON
② 源码核对器分析完整源码集合并锁定版本
③ 根据接口组用途、协议和字段角色匹配 CPU 适配器
④ 将取指/数据端口归一化为统一内存访问格式 `processor-memory-beat@1`
⑤ 选择外设说明、检查协议能力、生成非重叠地址区间
⑥ 生成接线施工图、RFuzz 输入位布局、CPU 执行边界和内存访问后端
⑦ 生成顶层 generic_composition_top.sv 和 sources.f
⑧ 受约束模式额外编译约束转导器和 RFuzz 字节打包器
⑨ 生成阶段先做 Verilator 语法/连接检查并原子发布；发布后再执行有界短测，二者都通过才算全流程成功
```

上面的九步可以分成三个阶段：①—⑤是在确认“能不能接”，⑥—⑧是在写出“应该怎样
接”，⑨是在确认“写出的东西真的能编译和运行”。组合器不会因为 CPU 名字熟悉就跳过
其中任何一步。

#### ① 读取 CPU 接口说明

组合命令首先读取 `--interface-description` 指向的说明文件，同时读取命令行提供的
ISA、协议优先级、外设选择和受约束模式参数。此时只做读取和格式检查，不生成顶层。

系统会得到这些最基本的事实：

- CPU 源码根目录、固定版本、顶层模块名和源码文件列表；
- include 目录、宏定义和编译参数；
- 哪个端口是时钟、哪个端口是复位；
- 哪些端口负责取指，哪些端口负责数据读写；
- 哪些端口是中断、debug、启动地址等外部控制；
- 每个端口的真实名字、方向、位宽和所在源码位置。

路径会被限制在 `--base-dir` 下面，说明文件不能通过 `..` 指向项目外部文件。JSON
解析失败、必填字段缺失、源码根目录不存在或端点用途没有写清时，组合立即停止，
不会创建一个不完整的输出目录。

#### ② 打开完整源码，核对说明是否属实

说明文件只是“待核对的清单”，不是事实本身。源码核对器会打开清单中的 HDL 文件和
include 目录，确认：

1. 顶层模块和被引用的模块确实存在；
2. 声明的端口确实出现在源码中，方向和位宽一致；
3. 端口所在的模块、时钟和复位关系一致；
4. 取指/数据端口确实具有请求、接受、响应等协议字段，而不是只写了一个同名信号；
5. 所有需要编译的源码都能解析出稳定的文件清单。

核对器还会为源码集合计算来源校验值。之后只要 CPU 源码、接口说明或桥的源码在生成
过程中发生变化，校验值就会不一致，发布会被拒绝。这样可以避免“说明文件指向了旧
版本，但实际编译了另一版本”的情况。

这一步失败的典型原因是：文件缺失、顶层端口名称写错、端口宽度不同、时钟/复位无法
判定、同一用途有多个冲突端口，或源码依赖超出项目根目录。

#### ③ 按协议选择 CPU 适配器

组合器先把端口按用途分组，而不是按 CPU 名称分组：

```text
clock/reset             → 组合时钟和复位
instruction_memory      → CPU 取指请求和指令响应
data_memory             → CPU 数据读写请求和数据响应
interrupt/debug/boot    → 外部控制输入
```

对每个内存端口，系统把“协议名称、字段角色、方向和位宽”与已有协议规则逐项比较。
例如一个 OBI 取指口至少要能解释请求、授权、地址、响应有效和返回指令；数据口还要
能解释读写方向、写数据和字节使能。字段缺失、输入输出方向相反、地址/数据宽度无法
统一时，不能靠改实例名解决，组合会直接失败。

CPU 适配器的选择结果会记录：适配器模块名、适配器源码、参数、每个 CPU 物理端口
连接到哪个统一字段，以及使用了哪一种复位语义。当前处理器适配路径要求每个处理器
组合只有一个时钟端点和一个复位端点，并要求适配器看到的复位契约为 active-low、同步
复位；不满足这一边界的 CPU 需要先增加专用适配器。

#### ④ 把 CPU 原生端口变成统一内存访问

这里的“统一内存访问”不是新的 RISC-V 指令，也不是 RFuzz 的输入格式，更不是要求
Ibex、CV32 或 CVA6 原生支持的新总线。它只是组合器内部使用的“转接头”：不同 CPU
先把自己的端口翻译成同一组字段，处理完以后，再把结果翻译回 CPU 原来的端口。

以 Ibex 为例，它原本使用 `instr_req_o`、`instr_addr_o`、`instr_gnt_i`、
`instr_rvalid_i`、`instr_rdata_i`；另一个 CPU 可能使用完全不同的信号名字。适配器不
要求这些名字相同，只要求这些信号表达的含义能够对应起来：

```text
Ibex 原生端口                  适配器                  统一读写字段
instr_req_o / instr_addr_o  ───────────────→  req_valid / addr / write=0
data_req_o / data_we_o     ───────────────→  req_valid / write
data_wdata_o / data_be_o   ───────────────→  wdata / be
统一字段的 rdata/error      ←───────────────  instr_rdata_i 或 data_rdata_i
```

`processor-memory-beat@1` 可以把名字拆开理解：`processor` 是处理器发起的访问，
`memory` 是一次内存/外设读写，`beat` 是“一笔访问”，`@1` 是这套字段的版本 1。
它只描述一次读写，不描述 CPU 执行哪条 RISC-V 指令。

| 字段 | 直白含义 |
| --- | --- |
| `req_valid` | 发起方说“我现在有一笔访问”。 |
| `req_ready` | 接收方说“我现在能接收”。两者同周期为 1，访问才真正开始。 |
| `write` | `0` 是读，`1` 是写；取指一定是 0。 |
| `addr` | 要访问的地址。 |
| `wdata` | 写操作要写入的数据；读操作不用它。 |
| `be` | 哪些字节有效；32 位数据通常对应 4 位 byte-enable。 |
| `rsp_valid` | 接收方说“这笔访问的结果准备好了”。 |
| `rsp_ready` | 发起方说“我能接收结果”。两者同周期为 1，响应才完成。 |
| `rdata` | 返回的数据；取指时就是返回给 CPU 的 32 位指令 bit。 |
| `error` | 访问失败，例如地址未映射或等待超时。 |

一次 Ibex 取指可以具体写成下面这样：

```text
周期 t：
  Ibex：instr_req_o=1，instr_addr_o=0x00000080
  适配器：req_valid=1，write=0，addr=0x00000080
  后端：req_ready=1，表示已经接收这笔请求

周期 t+N：
  后端：rsp_valid=1，rdata=某个 32 位指令，error=0
  适配器：instr_rvalid_i=1，instr_rdata_i=该指令
  Ibex：收到指令，继续执行
```

数据写入也是同样的翻译。例如 Ibex 给出
`data_req_o=1、data_we_o=1、data_addr_o=0x10004、data_wdata_o=0x12345678、data_be_o=1111`，
适配器就生成 `req_valid=1、write=1、addr=0x10004、wdata=0x12345678、be=1111`；
后端根据地址把这笔写请求送到 RAM 或外设桥。

RFuzz 与这个统一字段的关系要分两种情况：

- **受约束 RFuzz 路径**：CPU 先通过 `instr_req_o` 发起取指，RFuzz 的随机 bit 进入
  约束转导器，由转导器决定返回哪条合法指令或哪个内存响应；
- **真实外设路径**：CPU 的地址经过统一字段和地址选择，送到 RAM、UART、SPI、Timer
  或 GPIO 的桥，外设的返回值再沿适配器回到 CPU。

所以，统一字段不是替换 RFuzz，也不是替 CPU 取指，而是把“CPU 发出访问”和“外部返回
结果”用同一种写法表示。

它还规定三个简单的时序边界：

- 一次只处理一笔访问，不做 AXI burst 那样的多笔连续传输；
- 后端最多保留一笔尚未返回的请求。Ibex 的取指和数据两路同时存在时，仲裁器会先后
  处理它们，避免两笔请求互相覆盖；
- 默认最多等待 16 个周期，超时返回确定性错误并清理旧请求，避免 CPU 永久卡住。

如果 CPU 有独立的取指口和数据口，系统生成两条翻译路由，并把取指路由设为只读；如果
只有一个统一内存口，就生成一条路由。两条路由的地址宽度、数据宽度和复位语义必须一致，
适配器已经产生的握手输入也不会再次占用 RFuzz 输入 bit。

这一步生成的 `processor_execution.v1.json` 只是“翻译表”：它记录 CPU 哪个物理端口
连接到适配器的哪个字段。真正执行这些连接的是 `generic_composition_top.sv`，不是这个
JSON 文件。

#### ⑤ 选择外设、匹配协议并分配地址

系统会对每一个外设逐个执行以下检查：

1. 外设被标记为可用，顶层模块和全部 RTL 源码存在；
2. 外设声明的原生协议有可用桥，或者外设直接使用统一内存访问字段；
3. CPU 与外设的地址宽度、数据宽度、对齐方式和 byte-enable 规则兼容；
4. 读、写、等待、错误、复位和中断端口都有明确的连接含义；
5. 如果有多个协议或多个 CPU 端口都能连接，命令行优先级必须把选择结果变成唯一。

通过匹配后，组合器按地址宽度、外设对齐要求和默认大小确定连续的非重叠地址区间，
并为能产生中断的外设分配中断路由。地址重叠、协议选择含糊、外设源码缺失、依赖的
源端口未绑定，都会在这里失败。

例如在真实 CPU × 外设矩阵中，CPU 的统一访问字段经过 TL-UL、AXI4-Lite 或 APB4
桥，再到 RAM、UART、SPI、Timer 或 GPIO；在受约束 CPU-only 示例中，内存响应由约束
转导器提供，因此不会因为仓库里存在 UART 文件就自动把 UART 接进来。

#### ⑥ 生成接线施工图、输入布局和运行边界

前五步得到的是“事实”，第六步把事实写成几份可以互相核对的计划：

- `composition_ir.json`：CPU、外设、适配器、地址区间、中断路由、源码来源和警告；
- `input_layout.json`：RFuzz 一条周期输入的总位宽、每个字段的 bit 区间、方向和
  约束类别；
- `processor_execution.v1.json`：取指/数据路由、适配器、统一字段和复位契约；
- `processor_backend.v1.json`：单路直连或双路仲裁、地址解码、未映射地址错误、
  最大等待周期、取消和复位恢复；
- 源码文件列表、include 路径、宏定义和每份源码的校验值。

生成这些计划时还会检查输入位是否被两个模块同时驱动、打包字段是否有重叠或空洞、
取指/数据宽度是否一致、所有地址区间是否互不重叠。计划不完整时不会进入文件发布阶段。

处理器后端只有一个访问来源时使用 direct 路由；同时有取指和数据来源时使用
round-robin 仲裁器。两种模式都限制为单个未完成请求，未映射地址返回确定性错误，超时
会取消或排空旧请求后才允许复用，避免随机输入让 CPU 永久卡住。

#### ⑦ 生成顶层 SystemVerilog 和编译清单

`generic_composition_top.sv` 是最终的接线文件，不是说明文件。处理器组合通常按下面
的顺序实例化：

```text
真实 CPU
  → CPU 原生协议适配器
  → （取指/数据双路时）内存仲裁器
  → processor-memory-beat 后端
  → 约束转导器或真实外设桥/外设
```

如果选择了真实外设，顶层还会包含对应桥、目标模块、地址选择和中断连线；如果没有
选择外设，则后端只连接到契约内存或测试内存。

`sources.f` 会把 CPU 固定版本的 HDL、include 目录/宏、适配器、仲裁器、外设桥、外设
RTL 和生成顶层按编译顺序列出。它的作用是保证 Verilator 编译的是完整源码闭包，而
不是只编译一个能过语法的空 wrapper。

#### ⑧ 在受约束模式生成 RFuzz 约束硬件

只有传入 `--constrained` 并给出 XLEN 和 ISA 扩展时，才执行这一步。系统把以下内容
编译成一个受约束输入计划：

- 允许的 ISA 指令模板，例如 RV32IMC；
- 统一内存访问协议的握手和最大等待周期；
- instruction/data 是否共享 `main` 内存；
- 共享内存最多保存多少个 beat；
- 是否允许随机错误响应，以及外部中断/debug 哪些字段可随机。

然后生成四个互相对应的结果：

```text
contract_transducer.json      约束规则和 hash
contract_transducer.sv        实际执行约束的 RTL
rfuzz_input_transport.json    RFuzz 字节如何对应周期 bit
rfuzz_input_transport.sv      测试平台的字节到 bit 边界
```

受约束顶层接收的是 `rfuzz_cycle_bits`。RFuzz 客户端先按 transport 规则打包，转导器
再根据 ISA 模板和协议状态修复必要字段；未被约束的寄存器、立即数、响应数据和外部
输入仍然保持随机。没有 `--constrained` 时仍可生成输入布局和 transport，但不会生成
ISA 合法化转导器。

### 2.3 生成目录：每个文件是什么、什么时候看

组合命令成功后，系统会生成一个目录。这个目录不是让用户继续手工填写的配置，而是
“自动接线的结果”和“这次测试实际使用的输入规则”。以真实 Ibex 受约束运行结果为例：

```text
runs/examples/contract-rfuzz-final-replay/sim/
├── composition/                 # 自动接线和编译所需的全部文件
├── test_header.json              # 本次测试固定的启动/复位参数
├── runtime_layout.json           # 运行时真正采用的 RFuzz 位布局
└── runtime_transport.json        # 运行时真正采用的字节打包方式
```

| 文件 | 它实际回答的问题 | 什么时候看 |
| --- | --- | --- |
| `composition_ir.json` | “这次到底接了谁？”列出 CPU、外设、适配器、地址区间、中断连接、源码来源和校验值。 | 想确认选中了哪个 CPU/外设，或检查地址是否冲突时。 |
| `input_layout.json` | “RFuzz 每一位输入送到哪里？”列出每周期的字段、位区间、宽度和总位数。 | 想知道随机 bit 如何变成指令选择、内存响应或中断时。 |
| `processor_execution.v1.json` | “CPU 的取指口和数据口分别怎么接？”记录每一路端口使用的协议适配器、宽度和方向。 | 换 CPU 或怀疑端口接错时。 |
| `processor_backend.v1.json` | “CPU 发出一次读写后由谁响应？”记录取指/数据两路如何仲裁、地址如何分发、未映射地址和超时如何处理。 | 想理解内存响应、等待周期或错误响应时。 |
| `contract_transducer.json` | “约束器准备修复什么？”记录 ISA 合法指令范围、协议握手、共享内存容量和最大等待周期。 | 受约束模式下，想检查哪些随机字段会被修复时。 |
| `contract_transducer.sv` | “约束器在硬件中怎样执行？”是上一文件对应的可编译 RTL，不是 Python 模拟结果。 | 想看实际约束逻辑，或 Verilator 报错时。 |
| `rfuzz_input_transport.json` | “一条 RFuzz 记录怎样装进输入总线？”记录 raw bit 的总宽度、字节顺序、padding 和 16 字节记录格式。 | 自己写 RFuzz 客户端或复现输入时。 |
| `rfuzz_input_transport.sv` | “字节怎样变成顶层的 bit 总线？”是测试平台与顶层之间的打包边界，不负责决定哪条指令合法。 | 排查输入位序、大小端或 padding 问题时。 |
| `generic_composition_top.sv` | “最终的硬件接线是什么？”真正实例化 CPU、协议适配器、仲裁器、内存后端、约束器或真实外设。 | 想看最终连线，或需要 Verilator 编译顶层时。 |
| `sources.f` | “编译时到底用了哪些源码？”列出固定版本的 CPU/外设 RTL、适配器、桥、约束器和顶层文件。 | 想复现编译，或核对是否误用了另一份源码时。 |

外层三个运行文件也有明确分工：`test_header.json` 保存启动地址、复位周期、执行周期、
hart id 和相关校验值；`runtime_layout.json` 与 `runtime_transport.json` 是测试程序
真正读到的布局和打包规则。它们用于复现，不能替代 `generic_composition_top.sv`。



按目的查文件，可以直接这样做：

```text
看最终接线       → generic_composition_top.sv
看 CPU/外设选择  → composition_ir.json
看取指/数据适配  → processor_execution.v1.json
看仲裁/地址/超时  → processor_backend.v1.json
看 RFuzz 位含义  → input_layout.json + rfuzz_input_transport.json
看 ISA/协议修复  → contract_transducer.json（受约束模式才有）
复现一次测试      → test_header.json + runtime_*.json + sources.f
```

一条输入在这些文件中的流向是：RFuzz 字节先按 `rfuzz_input_transport.json` 还原为
周期 bit；`generic_composition_top.sv` 把它送入 CPU 和约束器；CPU 发出的取指/数据
请求经适配器变成统一的 `processor-memory-beat@1`；后端按地址和内存状态返回响应。
因此 `input_layout.json` 解释“输入是什么”，`processor_execution.v1.json` 解释“CPU
怎么接”，`generic_composition_top.sv` 才是“线已经怎样连起来”。



## 3. RFuzz 输入约束：随机来源不变，约束只修复必要关系

这里的“约束”不是把输入替换成固定程序，而是把一个 cycle 的随机 bit 分成几段：

```text
原始 RFuzz bits
  ├─ instruction selector/payload ──┐
  ├─ response choice/data           ├─ contract_transducer
  └─ 外部 IRQ/debug bits ───────────┘
       选择合法操作 → 布尔/模板修复 → 协议 FSM → 共享内存/响应
```

### 3.1 ISA：先选择操作，再保留随机性地修复编码

指令约束模块当前对 I/M/C 做合法编码验证：

1. 用 8 位 `selector` 在当前 ISA 支持的模板集合中均衡选择一个操作；
2. 用 `payload` 填充寄存器、立即数等自由字段；
3. 只把 opcode、funct、格式位和必要的非零约束写回模板固定值；
5. `illegal_instruction=false` 时不选择非法模板，`true` 时才加入非法选项。

因此输入仍然能产生大量不同寄存器和立即数，而不是每次都得到同一条指令。当前
公开实现只验证 I/M/C；Zicsr、F/D/A/B 等未实现扩展不会被假装成合法指令。合法
**编码**也不保证一定有用：分支目标、权限或地址可能让 CPU trap。

### 3.1.1 当前实际支持的 RISC-V 指令范围

这里的范围指“RFuzz 输入约束器能够主动选择并修复为合法编码”的范围，不是说 CPU
本身只能执行这些指令。

| ISA 配置 | 32 位指令模板 | 16 位压缩指令模板 | 说明                                                  |
| -------- | ------------: | ----------------: | ----------------------------------------------------- |
| RV32I    |            42 |                 0 | 基础整数运算、访存、分支、跳转、`FENCE`、基本系统指令 |
| RV32IM   |            50 |                 0 | RV32I 加乘法/除法/余数指令                            |
| RV32IMC  |            50 |                26 | 当前 Ibex 示例使用的范围                              |
| RV64I    |            54 |                 0 | 增加 64 位访存和 word 运算                            |
| RV64IM   |            67 |                 0 | 再增加 RV64 的乘除法 word 版本                        |
| RV64IMC  |            67 |                32 | 增加 RV64 压缩指令                                    |

32 位基础指令包括：

- 整数立即数：`ADDI`、`SLTI`、`SLTIU`、`XORI`、`ORI`、`ANDI`、`SLLI`、`SRLI`、`SRAI`；
- 寄存器整数运算：`ADD`、`SUB`、`SLL`、`SLT`、`SLTU`、`XOR`、`SRL`、`SRA`、`OR`、`AND`；
- RV32 访存：`LB`、`LH`、`LW`、`LBU`、`LHU`、`SB`、`SH`、`SW`；RV64 另有
  `LD`、`LWU`、`SD`；
- 分支：`BEQ`、`BNE`、`BLT`、`BGE`、`BLTU`、`BGEU`；
- 跳转和地址生成：`AUIPC`、`LUI`、`JAL`、`JALR`；
- 其他：`FENCE`、`ECALL`、`EBREAK`、`WFI`，以及按特权模式允许的 `MRET`/`SRET`；
- `M` 扩展：`MUL`、`MULH`、`MULHSU`、`MULHU`、`DIV`、`DIVU`、`REM`、`REMU`；
- RV64 word 运算：`ADDIW`、`SLLIW`、`SRLIW`、`SRAIW`、`ADDW`、`SLLW`、`SRLW`、
  `SUBW`、`SRAW`，以及 `MULW`、`DIVW`、`DIVUW`、`REMW`、`REMUW`。

当前没有主动生成或验证 `A` 原子、`F/D/Q` 浮点、`B` 位操作、`V` 向量、CSR 指令
（`CSRRW/CSRRS/CSRRC` 等）、`FENCE.I`、`SFENCE.VMA` 和自定义扩展。通用输入布局
可以把未知扩展当作完全原始的指令 bit，但受约束 RFuzz 执行只接受上表中的 I/M/C
集合；未知扩展不能被标记为“已经完成合法指令约束”。

最后，合法指令编码不等于一定能顺利执行：随机分支目标、访存地址、权限状态仍可能
使真实 CPU 产生 trap。当前约束器保证的是编码字段和跨周期内存/协议关系，不模拟完整
的寄存器语义、CSR 状态机或操作系统。

### 3.1.2 一条指令的实际约束：`ADDI x5, x6, 13`

下面以 RV32IMC、32 位指令槽、`illegal_instruction=false` 为例。假设这一周期的
`instruction_selector=0`，`instruction_payload=0x00d30280`，并且没有选择压缩指令。

1. 选择器在 32 位模板中选中第一个模板 `ADDI`。选择器只负责选“操作类型”，不是直
   接把一个完整指令塞给 CPU。
2. `ADDI` 模板把必须固定的字段写死：`opcode[6:0]=0010011`、
   `funct3[14:12]=000`。`rd`、`rs1` 和 12 位立即数仍从 payload 保留。
3. 这个 payload 提供 `rd=5`、`rs1=6`、`imm=13`。模板修复只改 opcode（payload
   原来低 7 位不是合法的 `ADDI` opcode），其他自由字段不改。
4. 得到的字段是：

   ```text
   imm[11:0] = 000000001101
   rs1       = 00110       (x6)
   funct3    = 000
   rd        = 00101       (x5)
   opcode    = 0010011
   ```

   拼接后的 32 位指令为 `0x00d30293`，也就是 `ADDI x5, x6, 13`。
5. 这 32 位结果作为一次取指响应的 `rdata`，通过适配器回到 CPU 的
   `instr_rdata_i`。CPU 收到 `instr_rvalid_i` 后再解码执行。

这里没有把寄存器和立即数固定成某个常量；换一个 payload 就会得到不同的 `rd`、`rs1`
或立即数。约束器只修复 ISA 要求必须相等的位。对于 `C.ADDI4SPN` 等压缩指令，还会
额外修复“立即数不能为零”“寄存器不能为零”等必要关系。

### 3.2 协议：只保证一次访问能有序完成

协议约束实际作用在 RFuzz 记录的 `response_choice` 三个 bit 上。这个字段在当前 104 位
布局的 `[51:49]`，含义是：

```text
response_choice[0] = 1：请求可以被接受
response_choice[1] = 1：已有请求可以返回响应
response_choice[2] = 1：本次响应尝试报错（只有 allow_error=true 才生效）
```

转导器不是简单地把这三个 bit 原样接到 CPU，而是先看自己处于哪个状态：

| 当前状态 | RFuzz bit | 转导器输出 | 结果 |
| --- | --- | --- | --- |
| 没有未完成请求，CPU 有请求 | bit0=1 | `req_ready=1` | 接受这一笔请求并保存地址/读写信息 |
| 没有未完成请求，CPU 有请求 | bit0=0 | `req_ready=0` | 不接受，下一拍继续尝试 |
| 已有未完成请求 | bit1=1 | `rsp_valid=1` | 返回数据或错误，结束这一笔请求 |
| 已有未完成请求 | bit1=0 | `rsp_valid=0` | 保留请求，下一拍继续等待 |

例如：

```text
response_choice=000：不接受新请求，也不返回响应
response_choice=001：空闲时接受请求；已有请求时 bit0 没有返回作用
response_choice=010：空闲时 bit1 被忽略；已有请求时返回响应
response_choice=111：空闲时接受；已有请求时返回，但本例 allow_error=false，bit2 被屏蔽
```

如果连续 16 个周期没有接受请求，转导器强制 `req_ready=1`；如果请求已经保存，又连续
16 个周期没有返回，转导器强制 `rsp_valid=1` 并结束等待。响应周期不能同时接受第二笔
请求，因此不会发生“响应属于哪一笔请求”不明确的问题。`req_valid`、地址和写数据不在
这三个随机 bit 中，而是由 CPU 产生；RFuzz 只控制接受/等待/返回/错误和返回数据。

AXI4-Lite、APB4、TL-UL 桥接后也遵守同一规则：AXI-Lite 等读写通道完成，APB4 先 setup
再 access，TL-UL 要求 A/D 通道配对。协议约束的结果是“输入 bit 可以随机，但总线不能
乱序或无限等待”。

### 3.3 共享内存和随机地址：地址由 CPU 产生，后端负责收敛

当前 RFuzz 周期布局没有 `address` 字段。地址来自 CPU 的 `instr_addr_o` 或
`data_addr_o`，而这些地址又是 CPU 根据 PC、随机指令、寄存器和之前的返回数据计算出来
的。因此地址可以表现出随机性，但不是 RFuzz 直接把 32 位地址接进 CPU。

收到 CPU 地址后，后端按一次 beat 处理：

1. 32 位数据时用 `base = addr & ~0x3` 对齐到 4 字节；64 位数据时对齐到 8 字节；
2. `be` 指出本次读写使用哪些字节；低位地址不会单独生成另一笔 beat；
3. 用 `(memory_domain, base)` 作为稀疏内存的键。新地址分配一个槽，旧地址直接取已保存
   的内容；
4. 第一次取指向新地址时写入修复后的合法指令；第一次数据读向新地址时写入随机
   `response_data`；CPU 写入时按 `be` 更新相应字节；
5. 一次测试最多保存 256 个 beat。新地址超过容量时返回 `capacity_error`，不随机驱逐
   旧地址；测试开始时清空这些槽位。

例如 CPU 产生 `data_addr_o=0x1003`、`data_be_o=0100`：

```text
对齐地址：base = 0x1000
本次访问：只操作 base 对应 beat 的第 2 号 byte lane（从 0 开始，即第三个字节）
后续访问 0x1000–0x1003：看到同一 beat 中已经保存的字节
```

受约束 CPU-only 模式把所有满足地址位宽的 CPU 地址交给这份稀疏内存处理，所以随机地址
不会凭空连接到 UART 或 GPIO；它只会占用一个内存槽，或者在容量满时得到错误。若数据生成
的 beat 随后被当作指令取回，转导器返回 `provenance_error`，避免把任意数据误当程序；
CPU 自己写入后再取指则允许精确返回。

真实 CPU × 外设模式则使用固定地址图：地址命中 RAM/UART/SPI/Timer/GPIO 区间时进入相应
桥接器，地址不在任何区间时由统一后端返回错误，不会把这笔访问送给某个随机外设。

因此，RFuzz 可以每拍提供新的指令选择、返回数据和控制 bit，CPU 可以由此逐步产生新的
地址；共享内存和地址解码负责让这些随机地址既保持可重复，又不会破坏协议或外设边界。

### 3.4 外部输入和固定控制

RFuzz 只随机接口说明中明确允许随机的输入，例如软件中断、定时器中断、外部中断、
快速中断、NMI 和 debug 请求。

下面这些由测试头固定，不随每条 RFuzz 记录变化：

```text
clock/reset、boot_address、hart_id、fetch_enable、scan_reset、完整性默认值
```

这样做的目的很简单：RFuzz 可以改变 CPU 的外部环境，但不能凭空制造一个不存在的端口，
也不会把复位和启动地址随机到无法解释的状态。

## 4. 数据流：RFuzz、CPU、统一访问和外设怎样连起来

### 4.1 两条方向相反的路径

CPU 的请求和 RFuzz 的刺激不是同一条方向：

```text
CPU 请求方向：
CPU 原生端口
  → CPU 适配器
  → 取指/数据两路 processor-memory-beat 请求
  → 内存仲裁器
  → 统一内存后端
  → 地址解码
  → RAM 或外设桥

RFuzz 刺激方向（受约束模式）：
RFuzz 字节
  → rfuzz_input_transport.sv
  → contract_transducer.sv
  → 合法指令、返回数据、等待/错误选择和中断/debug
  → 统一内存后端或 CPU 外部控制输入
```

`processor-memory-beat` 是两条路径之间共同使用的字段格式，不是额外的一颗 CPU 或
外设。CPU 适配器输出统一请求，仲裁器把取指/数据两路合成一路，后端再把响应送回原来
的适配器。

### 4.2 CPU 如何得到 RFuzz 产生的指令

这里要区分两种情况：

- **静态内存模式**：后端像 ROM 一样保存一份固定程序，CPU 给出地址后，直接返回
  `memory[address]`。同一个地址每次得到相同的指令。
- **受约束 RFuzz 模式**：后端没有预先写好的完整程序。CPU 先给出取指地址，约束转导器
  再使用当前 RFuzz 周期中的选择器和 payload 生成一条合法指令，返回给 CPU，并把它保存
  到这个地址。之后再次访问同一个 beat 时，优先返回已保存的内容。

以前的普通静态示例可以把取指写成 `instr_rdata = boot_rom_instruction(instr_addr)`；
地址只是查 ROM。启用 `--constrained` 后，生成的顶层改为接收 `rfuzz_cycle_bits`，并
实例化 `myfuzz_contract_transducer`，所以这一条路径不再使用固定的 boot ROM。两种模式
都保留 CPU 的正常取指接口，变化的是“谁来提供取指响应”。

所以 CPU 并不会“自己计算出一条指令”。CPU 只做三件事：维护 PC、发出取指请求、收到
`instr_rdata_i` 后解码执行。指令 bit 来自内存响应；在受约束模式中，这个响应由 RFuzz
输入经过约束转导器生成。

### 4.3 两条 RFuzz 记录的完整数据流

下面用一段可以产生 `ADDI x5, x6, 13` 的输入说明从字节到 CPU 的全过程。假设：

```text
ISA = RV32IMC
使用 32 位指令槽（instruction_compressed=0）
test_begin 已经完成，CPU 从 boot_address=0x80 开始取指
所有中断、debug 和 response_data 字段都为 0
```

当前 Ibex 组合的每条 RFuzz 记录是 16 字节。有效的 104 位从低到高分布如下，剩下的
低 24 位传输填充为 0：

| bit 区间 | 字段 | 本例用途 |
| --- | --- | --- |
| `[7:0]` | `instruction_selector` | 选择 32 位指令模板 |
| `[15:8]` | `instruction_selector_1` | 16 位压缩槽备用，本例不用 |
| `[47:16]` | `instruction_payload` | 提供寄存器和立即数等自由位 |
| `[48]` | `instruction_compressed` | 0，选择 32 位指令 |
| `[51:49]` | `response_choice` | 1 表示接受请求，2 表示返回响应 |
| `[83:52]` | `response_data` | 数据读时的返回值，本例不用 |
| `[84:103]` | 中断/debug 字段 | 本例全部为 0 |

两个 16 字节记录如下（每行是一拍输入，按大端字节顺序写入）：

```text
第 0 拍：00 00 00 00 00 00 02 00 00 00 00 00 00 00 00 00
第 1 拍：00 00 00 00 00 00 04 00 d3 02 80 00 00 00 00 00
```

传输层的处理是：先把 16 字节解释成 128 位大端整数，再丢掉末尾 24 个填充 bit，得到
104 位 `rfuzz_cycle_bits`。因此：

```text
第 0 拍：response_choice=1，其余字段为 0
第 1 拍：instruction_selector=0
        instruction_payload=0x00d30280
        instruction_compressed=0
        response_choice=2
```

随后硬件中的数据流是：

```text
第 0 拍：RFuzz 客户端
  → rfuzz_input_transport.sv
  → generic_composition_top.rfuzz_cycle_bits
  → contract_transducer.rfuzz_cycle_bits

CPU 取指请求：
  Ibex：instr_req_o=1，instr_addr_o=0x80
  → OBI 取指适配器
  → req_valid=1，write=0，addr=0x80
  → 取指/数据仲裁器
  → processor-memory 后端
  → req_instruction=1 的约束转导器

第 1 拍：约束转导器
  selector=0 选择 ADDI 模板
  payload=0x00d30280
  固定 opcode/funct3，得到 0x00d30293
  → rsp_valid=1，rsp_data=0x00d30293，rsp_error=0
  → 后端
  → 仲裁器
  → OBI 取指适配器
  → Ibex：instr_rvalid_i=1，instr_rdata_i=0x00d30293

CPU：
  解码 0x00d30293
  执行 ADDI x5, x6, 13
  更新 PC 后，再发出下一次取指请求
```

第 0 拍的 `response_choice=1` 只负责让后端接受 CPU 请求；有了未完成请求后，第 1 拍
的 `response_choice=2` 才表示可以返回响应。如果第 1 拍仍然没有返回选择，CPU 会继续
等待，直到达到最大等待周期。

这也说明了“动态”和“静态”的区别：静态 ROM 是地址直接索引固定内容；RFuzz 模式是
地址由 CPU 提供、指令内容由当前 RFuzz 记录选择并修复，第一次返回后再由共享内存保存。
RFuzz 不直接驱动 `instr_req_o` 或 `instr_addr_o`，因为这两个信号是 CPU 的输出；它通过
返回指令、返回数据和中断/debug 输入影响 CPU 的后续状态。

### 4.4 数据访问和真实外设的流动

数据读写遵循同一结构：

```text
CPU data_req_o/data_addr_o/data_we_o
  → 数据适配器
  → processor-memory-beat
  → 仲裁器和统一后端
  → 地址选择外设
  → AXI-Lite/APB4/TL-UL 桥
  → 真实外设
  ← 返回数据或错误
```

在真实外设模式下，UART、SPI、Timer、GPIO 的读写结果来自各自的 RTL；RFuzz 可以继续
提供中断和 debug 等外部输入，但不会把一个随机 `response_data` 强行当成外设寄存器返回值。
在受约束 CPU-only 模式下，没有真实外设时，统一后端由约束转导器直接提供指令和内存响应。

### 4.5 顶层模块在数据流中的位置

`generic_composition_top.sv` 就是上述数据流的总接线文件。它实例化并连接：

```text
CPU
  → CPU 适配器
  → 仲裁器
  → 统一内存后端
  → 地址解码
  → 外设桥接器/约束转导器
  → 真实外设或 RFuzz 响应
```

因此顶层模块不是另一个协议，而是把 CPU、适配器、仲裁器、后端、桥和外设组装成一次
可以编译和运行的完整系统。
